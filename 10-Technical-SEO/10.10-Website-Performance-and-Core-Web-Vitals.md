# 10.10 — Website Performance & Core Web Vitals

[← Domain 10 — Technical SEO](README.md)

Website performance concerns how efficiently a page and its dependencies are delivered, rendered, and kept responsive throughout a user's visit. It includes network transfer, server work, browser execution, rendering, interaction handling, visual stability, and the operational conditions that affect these processes.

Core Web Vitals (CWV) are a focused set of field-oriented metrics for loading performance, responsiveness, and visual stability. They provide useful evidence about real user experience, but they are not a complete performance model, a universal site-quality score, or a deterministic ranking formula. A page can meet all three CWV thresholds and still be slow in other important ways; it can also miss a threshold for reasons that require diagnosis rather than generic optimization. [1][2]

## 1. Current Core Web Vitals

The current Core Web Vitals are Largest Contentful Paint (LCP), Interaction to Next Paint (INP), and Cumulative Layout Shift (CLS). The commonly documented good thresholds are evaluated at the 75th percentile of page visits, with mobile and desktop experiences assessed separately where the data supports that segmentation. [1][2]

| Metric | User experience dimension | Good | Needs improvement | Poor |
|---|---|---:|---:|---:|
| Largest Contentful Paint (LCP) | Loading performance | ≤ 2.5 s | > 2.5 s and ≤ 4.0 s | > 4.0 s |
| Interaction to Next Paint (INP) | Responsiveness | ≤ 200 ms | > 200 ms and ≤ 500 ms | > 500 ms |
| Cumulative Layout Shift (CLS) | Visual stability | ≤ 0.1 | > 0.1 and ≤ 0.25 | > 0.25 |

These thresholds are guidance for evaluating user experience, not pass/fail requirements for crawling or indexing. Recheck the current metric definitions and thresholds before using them in a production standard because the Web Vitals program can evolve. [1][2]

### 1.1 Largest Contentful Paint (LCP)

LCP measures when the largest eligible image or text block in the viewport is rendered relative to the start of navigation. It is intended to approximate when the main content becomes visible, not when every resource or script on the page has finished loading.

The LCP candidate can vary with viewport size, content, personalization, fonts, and navigation context. A lab test and real users may therefore identify different LCP elements for the same URL. Diagnose the element and the conditions under which it becomes the LCP candidate before choosing an optimization. [2][3]

### 1.2 Interaction to Next Paint (INP)

INP assesses a page's responsiveness by observing qualifying click, tap, and keyboard interactions throughout a page visit. The reported value reflects the slowest interaction observed, with some outlier handling; it is not the average duration of all interactions. A page with few interactions may have limited INP observations, while an application with many interactions can expose a wider range of responsiveness problems. [2][4]

INP is not a direct measure of initial page-load speed. A page may render quickly but become unresponsive when a user opens a menu, filters results, submits a form, or interacts with a complex component.

### 1.3 Cumulative Layout Shift (CLS)

CLS measures unexpected visual movement by combining the impact fraction and distance fraction of layout shifts. It is a unitless score, not a time measurement. The metric considers layout instability over the page's lifetime rather than only the first viewport render; shifts associated with recent user input are treated differently from unexpected movement. [2][5]

Common causes include images or embeds without reserved dimensions, late-inserted advertisements or banners, dynamically injected content, and web-font changes that alter text layout. A page can appear stable during a short lab load and still shift later as the user scrolls or content is injected. [5]

## 2. Field data, lab data, and Real User Monitoring

Performance data must be interpreted according to how it was collected. A score without its measurement context is weak evidence.

### 2.1 Field data

Field data represents measurements collected from real page visits. It reflects the mix of devices, browsers, networks, locations, cache states, and user behavior in the measured population.

The Chrome User Experience Report (CrUX) is Google's public dataset of real-world Chrome user experience for eligible pages and origins. It is valuable for understanding broad Chrome user experience and for observing CWV data used in Google-facing tools. It is not a census of every visitor, every browser, or every visit to a site. Eligibility and aggregation rules affect which pages and observations are available. [6]

### 2.2 Lab data

Lab data is collected under controlled, repeatable test conditions. Tools such as Lighthouse and Chrome DevTools can help reproduce loading conditions, inspect network waterfalls, profile JavaScript, and identify rendering bottlenecks.

A lab run represents a particular device profile, network configuration, location, browser version, cache state, and test flow. It cannot reproduce the full distribution of real user conditions or all behavior during a page's lifetime. Lab metrics are therefore useful for diagnosis and regression testing, but should not be presented as a substitute for field experience. [3][7]

### 2.3 Real User Monitoring (RUM)

RUM instruments a site to collect performance observations from its own visitors. Depending on implementation, it can provide more granular segmentation and diagnostic context than a public aggregate dataset: affected templates, devices, browsers, user journeys, interaction targets, release versions, and the timing of regressions.

CrUX and RUM values may differ even when both are measuring Core Web Vitals. Their populations, browser coverage, eligibility, aggregation, instrumentation, iframe handling, and measurement lifecycle may not match. For example, LCP and INP can be measured at different points in a visit, while CLS can differ when one system observes only initial load and another observes the page's longer lifetime. Compare like with like before treating a difference as an instrumentation defect. [6]

### 2.4 Interpreting data responsibly

When comparing measurements, record at least:

- Metric definition and measurement library/tool.
- Field, lab, or RUM source.
- URL-level or origin-level scope.
- Page type or template and representative URL sample.
- Device class, browser, and relevant network conditions.
- Percentile and aggregation window.
- Whether the measurement covers the full page lifecycle or only a defined interaction/load phase.
- Test date, browser/tool version, and release context.

Do not compare a single Lighthouse run with an aggregated field percentile as if they were equivalent. Use field data to establish whether and where users experience a problem; use lab tools and profiling to investigate reproducible causes; use RUM when additional segmentation and attribution are needed. [3][6][7]

## 3. Diagnose and optimize LCP

LCP optimization should start with the actual LCP element and a breakdown of the time leading to its rendering. For an image-based LCP candidate, the useful phases are:

1. **Time to First Byte (TTFB):** time from navigation until the first byte of the HTML response arrives.
2. **Resource load delay:** time between receiving the HTML response and the browser starting to fetch the LCP resource.
3. **Resource load duration:** time spent fetching the LCP resource.
4. **Element render delay:** time between the resource becoming available and the LCP element being rendered.

The phases together account for the LCP duration. Optimizing one phase may have little effect if another phase remains the bottleneck. [3]

Useful diagnostic and implementation directions include:

- **Reduce server and document latency:** investigate origin processing, redirects, cache misses, database work, CDN configuration, and avoidable server-side dependencies affecting TTFB.
- **Make the LCP resource discoverable early:** prefer an HTML-discoverable resource over one that is only discovered after client-side JavaScript executes. Review CSS background images and JavaScript-generated content where they delay discovery.
- **Set appropriate resource priority:** avoid lazy-loading the above-the-fold LCP image. Where supported and justified by measurement, use **fetchpriority="high"** for the LCP image or preload a critical resource that would otherwise be discovered late. Do not apply high priority indiscriminately to many resources.
- **Deliver an appropriately sized asset:** use responsive image selection such as srcset and sizes, efficient image formats, and dimensions suited to the rendered display. Avoid transferring a desktop-sized asset to a small viewport without a reason.
- **Reduce render delay:** remove unnecessary render-blocking CSS and synchronous scripts, provide critical styles efficiently, and avoid hiding the LCP element until a large JavaScript bundle or unrelated request completes.
- **Choose rendering architecture deliberately:** server rendering or static generation can make primary content discoverable in the initial HTML, but server work can also increase TTFB. Measure the full request and rendering path rather than assuming one architecture is always faster.

Do not treat image compression, preloading, a CDN, or a framework change as universal fixes. Confirm which LCP phase is dominant and validate that the change improves the end-to-end metric without creating regressions elsewhere. [3]

## 4. Diagnose and optimize INP

A slow interaction can be decomposed into three phases:

1. **Input delay:** time from the user's input until the relevant event callbacks begin.
2. **Processing duration:** time spent executing event callbacks for the interaction.
3. **Presentation delay:** time from completion of event callbacks until the next frame is presented.

This breakdown helps distinguish a busy main thread from expensive event-handler logic or costly rendering after the handler has completed. [4]

Common optimization directions include:

- **Reduce main-thread contention:** split long JavaScript tasks into smaller units, yield between non-urgent work, and defer work that is not required for the current interaction.
- **Control script cost:** remove unused code, limit unnecessary third-party scripts, avoid excessive parsing and execution during startup, and load non-critical functionality only when it is needed.
- **Keep event handlers focused:** avoid synchronous network requests, expensive computations, large DOM updates, and repeated layout reads/writes in interaction callbacks.
- **Move suitable computation off the main thread:** use Web Workers for work that can run independently of the DOM, while keeping communication and result application efficient.
- **Reduce rendering cost:** avoid unnecessarily large DOM trees and broad style/layout invalidations. Prefer targeted updates and efficient visual changes.
- **Provide timely feedback:** make the interface acknowledge an action promptly, then complete non-critical work asynchronously where the interaction design permits it.

A low Total Blocking Time (TBT) score in a lab report does not prove that field INP is good. TBT can help identify main-thread blocking during a lab load, but it does not reproduce the user's full interaction sequence or directly measure INP. Use field attribution where available, then reproduce the slow interaction in DevTools and inspect the relevant main-thread activity. [4][7]

## 5. Diagnose and optimize CLS

CLS remediation should identify which elements moved, when the movement occurred, and what caused the layout change.

Common controls include:

- **Reserve media dimensions:** specify image and video dimensions or an appropriate aspect-ratio so the browser can allocate space before media loads.
- **Reserve space for embeds and advertisements:** define realistic slot dimensions or minimum space based on the expected creative sizes. Avoid removing placeholders in ways that cause a second shift.
- **Avoid inserting content above existing content unexpectedly:** reserve space for banners, consent notices, recommendations, and dynamically loaded modules, or use an overlay when it is appropriate for the interaction.
- **Manage font loading:** choose fallback fonts with compatible metrics where possible and test font swaps for text reflow. Preloading a font can help when it is demonstrably critical, but indiscriminate preloading can compete with more important resources.
- **Inspect post-load behavior:** test scrolling, lazy-loaded media, infinite feeds, asynchronous components, and interactions that reveal additional content. Initial-load-only tests may miss shifts later in the visit.
- **Prefer animation techniques that do not trigger layout:** where appropriate, use transform- or opacity-based transitions rather than repeatedly changing layout-affecting properties.

Not every movement is a CLS failure. Expected movement following a user interaction is treated differently from unexpected movement, but that does not make disruptive interaction design desirable. Evaluate the user experience as well as the metric. [5]

## 6. Performance beyond Core Web Vitals

CWV deliberately covers three dimensions, not every property of a fast, efficient, resilient website. Depending on the application, additional measurements may include:

- **Time to First Byte (TTFB):** server/network response timing and an important diagnostic input to loading performance.
- **First Contentful Paint (FCP):** when the browser first renders content from the document.
- **Total Blocking Time (TBT):** a lab-oriented measure of main-thread blocking that can help diagnose responsiveness problems; it is not a Core Web Vital.
- **JavaScript and rendering cost:** script transfer, parsing, compilation, execution, layout, paint, memory use, and main-thread availability.
- **Resource efficiency:** transfer size, request count, cache effectiveness, image/font delivery, and third-party dependency cost.
- **Operational reliability:** server availability, error rates, latency variation, and behavior under constrained devices or networks.

These measurements provide diagnostic context, not interchangeable substitutes for CWV. Select metrics based on the user journey and system architecture. A content page, checkout flow, dashboard, and browser-based editor have different critical interactions and performance risks.

Performance work should also consider trade-offs. Aggressive caching can create freshness or personalization problems; script deferral can break dependencies; image compression can reduce visual quality; preloading too many assets can increase contention; and server-side rendering can move work from the browser to the server rather than eliminate it. Measure the complete user-visible outcome.

## 7. Performance and Google Search

Google documents Core Web Vitals as part of the signals its core ranking systems use to assess page experience. Google also states that there is no single page-experience signal and that good CWV results do not guarantee top rankings. Its systems continue to seek the most relevant content, including when a page's experience is sub-par. [8]

Therefore:

- Treat CWV as user-experience and performance evidence, not a ranking formula.
- Do not promise ranking gains from crossing a threshold or improving a laboratory score.
- Do not prioritize a perfect score over a more meaningful user or business problem.
- Evaluate performance alongside relevance, content usefulness, accessibility, security, and the broader experience.
- Attribute search-specific claims to Google's current documentation; do not generalize Google's stated use of CWV to every search engine.

Technical performance improvements can support user satisfaction, conversion, reliability, and operational efficiency even when a measurable search-ranking change does not follow.

## 8. Monitoring, prioritization, and validation workflow

A sustainable performance process connects field observation, diagnosis, implementation, and regression monitoring.

1. **Define the scope.** Identify the host, representative URLs, templates, user journeys, devices, browsers, environments, and business-critical interactions.
2. **Establish a baseline.** Collect field data where available and retain lab traces under documented, repeatable conditions. Record the date, release, tool version, and measurement configuration.
3. **Segment the problem.** Determine whether poor results affect a page, template group, device class, browser, geography, or specific interaction. Avoid relying only on a site-wide aggregate.
4. **Identify the metric and mechanism.** For LCP, inspect the candidate element and timing phases. For INP, identify the slow interaction and its input, processing, and presentation phases. For CLS, identify the shifted elements and when they moved.
5. **Reproduce and profile.** Use representative pages and flows. Inspect network waterfalls, server timing, JavaScript execution, main-thread activity, layout, and paint with suitable browser tools.
6. **Prioritize by impact and confidence.** Consider affected users, frequency, severity, template reach, business importance, root-cause confidence, and engineering cost. A tool's generic priority label is not a substitute for this assessment.
7. **Implement a targeted change.** Change the measured bottleneck and document expected side effects, dependencies, and rollback considerations.
8. **Re-test under comparable conditions.** Repeat the lab flow and compare field/RUM data over an appropriate observation period. A single run is not sufficient evidence of a durable field improvement.
9. **Monitor after release.** Watch for regressions after changes to templates, scripts, images, fonts, advertising, analytics, hosting, CDN rules, or third-party integrations.
10. **Record the result.** Document the affected URLs/templates, evidence source, before/after measurements, release, test conditions, limitations, and whether the improvement is implemented or independently verified.

For reproducible browser profiling, Chrome DevTools' Performance panel can record runtime activity and help identify performance bottlenecks. PageSpeed Insights and Search Console can provide field-oriented views where eligible data is available. Use each tool for the type of evidence it actually provides. [6][7]

## 9. Reporting and interpretation limits

A useful performance report should include:

- Target URLs, templates, and user journeys.
- Field/lab/RUM source and measurement methodology.
- Metric definitions, percentile, device/browser segments, and time window.
- Observed bottleneck and supporting trace or attribution.
- Baseline and post-change values under comparable conditions.
- Code/configuration change and release identifier.
- User impact, trade-offs, unresolved issues, and confidence.
- Follow-up monitoring or regression criteria.

Keep three conclusions separate:

- **Observed:** a specific metric or behavior was measured under stated conditions.
- **Diagnosed:** evidence supports a plausible technical cause.
- **Improved:** comparable post-change evidence demonstrates a better outcome over a suitable sample or period.

A repository change, a single lab score, or a favorable aggregate report does not prove that every user experience improved. Nor does a CWV result establish that a page is accessible, secure, indexable, or eligible for a particular search feature.

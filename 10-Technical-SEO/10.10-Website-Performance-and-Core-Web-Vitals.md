# 10.10 — Website Performance & Core Web Vitals

[← Domain 10 — Technical SEO](README.md)

Website performance concerns how quickly and reliably a page loads, responds to user input, and maintains visual stability. Core Web Vitals are a defined set of user-experience metrics. They are not a complete performance model, a guarantee of ranking improvement, or a substitute for diagnosing the actual user journey. [1][2]

## 1. Current Core Web Vitals

The current Core Web Vitals are:

- **Largest Contentful Paint (LCP):** measures loading performance by recording when the largest eligible content element becomes visible in the viewport.
- **Interaction to Next Paint (INP):** assesses responsiveness across user interactions by measuring interaction latency and the next visual update.
- **Cumulative Layout Shift (CLS):** measures unexpected visual movement over the page's lifetime.

The commonly documented “good” thresholds are LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or below 0.1, evaluated at the 75th percentile of page visits. These thresholds are subject to the current Web Vitals documentation and should be rechecked before publication or implementation decisions. [1][2]

## 2. Field data and lab data

**Field data** represents observed user experiences in real environments. It varies by device, network, geography, browser, page content, and user behavior. The Chrome User Experience Report (CrUX) is a public dataset of real-user experiences for eligible Chrome users and pages; it is not a census of every visitor or browser. [2][3]

**Lab data** is collected under controlled conditions. It is useful for reproducing issues, profiling code, and testing changes, but a lab run cannot reproduce the full distribution of real-world users and devices. A field metric may identify a problem without identifying the code-level cause; lab diagnostics can help investigate that cause. [2][3]

Do not compare metrics without aligning page/origin scope, device, time window, percentile, metric definition, and measurement method. CrUX and a site's own Real User Monitoring (RUM) data can differ because of population, collection, segmentation, and measurement-lifecycle differences. [3]

## 3. Diagnose the mechanism, not just the score

For LCP, investigate server response, resource discovery, image selection/priority, render-blocking resources, and the time required for the largest content element to render. For INP, investigate long tasks, event handlers, JavaScript execution, and main-thread contention. For CLS, investigate images or embeds without reserved dimensions, late-injected content, font swaps, and layout changes caused by asynchronous components. The metric definitions and debugging guidance should be taken from current Web Vitals documentation. [1][2]

A useful process is:

1. Identify the affected metric and page/template group.
2. Determine whether the evidence is field, lab, or RUM data.
3. Segment by device and relevant user context.
4. Reproduce the issue using representative pages and interactions.
5. Profile network, rendering, JavaScript, layout, and server behavior.
6. Change the measured bottleneck rather than applying a generic optimization checklist.
7. Re-measure using the same methodology and an appropriate post-change window.

## 4. Performance and search

Google describes page experience as one aspect of its broader systems and recommends good page experiences, but does not present Core Web Vitals as a deterministic ranking formula or guarantee that crossing a threshold will improve a page's position. Relevance and many other systems remain important. Attribute search-specific statements to Google's documentation and keep performance engineering goals—user experience, conversion, reliability, and cost—distinct from search outcomes. [4]

## 5. Reporting and maintenance

Record the metric, page/template scope, data source, device class, percentile, date range, release version, and test conditions. Track regressions after major releases and prioritize issues based on reach, severity, user impact, and engineering cost. A single aggregate score can hide poor performance in a specific template or device group.

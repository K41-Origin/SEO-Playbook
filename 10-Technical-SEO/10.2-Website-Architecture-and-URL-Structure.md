# 10.2 — Website Architecture & URL Structure

[← Domain 10 — Technical SEO](README.md)

Website architecture and URL structure define how a website's resources are organized, addressed, routed, and exposed through its technical platform. They establish the relationship between a resource's public address and the application or infrastructure responsible for delivering it.

A sound architecture makes resource behavior predictable for users, maintainers, and automated clients. It supports coherent navigation and discovery, but it does not guarantee crawling, indexing, ranking, or any particular search result. Google recommends logical organization and descriptive URLs while explicitly cautioning site owners not to reorganize an established site merely to chase an assumed search benefit. [1][2]

This topic focuses on the technical organization of hosts, routes, paths, parameters, and resource endpoints. It does not own conceptual knowledge architecture (Domain 09), internal-link strategy (Domain 11), detailed crawl management (10.3), canonicalization (10.6), or redirect and migration implementation (10.7).

## 1. Understand the layers of website architecture

The phrase *site architecture* is used for several related but distinct things. Keeping them separate prevents technical decisions from being confused with content or navigation strategy.

### 1.1 Conceptual information architecture

Conceptual information architecture describes how information is grouped and related according to its meaning, audience, and purpose. It determines which content types and concepts belong together. Domain 09 owns semantic models and conceptual information architecture; Domain 11 owns the strategy for connecting pages through internal hyperlinks.

### 1.2 Technical resource architecture

Technical resource architecture describes how the application implements and delivers resources. It includes:

- Domains, subdomains, hosts, and origins.
- Application routes and URL path patterns.
- Page templates, content types, and resource identifiers.
- Query parameters and state representation.
- Routing, rewriting, and request dispatch.
- Backend services, content stores, APIs, and delivery layers.

A site's visible folder-like URL paths do not necessarily reveal its physical server directories, database schema, source-code structure, or actual navigation hierarchy. A route such as `/guides/url-design` may be generated by a CMS, a framework router, a serverless function, or a database lookup. The public URL is an address and routing contract, not a map of the implementation's internal filesystem.

### 1.3 Navigation and crawl paths

Navigation architecture concerns the links and controls through which people move between resources. Search crawlers may also discover URLs through links and other mechanisms. A well-designed URL hierarchy cannot compensate for pages that have no useful discovery path, while a flat URL pattern does not automatically mean that navigation is flat. Google describes logical organization and links as useful for helping users and search engines understand and discover content. [1]

These layers should support one another, but they should not be treated as interchangeable. A directory name in a URL does not create a semantic relationship by itself, and a route hierarchy does not replace deliberate internal linking.

## 2. URL anatomy and resource identity

Consider this illustrative URL:

`https://www.example.com:443/catalog/shoes/running?color=black&sort=price#specifications`

Its main components are:

| Component | Example | Technical role |
|---|---|---|
| Scheme | `https` | Identifies the protocol scheme used to access the resource. |
| Host | `www.example.com` | Identifies the named host within the URL authority. |
| Port | `443` | Identifies the service port; a default port may be omitted in the serialized URL. |
| Path | `/catalog/shoes/running` | Identifies a path within the origin's namespace and is commonly used by application routing. |
| Query | `color=black&sort=price` | Carries parameters interpreted by the application or server. |
| Fragment | `specifications` | Identifies a secondary location or state within the retrieved representation; it is not part of the ordinary HTTP request target sent to the server. |

The WHATWG URL Standard defines URL parsing, serialization, hosts, paths, queries, fragments, and related web-platform behavior. HTTP semantics define how request targets and resource interactions are represented at the protocol layer. Application frameworks may add their own routing and normalization rules, so the effective behavior must be tested in the deployed stack. [3][4]

### 2.1 Origin and host boundaries

For HTTP(S), an origin is determined by the scheme, host, and port after the applicable normalization rules. Two URLs with different schemes, hosts, or ports can identify distinct origins even when the same organization controls them. [4]

This matters operationally. A site may expose:

- `https://example.com` and `https://www.example.com`;
- separate subdomains such as `docs.example.com` and `shop.example.com`;
- locale-specific hosts;
- application or API hosts;
- legacy domains that remain accessible after a migration.

Each public host or origin may require its own DNS, TLS, routing, access, monitoring, and deployment configuration. Do not assume that two hosts behave identically because they resolve to the same infrastructure or share a brand.

### 2.2 Path, query, and fragment are not interchangeable

The path commonly selects a resource or application route. Query parameters commonly express a request variation or application state. A fragment is handled by the client after the resource is retrieved; Google Search generally does not use fragments to identify distinct page content for crawling and indexing. For JavaScript-driven navigation that changes the page resource, Google recommends using normal URLs and the History API rather than relying on fragments to represent separate content. [2]

Use each component for the role it is designed to represent. Putting essential resource identity only in client-side fragment state can make that content difficult for systems that do not interpret the fragment as a separate URL.

## 3. Choose a host and directory model deliberately

There is no universally correct host topology. Common patterns include:

| Pattern | Example | Typical reasons to consider it |
|---|---|---|
| One host with path-based sections | `example.com/shop/`, `example.com/docs/` | Shared platform, operations, branding, and deployment. |
| Subdomains | `shop.example.com`, `docs.example.com` | Separate applications, teams, infrastructure, release cycles, or product boundaries. |
| Country-code top-level domains | `example.de`, `example.fr` | Distinct country-market identity or business/legal requirements. |
| Locale subdirectories | `example.com/de/`, `example.com/fr/` | Shared host with locale-specific resource paths. |
| Separate domains | `brand-example.com` | Distinct brands, acquisitions, products, or ownership arrangements. |

Choose based on product boundaries, technical ownership, deployment needs, security, infrastructure, market requirements, and maintenance capacity. Google explicitly says that the choice between subdomains and subdirectories should be made according to what makes sense for the business; neither should be presented as a universal SEO advantage. [1]

For international sites, host or path structure is one implementation decision among several. Language and regional targeting, translated content, locale switching, and `hreflang` relationships belong to the strategy and implementation scope of Domain 13. A URL path containing a locale code does not, by itself, establish that a page is correctly localized or that search engines will serve it to the intended audience.

## 4. Design stable, understandable URL paths

A URL should identify a resource consistently over time. Prefer paths that are readable, descriptive, and understandable to the people who use the site. Google recommends descriptive words, audience-appropriate language, hyphens as word separators, and removal of parameters that do not change the content. It also documents that URL paths are case-sensitive in Google Search. [2]

### 4.1 Use meaningful path segments

A path such as:

`/support/billing/refunds`

communicates more context than an opaque route such as:

`/page?id=48392`

Descriptive paths can help users understand the destination and may contribute to breadcrumb interpretation. However, keywords in a domain name or URL path alone have little ranking effect beyond their appearance in breadcrumbs, according to Google's SEO Starter Guide. Do not treat keyword insertion into slugs as a substitute for useful content, sound architecture, or relevant links. [1]

### 4.2 Keep naming rules consistent

Establish a documented convention for:

- Lowercase or case-preserving path segments.
- Hyphenation and word boundaries.
- Trailing-slash behavior.
- File extensions, if the platform uses them.
- Reserved characters and percent encoding.
- Parameter names and serialization.
- Locale and version prefixes.
- Stable identifiers and human-readable slugs.

Consistency matters more than selecting a fashionable pattern. For example, if an application treats `/Products` and `/products` as the same route, it should avoid exposing both as independent public addresses. Google treats case variants as distinct URLs, so normalize them when the application considers them equivalent. [2]

Use percent encoding where required by URL syntax and the relevant client behavior. Do not manually concatenate untrusted values into paths or query strings. Use the platform's URL APIs and test parsing and serialization, particularly for spaces, non-ASCII text, reserved characters, and values containing delimiters. The WHATWG URL Standard defines the interoperable web-platform parsing and serialization model. [3]

### 4.3 Do not optimize for imaginary URL formulas

There is no defensible universal rule that every page must sit within a fixed number of directory levels, that shorter URLs always rank better, or that every URL must contain a target keyword. A path should be as simple as the resource model and operational needs allow, without sacrificing clarity or creating brittle routing.

Google's guidance recommends logical organization and grouping similar pages in directories, especially noting potential crawl and indexing effects for very large sites. It does not prescribe one mandatory folder depth or claim that a particular directory pattern guarantees better rankings. [1]

## 5. Model query parameters intentionally

Query parameters can change the resource representation, control a view, record attribution, or support application operations. Problems arise when a site exposes parameters without a clear policy or allows arbitrary combinations to generate unlimited URLs.

Classify parameters according to their actual effect:

| Parameter class | Example | Design consideration |
|---|---|---|
| Content-defining | `?product=blue-model` | Changes the substantive resource or variant; determine whether it deserves a distinct stable URL. |
| Filtering and sorting | `?color=black&sort=price-asc` | May create many combinations; decide which combinations have user value and which, if any, should be search-accessible. |
| Pagination or view state | `?page=3` | Should represent a predictable page or state, not an accidental duplicate of another view. |
| Tracking and referral | `?utm_source=newsletter` | Usually does not change the underlying content; avoid propagating tracking variants through internal navigation. |
| Session or transient state | `?sessionid=...` | Usually should not create a public address for the same resource; use appropriate session mechanisms instead. |
| Operational or action state | `?add_to_cart=1` | Should not accidentally create crawlable URLs for actions or user-specific state. |

Do not remove parameters indiscriminately. A parameter may distinguish a real product variant, language, page of results, or other meaningful representation. First establish whether it changes the resource, the user's view, or only the tracking/operational context.

For parameters that do not change the underlying content, avoid generating or linking to unnecessary variants. Use a consistent parameter format and avoid multiple syntactic representations for the same state. Google recommends common query encoding, fewer unnecessary parameters, and avoiding session identifiers in URLs where possible. [2]

## 6. Control faceted and combinatorial URL spaces

Faceted navigation allows users to filter a collection by attributes such as category, color, size, price, location, or availability. It is useful for users, but combining many filters can generate a combinatorial URL space.

If a collection has several independent filters, each with multiple possible values, the number of possible combinations can grow rapidly. Many combinations may produce nearly identical lists, empty results, or pages with little independent value. Google's crawling guidance identifies overcrawling and slower discovery of useful URLs as possible consequences of uncontrolled faceted URL generation. [5]

A deliberate policy should answer:

1. Which filtered views provide distinct and useful user experiences?
2. Which views represent stable resources that should be directly addressable?
3. Which combinations, if any, have sufficient value to be intentionally exposed to search?
4. Which parameters are merely transient controls or tracking metadata?
5. How will the application prevent invalid, redundant, or unbounded combinations?
6. How will crawler access and indexing directives be applied consistently with the intended policy?

Possible implementation approaches include limiting which combinations the application generates as links, creating stable routes for selected high-value views, and preventing crawling of parameter spaces that are not intended for search exposure. Google documents specific approaches for managing faceted navigation, but the correct policy depends on the site's inventory and business requirements. [5]

Do not confuse URL architecture with crawler access or indexing controls. robots.txt, `noindex`, canonical annotations, and redirects have different behaviors and belong to their dedicated topics. A robots.txt disallow rule is not a substitute for a coherent parameter model, and it does not itself remove a URL from an index. See 10.4 and 10.6 for the relevant mechanisms.

## 7. Make routing deterministic and resource-aware

A public URL should resolve predictably to the intended resource. Routing rules should be explicit enough that the application does not accidentally serve different content at equivalent addresses or return successful responses for nonexistent resources.

Important design considerations include:

- **Route precedence:** define how static paths, dynamic slugs, IDs, and catch-all routes are matched.
- **Identifier stability:** avoid changing public addresses whenever an internal database key, title, or organizational label changes.
- **Slug collisions:** handle duplicate titles, renamed resources, and deleted content without silently routing to the wrong page.
- **Direct-request support:** ensure that a URL works when opened directly, refreshed, or requested without first navigating through the application.
- **Consistent response behavior:** ensure the application returns the appropriate response for existing, moved, unavailable, and nonexistent resources. Detailed HTTP status and redirect behavior is covered in 10.7.
- **Environment separation:** prevent staging, preview, development, and private application hosts from becoming unintended public resource surfaces.
- **Cache compatibility:** ensure that the cache key and cache policy account for parameters or headers that genuinely change the representation.

A URL design is incomplete if it works only through client-side navigation but fails on a direct request, or if the application and caching layer disagree about which parameters define the response. These are implementation concerns to test in the actual stack, not properties that can be inferred from the visible URL alone.

## 8. Plan URL changes as controlled migrations

Changing a public URL can affect bookmarks, external links, internal navigation, cached references, analytics, and search-engine processing. Treat URL changes as resource migrations, not cosmetic renaming.

Before changing paths or hosts:

1. Inventory current URLs using the CMS, router, sitemaps, server logs, analytics, and relevant search reports.
2. Map each old URL to its intended new destination.
3. Identify URLs that should remain unchanged, move, consolidate, or return a genuine not-found response.
4. Prepare the new routes and test them before switching traffic.
5. Update internal links, canonical annotations, locale annotations, and sitemap entries where applicable.
6. Implement redirects appropriate to the actual move and verify that they resolve to relevant final destinations.
7. Monitor old and new URLs, server errors, crawl activity, and user traffic after the change.

Google's site-move documentation recommends preparing and testing the new site, creating an old-to-new URL mapping, using server-side permanent redirects where appropriate, updating internal links and URL annotations, testing redirects, and monitoring the move. It also warns against redirecting unrelated old URLs to a single irrelevant destination. [6]

Detailed redirect semantics, HTTP status selection, redirect chains, and migration troubleshooting are covered in 10.7. This section establishes the architectural planning responsibility and links to that canonical implementation topic.

## 9. A practical architecture and URL review

A review should evaluate both the intended model and the behavior of the deployed application. A useful sequence is:

### 9.1 Inventory the public resource space

Collect representative and important URLs from the CMS, route definitions, sitemap, internal links, logs, and search reporting. Group them by host, template, path pattern, content type, locale, and parameter behavior.

### 9.2 Document the route model

For each important resource type, record its canonical route pattern, identifier source, required parameters, optional parameters, expected response, and ownership. Identify legacy routes and routes generated by multiple systems.

### 9.3 Test URL equivalence and variation

Test case variants, trailing-slash variants, encoded characters, query-parameter order, tracking parameters, locale variants, and legacy hostnames. Confirm whether the application treats each variation as the same resource or as a genuinely distinct representation.

### 9.4 Inspect parameter generation

Review filters, sort controls, calendars, search pages, session state, and tracking integrations. Check whether they create an unbounded number of URLs, whether internal links propagate unnecessary parameters, and whether important resource variants remain accessible.

### 9.5 Validate routing and delivery

Request representative URLs directly, not only through browser navigation. Verify route resolution, returned content, response behavior, cache variation, and consistency across production-like environments. Use the detailed status-code and redirect checks in 10.7 where relevant.

### 9.6 Cross-check search-facing URL signals

Compare internal links, sitemap entries, canonical declarations, and intended indexable URL patterns. Canonical selection and indexability are separate mechanisms covered in 10.6; crawl access and URL discovery are covered in 10.3–10.5.

### 9.7 Record evidence and regression tests

Document the tested URL patterns, sample size, environment, timestamp, expected behavior, observed behavior, and exceptions. Turn important route and normalization expectations into automated tests where practical. Re-run them after CMS changes, framework upgrades, routing refactors, domain changes, and migrations.

A review of a representative sample does not prove that every possible URL or parameter combination is correct. State the sample and limits of the test.

## 10. Common misconceptions

- **"A deeper URL path is automatically worse for SEO."** Path depth alone does not establish discoverability or quality. Actual navigation, route behavior, resource organization, and crawl paths matter.
- **"Short URLs always rank better."** Google recommends simple and descriptive URLs, not a universal length formula. [2]
- **"Keywords in the URL are a powerful ranking lever."** Google says keywords in the domain name or URL path alone have little ranking effect beyond their appearance in breadcrumbs. [1]
- **"Subdirectories always outperform subdomains."** Google's guidance is to choose the structure that makes sense for the business and its operational requirements. [1]
- **"A folder in the URL must match a physical folder on the server."** Public routes may be generated by application code, a CMS, or other routing infrastructure.
- **"Every filter combination should be indexable."** Many combinations add little independent value and can create large URL spaces. Make an explicit policy based on user value and search intent. [5]
- **"Canonical tags fix poor URL architecture."** Canonicalization is a separate consolidation mechanism; it does not replace stable routes and coherent resource addressing.
- **"Changing a slug is harmless if the page content stays the same."** A URL is a public address that may be referenced elsewhere. Changes require migration planning and appropriate routing or redirects. [6]
- **"A successful client-side route proves direct URL access works."** Test direct requests and refresh behavior independently; the application router and server fallback must agree.

# 10.2 — Website Architecture & URL Structure

[← Domain 10 — Technical SEO](README.md)

Website architecture and URL structure define how a site organizes, addresses, routes, and serves its resources. This topic covers the technical organization of hosts, paths, routes, parameters, and resource endpoints. It does not own the conceptual organization of knowledge (Domain 09) or the strategy for linking pages together (Domain 11).

## 1. URL anatomy and normalization

A URL can contain a scheme, authority (including host and optional port), path, query, and fragment. The WHATWG URL Standard defines parsing and serialization behavior for web-platform URLs; application frameworks and server infrastructure must still be tested for their actual routing and cache behavior. [1]

For example:

`https://www.example.com/products/shoes?color=black&page=2#details`

The scheme and host identify the origin; the path selects a route or resource; the query carries parameters; and the fragment identifies a location within the retrieved representation. A fragment is generally processed client-side and is not sent as part of the HTTP request target in the ordinary HTTP request model. [1][2]

Choose and consistently implement policies for HTTPS, preferred hostname, default ports, trailing slashes, path case, percent-encoding, query parameter order, and redirects. Do not assume two visually similar URLs are equivalent: the server, application, cache, or framework may treat them differently. Test the actual response and application routing rather than relying on string comparisons alone. [1]

## 2. Information architecture versus technical architecture

A conceptual information architecture groups content according to meaning, audience needs, and relationships. A technical site architecture implements routes, templates, directories, hosts, and delivery services. These layers should support each other but are not interchangeable.

A deep-looking URL path does not by itself prove that a page is difficult to discover; nor does a short URL guarantee that the site has coherent navigation. Search engines discover URLs through multiple mechanisms, including links and sitemaps. Google's guidance recommends logical URL structures, but does not define one universally optimal folder depth or URL length. [3]

## 3. Parameterized and faceted URL spaces

Query parameters can represent materially different resources (for example, a product variant) or transient state (sorting, tracking, session identifiers, filters). Classify parameters by their effect:

- **Content-defining:** changes the resource or user-visible primary content.
- **State/navigation:** changes a view, filter, sort, pagination, or interaction state.
- **Tracking:** records campaign or attribution metadata without changing the underlying content.
- **Operational:** supports application behavior, authentication, or session handling.

Unbounded combinations can create very large URL spaces. Decide which combinations should be accessible, linked, crawlable, indexable, canonicalized, or excluded. These are separate decisions: blocking crawling, applying noindex, redirecting, and canonicalizing have different effects and must not be used as interchangeable controls. Google provides specific guidance for managing faceted navigation and crawling; apply it to the actual URL patterns and search-engine behavior in scope. [4]

## 4. Host, routing, and canonical consistency

Inventory all public hosts and URL patterns, including staging domains, legacy hosts, alternate protocols, subdomains, pagination, print routes, and application endpoints. Define how each should respond. Use permanent redirects when a URL has permanently moved, and avoid maintaining competing versions without a documented reason. [2][5]

For every indexable template, compare:

- Internal links and navigation destinations.
- HTTP response URL and redirect destination.
- Canonical declaration and its target.
- Sitemap URL and host.
- Robots directives and access rules.
- Rendered links generated by client-side routing.

A canonical tag does not repair inconsistent architecture by itself. Google treats canonical annotations as signals and may select a different canonical URL based on its own processing. [6]

## 5. Implementation and validation workflow

1. Export or generate a URL inventory from the CMS, router, database, sitemap, and crawl data.
2. Group URLs by template, host, path pattern, and parameter behavior.
3. Identify duplicate or unbounded patterns and classify their intended purpose.
4. Define the canonical host/scheme and route behavior.
5. Test direct requests—not only in-app navigation—for status, redirects, content, and metadata.
6. Test representative parameter combinations, encoded characters, case variants, and trailing-slash variants.
7. Compare internal links, canonical declarations, and sitemap entries.
8. Repeat after routing, CMS, CDN, or migration changes.

Use representative samples for large URL spaces and document the sampling method. A finite test set cannot prove that every possible parameter combination is correct.

## 6. Common failure patterns

- Inconsistent HTTP/HTTPS or www/non-www handling.
- Multiple routes serving substantially identical content without a consolidation policy.
- Tracking or session parameters propagated into internal links and sitemaps.
- Faceted navigation creating unbounded crawlable combinations.
- Client-side routes that fail on direct request or return incorrect status codes.
- Canonical targets that redirect, return errors, or describe different content.
- URL rewriting that changes application behavior or breaks cached resources.

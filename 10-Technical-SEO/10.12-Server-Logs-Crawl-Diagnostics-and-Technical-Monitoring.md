# 10.12 — Server Logs, Crawl Diagnostics & Technical Monitoring

[← Domain 10 — Technical SEO](README.md)

Server logs record requests observed by a web server, proxy, CDN, application, or another infrastructure component. Properly interpreted, they can help explain how clients interact with a site. Logs do not automatically reveal what a search engine indexed, how it interpreted content, or why it selected a URL.

## 1. What access logs can show

Depending on the logging layer and configured fields, an access log may contain timestamp, request method, host, path, query string, response status, response size, user-agent, referrer, latency, and client address. The available fields and their meaning depend on the server, proxy, CDN, and logging configuration.

A request may be recorded at the CDN but not at the origin, or at the origin after a cache miss. A cache hit may never reach the application server. Therefore, a single log source may not represent every request path. Document the layer, sampling, retention, timezone, and fields before drawing conclusions.

## 2. Verify crawler identity

User-agent strings can be spoofed. A request claiming to be Googlebot is not sufficient proof that it originated from Google. Google publishes verification procedures, including reverse DNS followed by forward DNS confirmation, and maintains documentation for its crawlers and fetchers. Apply the relevant provider's published verification method before labeling traffic as a verified crawler. [1]

Do not classify every bot as a search crawler. Separate verified search-engine crawlers, other known automated clients, unknown bots, monitoring services, and human traffic where the data permits.

## 3. Diagnostic questions

Log analysis can help investigate:

- Which URL patterns receive requests and how often.
- Whether important URLs return 2xx responses or unexpected 3xx/4xx/5xx responses.
- Whether redirect chains or loops occur.
- Whether query parameters create repeated URL variants.
- Whether crawl activity changes after a release or migration.
- Whether latency, rate limiting, or server errors correlate with reduced request activity.
- Whether bots repeatedly request stale, removed, or low-value URLs.

Google's crawl-budget documentation describes the relationship between host capacity and crawler demand for Google Search. Treat this as a Google-specific model and combine logs with provider reports rather than assuming log frequency equals crawl budget or indexing. [2]

## 4. A repeatable log-analysis workflow

1. Identify the logging layer and the completeness of the captured request stream.
2. Normalize timestamps, hosts, paths, query strings, response codes, and user-agent categories.
3. Remove or redact secrets and unnecessary personal data.
4. Verify crawler identity where provider-specific conclusions are needed.
5. Group requests by URL pattern, template, status, and time window.
6. Compare observed requests with the intended URL inventory, sitemap, release history, and known incidents.
7. Investigate anomalies at the relevant infrastructure layer.
8. Test the suspected cause using direct requests and representative URLs.
9. Record the evidence, uncertainty, and remediation outcome.

A log sample is evidence about the captured requests, not necessarily a complete census. Sampling, retention gaps, cache behavior, privacy filtering, and distributed infrastructure can affect conclusions.

## 5. Technical monitoring

Useful monitoring signals may include origin availability, DNS/TLS failures, response latency, 4xx/5xx/429 distributions, redirect rates, cache behavior, resource delivery, crawl request patterns, sitemap processing, rendering errors, and performance metrics. Select signals according to site architecture and operational risk; avoid building dashboards that collect data without supporting decisions.

Set alerts around actionable thresholds and establish ownership and response procedures. A monitoring event is not automatically an SEO defect: correlate it with affected URLs, user impact, deployment events, and search-engine observations.

Domain 14 owns organic search performance measurement, analysis, and attribution. This topic owns technical request diagnostics and infrastructure monitoring.

## 6. Privacy and security

Logs may contain IP addresses, identifiers, query strings, authentication tokens, or other sensitive information. Minimize collection, restrict access, define retention, redact secrets, and follow applicable privacy/security requirements. Never publish raw production logs as documentation examples.

# 10.6 — Indexability, Canonicalization & Duplicate URL Management

[← Domain 10 — Technical SEO](README.md)

Indexability is the set of technical and content conditions under which a search engine can consider a resource for inclusion in its index. Site owners can expose content and provide directives or canonical hints, but the search engine makes its own indexing and canonical-selection decisions. [1][2]

## 1. Crawlability is not indexability

A URL may be crawlable but carry a `noindex` directive. Conversely, a URL blocked by robots.txt may still be known from links or other sources and can potentially appear in search results without a fetched page description. Robots.txt controls crawling; robots meta and `X-Robots-Tag` communicate indexing/serving directives in a fetched response. [1][3]

The practical diagnostic sequence is therefore:

1. Can the intended crawler request the URL?
2. What HTTP response and content does it receive?
3. Are robots directives present in the HTML or response headers?
4. Does the page declare a canonical URL?
5. Does the search engine report the URL as indexed, excluded, or represented by another URL?

Do not infer the answer to a later question from an earlier check.

## 2. Robots directives

The HTML robots meta element applies to a document, while the `X-Robots-Tag` HTTP header can apply to non-HTML resources such as PDFs and image files. Directive names and supported values are crawler-specific; consult the relevant provider documentation before relying on a directive. [3]

A `noindex` directive must be available to the crawler for it to be processed. Blocking the URL in robots.txt can prevent the crawler from fetching the page and seeing the directive. A directive is not a security mechanism: confidential content requires authentication and access control. [1][3]

## 3. Canonicalization and duplicate clusters

Canonicalization is the process by which a search engine selects a representative URL from duplicate or substantially similar resources. Duplicate variants may arise from HTTP/HTTPS, hostname differences, tracking parameters, session identifiers, sorting/filtering, print views, pagination, CMS routes, or alternate URL forms.

Google describes canonicalization as a signal-based process. Signals can include redirects, `rel="canonical"` annotations, sitemap inclusion, and internal linking patterns. These signals are not commands; Google can select a different canonical URL. [2][4]

A canonical annotation should point to a preferred, accessible URL that represents the content. Avoid canonical targets that redirect, return errors, are blocked from crawling, or contain materially different content. Keep canonical declarations consistent with internal links, redirects, and sitemap entries.

## 4. Choose the correct control

| Situation | Typical control | Important limitation |
|---|---|---|
| A URL has permanently moved | Permanent redirect | Update internal links and relevant sitemap entries. |
| Duplicate or similar accessible URLs should consolidate | Canonical annotation and consistent signals | Search engine may choose another canonical. |
| A page should be crawled but excluded from indexing | noindex directive | Crawler must fetch the directive. |
| A crawler should not request a path/resource | robots.txt | Does not guarantee exclusion from indexing. |
| A resource is private | Authentication/authorization | Do not rely on crawler conventions. |
| A resource is permanently gone | Accurate 404 or 410 response | Do not redirect unrelated removals to a generic page. |

The table describes common use cases, not universal provider behavior. Consult each search engine's current documentation before applying a control. [1][2][3][5]

## 5. Duplicate URL management workflow

1. Build an inventory of URL variants from the application, CMS, internal links, sitemap, logs, and crawler data.
2. Group URLs by content identity and identify which variants materially change the resource.
3. Define the preferred URL for each duplicate cluster.
4. Select redirects, canonical annotations, noindex, robots rules, or access controls according to the actual goal.
5. Align internal links, canonical declarations, sitemap entries, and response behavior.
6. Inspect source HTML and response headers, then compare with search-engine URL inspection or indexing reports.
7. Recheck after template, routing, or migration changes.

Do not use a canonical tag as a substitute for URL architecture. Do not apply noindex to a URL that is blocked from crawling if the goal is for the crawler to see that directive.

## 6. Common failure patterns

- Canonical points to a different page or an inaccessible destination.
- Sitemap lists a URL that redirects or is marked noindex.
- Internal links consistently reinforce a different URL than the declared canonical.
- Robots.txt blocks a page whose noindex directive must be processed.
- Parameter variants multiply without a content-based policy.
- Multiple controls contradict each other and make the preferred URL unclear.

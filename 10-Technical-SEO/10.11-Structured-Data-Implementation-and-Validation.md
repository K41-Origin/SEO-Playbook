# 10.11 — Structured Data Implementation & Validation

[← Domain 10 — Technical SEO](README.md)

Structured data is a machine-readable representation of information associated with a page or resource. On websites, it can express entities, properties, and relationships using a defined vocabulary and serialization format. Domain 09 owns conceptual meaning and entity modeling; Domain 10 owns technical implementation and validation; Domain 06 owns search-result presentation and feature behavior.

## 1. Vocabulary and serialization are different layers

Schema.org provides a shared vocabulary of types and properties. JSON-LD, Microdata, and RDFa are different ways to encode structured information in a document. A vocabulary defines what terms mean; a syntax defines how data is represented. The choice of syntax does not by itself make the underlying description accurate or useful. [1][2]

Google supports JSON-LD, Microdata, and RDFa for Search structured data and generally recommends JSON-LD where practical. This is Google's documented support, not a requirement imposed by the Schema.org vocabulary for every consumer. Other parsers and applications may support different subsets. [2]

Example JSON-LD (illustrative; values must describe the actual page):

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "name": "Example Organization",
  "url": "https://example.com/"
}
</script>
```

Do not copy example values into a production page unless they accurately describe the organization and visible page content.

## 2. Select types and properties responsibly

Choose a type that accurately represents the primary entity or content on the page. Add properties only when the values are known, relevant, and consistent with the visible content. Avoid inventing ratings, reviews, prices, authorship, dates, locations, or other attributes to satisfy a schema example.

Schema.org defines a broad vocabulary; Google Search supports only selected structured-data features and imposes feature-specific requirements. A type existing in Schema.org does not mean it qualifies for a Google rich result. Consult the current feature documentation and policies for the exact type and property set. [1][3]

Use stable identifiers such as `@id` where they help distinguish and connect entities across a site's data. Identifier design should align with the site's canonical semantic model; do not generate contradictory IDs for the same real-world entity on different templates. This is an implementation recommendation grounded in consistent data modeling, not a guarantee of search feature eligibility.

## 3. Validation has multiple layers

A structured-data check should distinguish:

1. **Parsing and syntax:** the JSON-LD or markup can be parsed.
2. **Vocabulary validity:** types and properties exist and are used in a compatible way.
3. **Required/recommended properties:** feature-specific requirements and recommendations are met.
4. **Content consistency:** markup accurately reflects visible page content and is not misleading.
5. **Crawl and rendering access:** the crawler can fetch the page and relevant markup/resources.
6. **Policy compliance:** the implementation follows current search-feature policies.
7. **Search appearance:** the search engine independently decides whether to display a supported enhancement.

Passing a parser or rich-results test does not guarantee that a feature will appear. Google states that valid structured data makes a page eligible for certain rich results but does not guarantee display. [2][3]

## 4. Deployment patterns and operational risks

Structured data may be authored in templates, generated from CMS fields, emitted by server-side application code, or inserted by client-side JavaScript. Choose a source of truth and avoid duplicate, conflicting, stale, or placeholder markup. If markup is generated dynamically, inspect the rendered representation available to the relevant crawler and test after changes to the rendering pipeline. [2][4]

Common implementation defects include:

- Markup describes content not visible to users.
- Values differ from the page's current content.
- Multiple scripts describe the same entity inconsistently.
- Required properties are missing or malformed.
- Structured data is emitted on the wrong canonical URL.
- Entity identifiers are unstable or contradictory.
- A template change silently removes markup from a subset of pages.

## 5. Implementation workflow

1. Identify the page type and the semantic entity/content model.
2. Select the relevant vocabulary terms and supported search feature, if any.
3. Map source-of-truth fields to structured-data properties.
4. Serialize the data in the chosen format.
5. Validate parsing, vocabulary, property requirements, visible-content consistency, and policy.
6. Test representative templates and edge cases.
7. Deploy and inspect the live page.
8. Monitor relevant search-engine reports and re-test after CMS, schema, content, or template changes.

# 10.11 — Structured Data Implementation & Validation

[← Domain 10 — Technical SEO](README.md)

Structured data is a machine-readable representation of information associated with a page or resource. It expresses entities, properties, and relationships through a vocabulary and a serialization syntax. On a website, structured data can help search engines and other consuming systems interpret what a page describes. It does not replace visible content, establish that a page is indexable, or compel a search engine to display a particular search feature.

The ownership boundary is deliberate: Domain 09 owns conceptual meaning, entity modeling, and semantic relationships; Domain 10 owns the technical implementation, delivery, and validation of structured data; Domain 06 owns visible search-result features, eligibility explanations, and presentation behavior. [1][2]

## 1. Vocabulary, syntax, and search features are separate layers

Three concepts are often conflated:

- **Vocabulary:** defines the types, properties, and relationships used to describe things. Schema.org is a widely used shared vocabulary with a type hierarchy and property definitions. [1]
- **Serialization syntax:** defines how the description is encoded in a document. Common formats include JSON-LD, Microdata, and RDFa. These formats can express Schema.org vocabulary; they are not themselves vocabularies. [2]
- **Search feature:** a search engine's product-specific use of selected structured-data types and properties to support an enhanced result or another search experience. A vocabulary term existing in Schema.org does not mean Google supports it for a rich result. [3]

Google documents support for JSON-LD, Microdata, and RDFa for its structured-data features, and generally recommends JSON-LD when a site's implementation allows it. That is Google-specific implementation guidance, not a universal requirement for every structured-data consumer. Choose a format that can be generated accurately, maintained consistently, and validated within the site's architecture. [2]

### 1.1 JSON-LD

JSON-LD is a JSON-based format commonly embedded in an HTML document in a script element with type application/ld+json. Because the data is separate from the visible HTML elements, it can be convenient to generate from CMS or application data and to represent nested entities.

The key JSON-LD terms used in common implementations include:

- @context: identifies the context used to interpret terms, commonly https://schema.org.
- @type: identifies the type or types of the described item.
- @id: provides an identifier for a node, often a stable URI that can be referenced elsewhere in the graph.
- @graph: groups multiple related nodes in one JSON-LD document.
- Ordinary properties: provide values or references for the selected type, such as name, url, publisher, or about.

The following illustrative example describes an organization's public homepage. All names and URLs are placeholders and must be replaced with accurate information before use.

~~~html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "Organization",
      "@id": "https://example.com/#organization",
      "name": "Example Organization",
      "url": "https://example.com/",
      "sameAs": [
        "https://www.linkedin.com/company/example/"
      ]
    },
    {
      "@type": "WebSite",
      "@id": "https://example.com/#website",
      "url": "https://example.com/",
      "name": "Example Organization",
      "publisher": {
        "@id": "https://example.com/#organization"
      }
    },
    {
      "@type": "WebPage",
      "@id": "https://example.com/#webpage",
      "url": "https://example.com/",
      "name": "Example Organization",
      "isPartOf": {
        "@id": "https://example.com/#website"
      },
      "about": {
        "@id": "https://example.com/#organization"
      }
    }
  ]
}
</script>
~~~

This graph uses stable identifiers to connect the homepage, website, and organization nodes. It illustrates entity relationships; it does not imply that Google will show a rich result for every type in the graph. The page must genuinely describe the organization and website, and the values must agree with the information available to users. [2][4]

### 1.2 Microdata and RDFa

Microdata and RDFa attach machine-readable attributes to HTML elements. They can be useful when the markup should be closely associated with visible content or when an existing CMS/theme already uses one of these formats.

Avoid adding a second syntax simply to repeat the same data. Multiple formats can coexist, but only when there is a clear reason and their values remain consistent. Duplicated or conflicting markup makes debugging harder and can cause consumers to interpret different versions of the same entity. [1][2]

## 2. Select types and properties responsibly

Choose a type that accurately describes the primary entity or content on the page. Prefer the most specific applicable Schema.org type when it represents the real subject, but do not force a type merely because it appears in an SEO checklist or plugin interface.

A practical selection process:

1. Identify what the page is primarily about and what a visitor can actually see.
2. Identify the real-world entity or content item being described.
3. Check the relevant Schema.org type and property definitions, including expected value types and relationships.
4. Check whether Google currently documents a search feature for that type, if a Google rich result is an objective.
5. Review the exact feature-specific required properties, recommended properties, technical rules, and content policies.
6. Omit unsupported, unknown, irrelevant, or unverifiable values.

Schema.org defines a broad vocabulary. Google Search uses only a subset for documented search features, and the supported set can change. Some structured data may help Google understand page information without corresponding to a dedicated rich-result feature. Do not equate vocabulary validity, consumer support, rich-result eligibility, and actual display. [1][3]

### 2.1 Required and recommended properties

Schema.org's property definitions and Google's feature requirements serve different purposes. Schema.org describes vocabulary semantics and expected values; Google feature documentation defines what is required or recommended for a specific Google Search enhancement.

For a Google feature, missing a required property can make an item ineligible. Recommended properties may improve completeness or usefulness, but adding every possible property is not a substitute for accurate data. Prefer a smaller, complete, truthful description over a large graph populated with empty strings, invented values, or guessed attributes. [2][4]

### 2.2 Stable identifiers and entity relationships

Use @id where a stable identifier helps distinguish and connect entities. A site may use consistent identifiers for its organization, website, and page nodes, then refer to those nodes from other markup. A stable identifier should be predictable, unique within the site's model, and consistently reused when the same entity is described across templates.

Do not create a new identifier for the same entity on every page without a reason. Conversely, do not reuse one identifier for distinct entities simply because they share a name. Identifier design should follow the canonical semantic model owned by Domain 09. Structured data implements that model; it should not silently redefine it. [1]

Properties such as sameAs should point to authoritative pages that identify the same entity, not loosely related profiles, search result pages, or unrelated entities with similar names. A URL in a property is a data relationship, not proof that the destination endorses or verifies the entity.

### 2.3 Multiple entities on one page

A page may contain more than one meaningful entity—for example, a primary article, its author, its publisher, and a video embedded in the article. These can be represented as connected or separate nodes when each item genuinely appears in or relates to the page.

Use nesting when a property naturally contains another item, and use graph references when multiple nodes need to refer to the same entity. Ensure that the graph reflects the page's actual hierarchy and purpose. Do not add unrelated types to chase multiple possible search appearances. Google specifically advises using markup that represents the page's main purpose and the additional content actually present. [4]

## 3. Match markup to visible content and page identity

Structured data must accurately represent the page it describes. The values should be consistent with the visible content and the current state of the underlying source data.

Implementation checks include:

- **Visible-content consistency:** do not mark up information that is hidden from users, unrelated to the page, misleading, or materially different from the content presented.
- **Page-level relevance:** place the markup on the page that describes the item, following any feature-specific instructions. Do not attach one product, event, article, or review to unrelated URLs.
- **Completeness:** include all required properties for the intended feature and ensure marked-up collections or reviews accurately represent the relevant visible content.
- **Freshness:** keep volatile fields such as availability, price, event dates, ratings, and job status synchronized with the actual current state.
- **Image accessibility:** when a feature uses image URLs, ensure the referenced assets are relevant and can be fetched by the relevant crawler.
- **Canonical consistency:** align entity/page URLs with the site's canonical URL strategy. Structured data does not repair conflicting canonicals, duplicate URL architecture, or inaccessible pages.
- **Language and locale:** use values that correctly describe the localized page and entity. Do not use markup to claim a locale, currency, or language that the page does not actually represent.

Google's general guidelines require accurate, relevant markup and prohibit misleading or hidden content. Some violations can prevent rich-result display or result in structured-data manual actions. [2][5]

## 4. Implementation architecture and data governance

Structured data can be generated in server-side templates, static-site build pipelines, CMS fields, application services, or client-side JavaScript. The correct approach depends on the site's architecture, but the data should have a clear source of truth.

### 4.1 Establish one authoritative data source

Map each structured-data property to an authoritative content or application field. For example, product availability should come from the current inventory system, not a manually maintained template string. Article dates should come from the publishing system's actual publication and modification records, not from the current render time.

Document field mappings, transformations, default behavior, null handling, freshness requirements, and ownership. Avoid fabricated defaults such as generic prices, placeholder authors, empty ratings, or dates generated only to populate markup.

### 4.2 Generate markup in templates or application code

Template-based or server-side generation can make markup available in the initial HTML and keep it aligned with the content record. Static generation can provide the same benefit when the build process refreshes the data appropriately. The implementation should account for pagination, localization, product variants, multi-author content, and other template edge cases.

Where JavaScript generates structured data, verify that the relevant crawler can render and process the final markup. Google documents that it can process dynamically injected JSON-LD, but client-side generation introduces dependencies on successful rendering, data requests, and script execution. For fast-changing product information such as price and availability, Google warns that dynamically generated markup can make Shopping crawls less frequent and reliable. [6]

### 4.3 Prevent duplication and conflicts

A common source of defects is multiple systems emitting overlapping markup—for example, a CMS plugin, theme, tag manager, and custom application code all generating an Organization or Product entity independently.

Inventory every source of structured data on representative templates. Decide which system owns each node and property. If more than one component contributes to a graph, define how identifiers and values are shared. Remove stale markup when a plugin, theme, or template is replaced.

### 4.4 Treat markup as production data

Structured data should be included in the same change-control process as other application output:

- Validate field mappings and schema generation in development.
- Test representative templates and data edge cases.
- Include structured-data checks in release and regression testing.
- Monitor source data changes that can invalidate markup.
- Keep implementation and feature documentation current.
- Record the affected templates, properties, and rollout when making a material change.

A syntactically valid JSON-LD block can still describe the wrong entity or outdated business state. Production correctness depends on data lineage and lifecycle management, not only on serialization.

## 5. Validation is a layered process

No single validator proves that structured data is correct in every sense. Separate the following validation layers:

| Layer | What it checks | Suitable methods |
|---|---|---|
| 1. Serialization and parsing | JSON syntax, valid HTML embedding, and parseable markup | JSON parser, HTML inspection, build tests |
| 2. Vocabulary semantics | Recognized types/properties and compatible value structures | Schema.org vocabulary reference and Schema Markup Validator |
| 3. Search-feature eligibility | Feature-specific required properties and technical rules | Google's Rich Results Test and exact feature documentation |
| 4. Content and policy compliance | Accuracy, visibility, relevance, completeness, freshness, and policy compliance | Manual review against the rendered page and feature policies |
| 5. Crawl and rendering | Whether the crawler can fetch the page and access the final markup and resources | URL Inspection, live URL tests, rendered HTML/DOM inspection |
| 6. Search processing and reporting | Whether Google has detected eligible items or reported issues after crawling | Search Console enhancement reports where available |
| 7. Search appearance | Whether the feature is actually displayed for relevant queries | Search observation and performance analysis; display is not guaranteed |

The Schema Markup Validator checks Schema.org vocabulary usage; it is not a Google rich-result eligibility test. Google's Rich Results Test focuses on supported Google Search rich-result types. URL Inspection helps investigate the indexed or live URL and the rendered page. Search Console reports provide site-level information for supported features and detected issues. Use each tool for its actual purpose. [2][7][8]

### 5.1 Validate code and rendered URLs

Code testing is useful during development, but it cannot fully reproduce a live page's rendering, access, or data state. Test representative live URLs where possible, especially when markup is generated by JavaScript, CMS plugins, application APIs, or complex templates.

For dynamically rendered pages, inspect the final rendered HTML or DOM rather than assuming the source template contains the final markup. Check that requests required to generate the structured data succeed and that no rendering error prevents its insertion. Google recommends URL-based testing for JavaScript-generated structured data because code-input testing has limitations. [6]

### 5.2 Interpret errors and warnings

An error may indicate malformed markup, an invalid value, or a missing required property. A warning may indicate a recommended property is absent or that the data could be more complete. Read the exact feature documentation before deciding whether a warning blocks eligibility.

A clean test result does not verify that every value is true, visible, current, or policy-compliant. Automated tests cannot reliably determine all semantic and editorial issues. Manual inspection remains necessary. [2][7]

### 5.3 Verify after deployment

After publishing a change:

1. Fetch the live URL and confirm the expected HTTP response.
2. Inspect the rendered page and verify that the markup exists in the final output.
3. Run the relevant feature test against the live URL.
4. Use URL Inspection to investigate crawl/rendering or indexed-version differences when needed.
5. Review Search Console reports for detected issues and eligible items, where those reports exist.
6. Allow for recrawling and reprocessing; a successful test immediately after deployment does not mean Google has already processed the change.
7. Re-test representative templates after CMS, plugin, theme, schema-library, or application updates.

## 6. Google Search support and feature lifecycle

Google's supported structured-data features are product-specific and subject to change. The Search Gallery is the current reference for the features Google documents as supported. Consult the exact feature guide before implementing or maintaining a type for Google Search. [3]

A type can remain valid in Schema.org and useful to other consumers even if Google no longer uses it for a dedicated rich result. Conversely, Google may use structured information in ways that do not correspond to a standalone rich-result treatment. Therefore:

- Do not describe every Schema.org type as a Google rich-result type.
- Do not rely on old tutorials, plugin defaults, or screenshots as proof of current feature support.
- Recheck feature availability, required properties, and policies before implementation and during maintenance.
- When Google retires a search appearance, distinguish the loss of that Google feature from the broader validity or usefulness of the vocabulary elsewhere.

Google announced in 2025 that it was phasing out selected less-used structured-data search features and later documented removal of support for affected types in Search Console and its API from January 2026. This illustrates why feature-specific guidance and changelogs must be checked rather than treated as permanent. [9][10]

## 7. Common implementation failures

| Failure | Why it matters | Corrective direction |
|---|---|---|
| Choosing a type because a plugin recommends it | The type may not describe the page or be supported for the intended search feature | Start with the page's actual subject and verify the current feature guide |
| Marking up hidden or unrelated content | The data misrepresents what users can see | Align markup with the rendered, visible page |
| Inventing ratings, reviews, prices, authors, or dates | Creates misleading or policy-violating data | Use verified source fields; omit unknown values |
| Duplicating markup across plugins and templates | Can create conflicting nodes or stale values | Establish one source of truth and audit emitted output |
| Using unstable or contradictory @id values | Prevents reliable entity references across pages | Align IDs with the canonical entity model |
| Generating dynamic markup from unreliable client requests | Rendering or data-fetch failures can prevent processing; volatile product data may be delayed | Prefer dependable server/build output where appropriate and validate rendered URLs |
| Testing only pasted code | Does not test the live page, crawler access, or runtime generation | Test representative live URLs and rendered output |
| Treating warnings as errors—or ignoring all warnings | Misreads feature eligibility and data quality | Interpret each result using the exact feature documentation |
| Assuming a passing test guarantees a rich result | Search engines make independent display decisions | Report technical validity and actual appearance as separate outcomes |
| Leaving old markup after a feature retirement | Creates maintenance cost without the expected search appearance | Reassess the use case and retain markup only where it remains useful and accurate |

## 8. Implementation and maintenance workflow

Use the following workflow for new deployments and material changes:

1. **Define the page and entity.** Identify the page's primary subject, supporting entities, canonical URL, and intended consumer.
2. **Resolve semantic ownership.** Reuse the approved entity and concept model from Domain 09. Do not create a competing semantic model inside the technical implementation.
3. **Check consumer requirements.** Consult Schema.org for vocabulary semantics and the current Google Search Gallery and feature-specific documentation for Google eligibility.
4. **Map authoritative fields.** Identify the source system for each property, transformations, null behavior, freshness requirements, and responsible owner.
5. **Choose the serialization format.** Select JSON-LD, Microdata, or RDFa based on maintainability and the existing architecture. Avoid redundant parallel output.
6. **Implement in the correct layer.** Use the CMS, template, build pipeline, or application component that can keep markup synchronized with source data.
7. **Validate each layer.** Test syntax, vocabulary, feature requirements, visible-content consistency, policies, and crawler rendering.
8. **Test representative cases.** Include multiple templates, missing optional data, localized pages, pagination, product or event state changes, and relevant edge cases.
9. **Deploy and verify live output.** Re-test live URLs, inspect rendered markup, and check Search Console after processing where applicable.
10. **Monitor and maintain.** Revisit the implementation when source data, templates, plugins, vocabulary definitions, search features, or policies change.
11. **Record evidence.** Document the affected templates and URLs, tools, test date, errors/warnings, fixes, deployment ref, and remaining limitations.

## 9. Reporting and interpretation limits

A structured-data implementation report should state:

- Pages, templates, and entity types in scope.
- Intended consumer and search feature, if applicable.
- Vocabulary and serialization format.
- Source-of-truth fields and implementation component.
- Validation tools, dates, and representative URLs tested.
- Parsing, vocabulary, eligibility, policy, and rendering results as separate findings.
- Errors, warnings, exceptions, and unresolved data-quality issues.
- Deployment reference and post-deployment checks.
- Whether the result is implemented, technically validated within scope, or observed in search appearance.

Keep the conclusions distinct:

- **Implemented:** markup has been added to the relevant site output.
- **Technically validated:** specified parsing, vocabulary, or feature checks passed for the tested scope.
- **Policy reviewed:** visible-content and relevant feature-policy checks were performed.
- **Crawl/render checked:** the tested crawler-facing representation exposed the expected markup.
- **Displayed:** a search feature was observed in a particular context and at a particular time.

None of these states automatically proves the next. A technically valid page may not be indexed, a valid item may not be eligible for a particular Google feature, and an eligible item may not be displayed for a given query. Structured data does not guarantee indexing, ranking improvements, or rich-result appearance. [2][3]

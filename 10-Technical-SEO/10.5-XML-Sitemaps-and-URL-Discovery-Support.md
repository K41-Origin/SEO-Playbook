# 10.5 — XML Sitemaps & URL Discovery Support

[← Domain 10 — Technical SEO](README.md)

An XML sitemap is a machine-readable inventory of URLs that a publisher makes available to search engines. It can support URL discovery and communicate selected metadata, but it is not a crawl command, an indexing directive, or a guarantee of search visibility. A search engine independently decides whether and when to fetch a sitemap, crawl a listed URL, index its content, and show it in results. [1][2]

This topic covers the publisher-side design, generation, publication, submission, and maintenance of XML sitemaps. It does not replace the crawl-management model in [10.3](10.3-Crawlability-and-Crawl-Management.md), crawler access rules in [10.4](10.4-Robots-txt-and-Crawler-Access-Control.md), or indexability and canonical selection in [10.6](10.6-Indexability-Canonicalization-and-Duplicate-URL-Management.md).

## 1. What a sitemap can and cannot do

A sitemap gives search engines a structured list of URLs and, where supported, additional information about those resources. It is especially useful when a site has a large URL inventory, newly published pages with few external discovery paths, complex sections, or specialized media and news content. Google notes that a small site with comprehensive internal linking may not need a sitemap, although a sitemap can still be useful as an operational inventory. [1]

A sitemap can help a crawler discover a URL it has not yet encountered through links. It does not:

- Force a crawler to fetch a listed URL.
- Increase a site's crawl capacity or guarantee a crawl schedule.
- Override robots.txt or other access restrictions.
- Make a noindex page indexable.
- Force a search engine to accept the publisher's canonical preference.
- Guarantee indexing, ranking, or search-result presentation.

The distinction matters operationally: sitemap inclusion is a publisher-provided discovery and canonical-preference signal. It is not proof that the URL is crawlable, eligible for indexing, or indexed. [1][2]

## 2. Decide which URLs belong in the sitemap

Start with the intended canonical URL inventory, not with every URL that the application can generate. In ordinary cases, include the stable, preferred URLs that you want search engines to discover and potentially show in search results.

A practical inclusion policy should generally require that a URL:

- Represents a real, useful resource intended to be available in search.
- Uses the preferred protocol, hostname, and URL form.
- Returns the expected successful response rather than redirecting or failing.
- Is not deliberately excluded from indexing with a robots meta directive or `X-Robots-Tag`.
- Is not blocked from the relevant crawler when the intention is for that crawler to fetch and evaluate it.
- Is not a duplicate or alternate URL when another URL is the preferred canonical.

Google recommends listing canonical URLs and notes that it generally uses canonical URLs in Search. Sitemap inclusion can contribute to canonicalization signals, but it does not compel Google to select the listed URL. Keep the sitemap aligned with canonical declarations, redirects, and internal links rather than using it to compensate for contradictory signals. [2][3]

Avoid routinely including:

- Redirecting URLs and redirect-chain intermediates.
- URLs returning 4xx or 5xx responses.
- Duplicate variants that resolve to the same content when a preferred URL exists.
- Tracking, session, sorting, filtering, or other parameter combinations that do not represent distinct search-worthy resources.
- URLs carrying a deliberate noindex directive.
- URLs that are inaccessible to the intended crawler because of access controls or robots rules.

These are general inventory-quality recommendations, not a claim that every search engine treats every conflicting URL identically. A search engine may still discover a URL from other sources or make its own canonical and indexing decisions. For the exact effects of directives and canonical hints, see [10.6](10.6-Indexability-Canonicalization-and-Duplicate-URL-Management.md).

## 3. XML sitemap structure

The standard XML sitemap format uses the Sitemap protocol namespace:

`http://www.sitemaps.org/schemas/sitemap/0.9`

A basic sitemap has a `<urlset>` root, one `<url>` entry per listed resource, and a required `<loc>` element containing the absolute URL. The `<lastmod>` element is optional. [3]

Example:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://www.example.com/guides/technical-seo/</loc>
    <lastmod>2026-11-20</lastmod>
  </url>
  <url>
    <loc>https://www.example.com/guides/xml-sitemaps/</loc>
    <lastmod>2026-11-18T14:30:00+00:00</lastmod>
  </url>
</urlset>
```

The protocol also limits each `<loc>` value to fewer than 2,048 characters. [3]

The important elements are:

| Element | Requirement | Meaning |
|---|---|---|
| `<urlset>` | Required | Root element containing URL entries and the protocol namespace. |
| `<url>` | Required | Container for one URL entry. |
| `<loc>` | Required | Fully qualified URL of the resource. |
| `<lastmod>` | Optional | Date/time when the linked page was last meaningfully modified. |
| `<changefreq>` | Optional in the protocol | Publisher estimate of expected change frequency; Google ignores it. |
| `<priority>` | Optional in the protocol | Relative priority value; Google ignores it. |

All XML values must be properly entity-escaped. For example, an ampersand in a query string must be represented as `&amp;` inside XML. URLs must also be correctly URL-encoded. The file must use UTF-8 encoding. [2][3]

Use absolute URLs, including scheme and hostname. Do not use root-relative or path-relative values such as `/products/item-1`. Under the protocol's location rules, a sitemap at `/catalog/sitemap.xml` can list URLs under `/catalog/`, but not unrelated paths such as `/images/`; the listed URLs must also match the applicable host and protocol scope. Google separately documents that, unless the sitemap is submitted through Search Console, its effect is limited to descendants of the sitemap's parent directory. Placing the sitemap at the site root is therefore a practical default when a single sitemap should cover the broader site. [2][3]

## 4. The meaning of lastmod, changefreq, and priority

### lastmod: report real page changes

The `<lastmod>` value should represent when the linked page was last significantly modified, not when the sitemap file was generated. A substantial change to the main content, structured data, or important links can qualify. A routine deployment, automated timestamp refresh, or copyright-year update does not necessarily represent a meaningful page change. [2][3]

Google says it uses `lastmod` when the value is consistently and verifiably accurate. A reliable implementation therefore needs a trustworthy content-modification timestamp from the publishing system, CMS, or content pipeline. If the system cannot distinguish meaningful page changes from routine updates, omitting `lastmod` is preferable to publishing systematically misleading values. [2]

Do not confuse a page's `<lastmod>` value with the `<lastmod>` value in a sitemap index. In a sitemap index, the latter describes when the referenced sitemap file was modified, not when any individual page inside it changed. [3][4]

### changefreq and priority: protocol fields are not universal controls

The Sitemap protocol defines `<changefreq>` and `<priority>` as optional fields. Their interpretation and support can vary by search engine. Google explicitly ignores both values, so adding them does not tell Google to crawl a page more frequently or rank it more highly. [2][3]

Do not spend engineering effort populating these fields for a Google-specific benefit that Google says it does not use. If another search engine documents support, evaluate that behavior from its own current documentation rather than generalizing Google's implementation.

## 5. Splitting large inventories and using sitemap indexes

A single sitemap file must contain no more than 50,000 URLs and must not exceed 50 MB when uncompressed. The same size and URL limits apply even when the sitemap is compressed with gzip: compression reduces transfer size, but the uncompressed file must remain within the limit. [2][3]

When the inventory exceeds either limit, split it into multiple sitemap files. A sitemap index can then list the child sitemap files so a search engine can discover the collection from one submitted index.

Example:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap>
    <loc>https://www.example.com/sitemaps/pages-1.xml.gz</loc>
    <lastmod>2026-11-20T10:00:00+00:00</lastmod>
  </sitemap>
  <sitemap>
    <loc>https://www.example.com/sitemaps/articles-1.xml.gz</loc>
    <lastmod>2026-11-21T08:30:00+00:00</lastmod>
  </sitemap>
</sitemapindex>
```

A sitemap index uses `<sitemapindex>` as its root, with one `<sitemap>` element per referenced file and a required `<loc>` for each child sitemap. Its optional `<lastmod>` describes the modification time of that child sitemap. A sitemap index can reference up to 50,000 sitemap files and is subject to the same 50 MB uncompressed size limit. [3][4]

Google's sitemap-index guidance adds operational constraints: referenced sitemaps must normally be on the same site as the index and in the same directory or a lower directory in the hierarchy. Cross-site submission is an exception when configured through Google's documented process. Google Search Console allows up to 500 sitemap index files per site property; that Search Console account limit should not be confused with the protocol's 50,000 child-sitemap limit per index file. [4]

Choose partitions that make the inventory easier to generate and diagnose. Common strategies include separating content types, site sections, locales, or update cadences. Partitioning is an operational design choice, not a ranking tactic. Keep the grouping stable enough that changes in reported counts can be interpreted over time.

## 6. Generate from a controlled URL source

For a small, rarely changing site, a manually maintained sitemap may be practical. For larger or frequently updated sites, generation from the CMS, database, routing layer, or a controlled publishing inventory is generally more reliable. Google recommends using the site's software to generate the sitemap where possible. [2]

A robust generation pipeline should:

1. Define which content types and URL states are eligible for inclusion.
2. Resolve each resource to its preferred absolute URL.
3. Exclude duplicates, redirects, errors, noindex resources, and URLs outside the intended scope.
4. Read a meaningful last-modified timestamp from the source system when available.
5. Escape XML values and serialize valid UTF-8 XML.
6. Split output before either the URL-count or uncompressed-size limit is exceeded.
7. Generate or update the sitemap index when child files change.
8. Publish files atomically so crawlers do not encounter partially written XML.
9. Validate the generated output before exposing the new version.
10. Retain enough generation metadata to investigate unexpected changes in URL counts or timestamps.

Do not build the sitemap from an indiscriminate crawl export alone. A crawl can reveal URLs that exist technically but should not be promoted as canonical, indexable resources. Instead, reconcile application inventory, canonical rules, response behavior, and publication status. This is a publisher-side engineering recommendation derived from the need to keep sitemap entries aligned with the intended URL set; the exact implementation depends on the site's architecture.

## 7. Publish, discover, and submit

A sitemap must be publicly retrievable by the intended crawler. Check that the file is served at a stable URL, returns a successful response, is not behind authentication, and is not blocked by robots.txt or infrastructure rules. Google recommends hosting a sitemap at the site root where practical. [2][5]

Common discovery and submission methods include:

- **robots.txt:** add a fully qualified `Sitemap:` directive pointing to the sitemap or sitemap index. Multiple sitemap declarations can be used.
- **Google Search Console:** submit the sitemap URL or sitemap index through the Sitemaps report.
- **Search Console API:** submit and manage sitemaps programmatically where an authorized workflow requires it.

Submitting a sitemap through Search Console tells Google where the file is; it does not upload the file to Google. The sitemap remains hosted on the publisher's site. Search Console submission requires owner permissions for the property. A robots.txt reference is an alternative discovery path. [2][5]

Google supports cross-site sitemap submission under documented conditions, including verifying ownership of all relevant sites when using Search Console. Cross-site arrangements are an exception to the normal same-site scope rules and should not be assumed to work automatically for every crawler. Follow the relevant search engine's current instructions. [2][4]

Sitemap discovery through robots.txt connects this topic to [10.4 — Robots.txt & Crawler Access Control](10.4-Robots-txt-and-Crawler-Access-Control.md). The robots.txt file announces a sitemap location; it does not make the listed page URLs crawlable if other access restrictions prevent retrieval.

## 8. Validation and ongoing maintenance

Treat sitemap validation as both a format check and an inventory-quality check.

### File and protocol validation

- Confirm XML is well-formed and uses UTF-8.
- Confirm the required namespace and elements are present.
- Confirm every `<loc>` is an absolute, correctly encoded URL.
- Confirm XML special characters are entity-escaped.
- Confirm each file stays within the 50,000-URL and 50 MB uncompressed limits.
- Confirm gzip files decompress correctly and the uncompressed content is valid.
- Confirm every sitemap-index child URL resolves to an available sitemap.
- Confirm the sitemap and its child files are retrievable without authentication.

### URL inventory validation

- Compare sitemap entries with the intended canonical URL inventory.
- Check status codes and redirect destinations.
- Identify duplicate URLs, unexpected hosts, parameter variants, and stale entries.
- Check consistency with canonical declarations and indexability directives.
- Check that robots.txt does not prevent the intended crawler from fetching the sitemap or listed resources.
- Confirm `lastmod` values change only when the corresponding page is meaningfully modified.
- Track unexpected changes in total URL counts and per-section distribution.

### Search Console diagnostics

Google's Sitemaps report records submitted sitemap history and reports fetch or parsing errors. It can show whether Google successfully fetched and read a submitted sitemap, but this is not the same as confirming that every listed URL was crawled or indexed. A sitemap can be successfully processed while individual URLs remain uncrawled or unindexed. [5]

Keep these quantities separate:

| Measurement | What it represents |
|---|---|
| URLs listed | Entries emitted by the publisher's sitemap generator. |
| Sitemap fetched | Whether the search engine retrieved the sitemap file. |
| Sitemap processed | Whether the search engine could parse and process the file. |
| URLs discovered | URLs the search engine has learned about; this may include sources beyond the sitemap. |
| URLs crawled | URLs actually requested by a crawler. |
| URLs indexed | URLs selected for inclusion in a search index. |

These are different stages and measurements. Do not interpret a submitted count or a successful sitemap status as an indexing report. For Google-specific diagnostics, consult the Sitemaps report and the relevant indexing reports; for request-level crawl evidence, see [10.12 — Server Logs, Crawl Diagnostics & Technical Monitoring](10.12-Server-Logs-Crawl-Diagnostics-and-Technical-Monitoring.md). [5]

## 9. Common implementation failures

- **Sitemap treated as a crawl command:** submission is a hint, not a guaranteed fetch or indexing request.
- **Generated from every route:** the file becomes polluted with duplicate, filtered, session, or otherwise low-value URL variants.
- **Canonical mismatch:** sitemap entries conflict with canonical declarations, redirects, or internal links.
- **Stale inventory:** deleted and redirected URLs remain listed after publication changes.
- **False freshness:** every build updates `lastmod`, even when page content has not materially changed.
- **Invalid XML:** unescaped query strings, malformed XML, incorrect encoding, or missing required elements prevent reliable processing.
- **Scope mismatch:** a sitemap is placed in a narrow directory or references hosts and paths outside its permitted scope.
- **Oversized files:** URL count or uncompressed byte size exceeds the protocol limit.
- **Broken sitemap index:** one or more child sitemap files are missing, inaccessible, malformed, or outside the allowed location.
- **Blocked sitemap retrieval:** authentication, robots rules, CDN behavior, or server errors prevent the crawler from reading the file.
- **Reporting confusion:** sitemap submission, fetch success, URL discovery, crawling, and indexing are treated as interchangeable outcomes.

## 10. Practical implementation workflow

A maintainable sitemap workflow can be organized as follows:

1. **Define the inventory:** document eligible resource types, canonical URL rules, exclusions, and ownership.
2. **Choose the format:** use XML when structured metadata or extensions are needed; consider RSS/Atom or text formats only when their narrower capabilities fit the use case. Google supports several sitemap formats and does not express a preference among them. [2]
3. **Generate deterministically:** derive entries from trusted application data and stable URL rules.
4. **Partition deliberately:** split large inventories by a maintainable dimension and create a sitemap index when useful.
5. **Validate before release:** test XML, URL scope, response behavior, canonical alignment, timestamps, size, and index references.
6. **Publish atomically:** make the complete new sitemap set available before updating the index that points to it.
7. **Expose discovery paths:** reference the sitemap in robots.txt and/or submit it through the relevant search-engine tools.
8. **Monitor processing:** review fetch and parse errors, URL counts, and representative URL states.
9. **Reconcile outcomes:** investigate important differences between listed, discovered, crawled, and indexed URLs without assuming the sitemap alone explains them.
10. **Maintain with releases:** update sitemap output when content is created, materially changed, canonicalized, redirected, or removed.

This workflow is a technical control model. The exact automation, alert thresholds, and ownership depend on the CMS, infrastructure, URL volume, and operational requirements of the site.

# 10.7 — HTTP Status Codes, Redirects & URL Migration

[← Domain 10 — Technical SEO](README.md)

HTTP is a request/response protocol. Status codes communicate the result of handling a request; they are protocol semantics, not SEO scores. RFC 9110 groups status codes into five classes: 1xx informational, 2xx successful, 3xx redirection, 4xx client error, and 5xx server error. [1]

## 1. Status codes in technical diagnosis

Common responses include:

- **200 OK:** the request succeeded. It does not prove that the content is indexable or useful.
- **204 No Content:** the request succeeded but the response has no content.
- **301 Moved Permanently / 308 Permanent Redirect:** the target is intended to replace the requested URI permanently; 308 preserves the request method.
- **302 Found / 307 Temporary Redirect:** temporary redirection; 307 preserves the request method.
- **304 Not Modified:** the representation has not changed relative to the conditional request, allowing cache reuse.
- **400 Bad Request:** the server cannot or will not process the request due to a perceived client error.
- **401 Unauthorized / 403 Forbidden:** authentication is required or access is refused, respectively.
- **404 Not Found / 410 Gone:** the resource is not currently available or is known to be permanently gone.
- **429 Too Many Requests:** the client has sent too many requests in a given period.
- **5xx:** server-side failures.

These are concise descriptions; consult RFC 9110 for normative semantics and the applicable server/client documentation for implementation details. [1] Google publishes how its crawlers process common status codes, but those effects are Google-specific and should not be generalized to all crawlers. [2]

## 2. Redirect design

Use a redirect when the requested resource has moved or the client should resolve to another URL. Select a status consistent with the intended permanence and request-method behavior. For ordinary page migrations, permanent redirects are generally used when the new URL is the lasting replacement; temporary redirects are for temporary conditions. [1][3]

Avoid redirect chains, loops, irrelevant destinations, and redirecting every removed URL to the homepage. Redirects should preserve the closest meaningful destination. Update internal links and canonical declarations to point directly to the final URL rather than relying on a chain.

## 3. URL and site migrations

A migration may change paths, hostname, protocol, CMS, rendering architecture, or domain. Scope the change before launch:

1. Inventory old URLs, templates, assets, and important entry points.
2. Map each old URL to its closest equivalent destination.
3. Identify removals that have no replacement and return an accurate not-found/gone response.
4. Prepare redirects and update internal links, canonicals, structured data, and sitemaps.
5. Test representative old/new URLs, response codes, destination relevance, robots rules, and rendering.
6. Deploy in a controlled window and retain rollback capability.
7. Monitor server logs, crawl errors, redirects, sitemap processing, and search-engine reports.
8. Keep redirects in place long enough to support users and crawlers; follow current provider guidance for the migration type.

Google recommends preparing URL mappings, implementing redirects, and monitoring the move. Search fluctuations can occur while URLs are recrawled and reprocessed; no migration checklist guarantees uninterrupted visibility. [3]

## 4. Response correctness and soft 404s

A page that displays a “not found” message but returns HTTP 200 may be interpreted as a soft 404 by a search engine. Conversely, returning 404 for a real resource because of a routing or CDN defect hides a valid page behind an error. Google documents its treatment of status codes for Google crawlers; use server-side evidence to identify the actual response rather than relying on the browser's visual display. [2]

## 5. Validation checklist

- Test GET and other relevant methods where application behavior requires them.
- Record the complete redirect chain and final destination.
- Check status, headers, response body, and cache behavior.
- Test trailing slash, hostname, protocol, and parameter variants.
- Verify canonical and sitemap targets after redirects are deployed.
- Test missing resources and removed content with accurate response codes.
- Check 429/5xx rates and server capacity during high-volume changes.
- Compare staging and production; do not treat a successful staging test as production verification.

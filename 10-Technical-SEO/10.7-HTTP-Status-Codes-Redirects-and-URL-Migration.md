# 10.7 — HTTP Status Codes, Redirects & URL Migration

[← Domain 10 — Technical SEO](README.md)

HTTP status codes communicate the result of handling a request. Redirects communicate that a client should take further action to reach a resource or representation. URL migrations change the address or location through which users and systems access resources. These mechanisms affect technical delivery, user experience, caching, crawling, and search-engine processing, but HTTP status codes are not SEO scores. [1]

This topic explains HTTP response semantics relevant to technical SEO, redirect selection and implementation, URL migration planning, and post-release verification. It does not replace the HTTP specification, cover every application-level protocol behavior, or guarantee how any search engine will process a migration.

## 1. HTTP response fundamentals

HTTP uses a request/response model. A client sends a request for a resource; a server or intermediary returns a response containing a status code and, depending on the response, headers and content. The status code is a three-digit value whose first digit identifies the response class. [1]

| Class | Meaning | Common technical SEO relevance |
|---|---|---|
| 1xx | Informational | Interim protocol responses; rarely a final page outcome in ordinary crawling reports. |
| 2xx | Successful | The request was handled successfully; the returned representation may be processed. |
| 3xx | Redirection | Further action or another request is needed to complete the interaction. |
| 4xx | Client error | The request cannot be fulfilled as received; may indicate a missing resource, access restriction, or invalid request. |
| 5xx | Server error | The server failed to fulfill an apparently valid request; may indicate transient or persistent infrastructure/application failure. |

The status code must describe the actual outcome, not the response body the site owner wishes the client to believe it received. A page that visually says “not found” but returns 200 OK is not an ordinary HTTP 404 response. Conversely, a valid page that returns 404 due to a routing defect is still delivered as an HTTP error from the client's perspective. [1][2]

### Status code, headers, and body must agree

A complete diagnosis inspects more than the visible browser page:

- Request URL and method.
- Response status.
- Location header for redirects.
- Retry-After when a server asks clients to retry later.
- Cache-Control, ETag, and Last-Modified where relevant to caching and conditional requests.
- Content-Type and response body.
- Redirect chain and final destination.
- Whether the response differs by host, protocol, user agent, cookie, geography, or CDN edge.

A browser may follow redirects automatically and display only the final page. That is useful for navigation but hides the intermediate responses that matter when debugging redirect chains, loops, and unexpected status changes.

## 2. Status codes that commonly matter

The following table summarizes selected codes using their HTTP semantics. Search-engine handling is a separate implementation layer and is discussed in Section 3.

| Code | HTTP meaning | Typical use and technical interpretation |
|---|---|---|
| 200 OK | Request succeeded. | Normal response when the requested representation is available. It does not prove indexability or indexing. |
| 201 Created | Request created a resource. | Common in APIs and resource-creation workflows; not a typical final response for a normal content page. |
| 202 Accepted | Request accepted for processing, but processing is incomplete. | Often used for asynchronous operations. A crawler receiving an interim or placeholder response may not receive the eventual content. |
| 204 No Content | Request succeeded, with no response content. | Appropriate for certain API actions, generally unsuitable when a page crawler is expected to receive a document. |
| 206 Partial Content | Server fulfilled a range request. | Relevant to partial downloads and media; inspect request headers and resource behavior before treating it as a page failure. |
| 301 Moved Permanently | Resource has a new permanent URI. | Common for permanent URL changes and canonical host/protocol normalization. |
| 302 Found | Resource is temporarily available at another URI. | Common temporary redirect; does not express the same permanence semantics as 301. |
| 303 See Other | Client is redirected to another resource, commonly retrieved with GET. | Often used after a state-changing request to direct the client to a result page. |
| 304 Not Modified | The selected representation has not changed relative to a conditional request. | Enables cache reuse; it is not a redirect to another URL and ordinarily has no response body. |
| 307 Temporary Redirect | Temporary redirect that preserves the request method. | Use when temporary redirection must not change the method. |
| 308 Permanent Redirect | Permanent redirect that preserves the request method. | Permanent counterpart to 307; useful when method preservation matters. |
| 400 Bad Request | Server cannot or will not process the request due to a perceived client error. | Can indicate malformed URLs, invalid parameters, or application validation failure. |
| 401 Unauthorized | Request lacks valid authentication credentials. | Authentication challenge; not a substitute for crawl-rate management. |
| 403 Forbidden | Server understood the request but refuses to fulfill it. | Access is refused; distinguish intentional authorization from accidental bot/firewall blocking. |
| 404 Not Found | No current representation was found, or the server is unwilling to disclose one. | Appropriate for a resource that cannot be found and has no suitable replacement. |
| 410 Gone | Access to the target resource is no longer available and this condition is likely permanent. | Useful when the publisher knows the resource has been intentionally and permanently removed. |
| 429 Too Many Requests | Client sent too many requests in a given period. | Rate limiting; may include Retry-After. Misapplied limits can block legitimate crawlers and users. |
| 500 Internal Server Error | Unexpected server condition prevented fulfillment. | Application or server failure; investigate logs and error rates. |
| 502 Bad Gateway | Gateway/proxy received an invalid response from an upstream server. | Often points to an origin, proxy, or upstream dependency problem. |
| 503 Service Unavailable | Server is temporarily unable to handle the request. | Appropriate for temporary overload or maintenance; may include Retry-After. |
| 504 Gateway Timeout | Gateway/proxy did not receive a timely upstream response. | Often points to upstream latency, dependency failure, or timeout configuration. |

The normative meanings come from RFC 9110. The table is selective, not a replacement for the complete status-code registry or application-specific documentation. [1]

### 404 versus 410

Both 404 and 410 communicate that the requested resource is unavailable. A 404 does not necessarily assert that the resource is permanently gone; a 410 more explicitly indicates that the condition is likely permanent. Choose the response that accurately reflects the resource's state. Do not return 410 merely because someone expects it to remove a URL faster, and do not redirect a deleted URL to an unrelated destination to avoid an error. [1][2]

### 401 and 403 are not crawl controls

Authentication and authorization responses should reflect the actual access policy. They should not be deployed as a way to slow a crawler or suppress unwanted requests. For Google, 401 and 403 are treated as client errors for indexing purposes, while 429 is treated as a server-overload signal. These details are Google-specific and may differ for other crawlers. [2]

## 3. How Google documents crawler handling of status codes

HTTP semantics apply across HTTP clients, but crawler behavior is implemented by each search engine. Google's current crawling-infrastructure documentation describes the following behavior for Google crawlers:

- **2xx:** Google can pass the received content to later processing. A 200 response does not guarantee indexing. An empty page or an error-like body returned with 2xx may be classified as a soft 404.
- **3xx:** Google crawlers generally follow redirects, with a documented default of up to 10 hops for general web crawling. The final target's content is processed; content from the redirecting response is ignored.
- **301 and 308:** Google treats these as strong signals that the redirect target should be processed.
- **302 and 307:** Google treats these as weaker redirect signals. 303 is also followed as a redirect, but its HTTP method semantics remain distinct.
- **304:** Google uses the response to indicate that the content is unchanged since the previous crawl, allowing the processing pipeline to reuse the previous content representation.
- **4xx:** Google does not use the response content. Previously indexed URLs returning 4xx are removed over time. The documentation treats 4xx responses similarly for indexing, with 429 as a notable exception.
- **429 and 5xx:** Google treats these as server-overload or server-error signals and temporarily reduces crawling. Persistently failing URLs can eventually be removed from the index. [2]

Google explicitly notes that crawler products may have different redirect limits and behavior. For example, its Inspection Tools do not follow redirects in the same way as general Googlebot crawling. Do not turn a Google-specific processing description into a universal rule for all bots, browsers, clients, or search engines. [2]

The most important operational distinction is between a deliberate resource state and an infrastructure failure. A real deleted page returning 404 is not equivalent to a valid page accidentally returning 404 because of a broken deployment. A temporary 503 during a planned maintenance window is not equivalent to a persistent 503 caused by an unstable origin.

## 4. Redirect semantics and selection

A redirect instructs a client to make a further request, commonly to the URI identified by the Location response header. Choose the redirect according to the intended resource relationship, permanence, and request-method behavior. [1]

### Permanent redirects: 301 and 308

Use a permanent redirect when the source URL has been replaced and the destination is the lasting location.

- **301 Moved Permanently** is widely used for ordinary page and URL migrations.
- **308 Permanent Redirect** communicates permanence while preserving the request method.

RFC 9110 notes historical method-handling differences for 301 and 302. A user agent may change a POST request to GET when following a 301 or 302; 307 and 308 were defined to make method preservation unambiguous. For ordinary GET-based content URLs, the distinction may not be visible to users, but it matters for APIs, forms, and other non-GET requests. [1]

Google recommends server-side permanent redirects such as 301 or 308 when a URL has permanently moved. It documents both as strong signals for the redirect target. This describes Google's processing, not a claim that every search engine uses an identical signal model. [2][3]

### Temporary redirects: 302 and 307

Use a temporary redirect when the source URL is expected to remain the preferred address after a temporary condition ends.

- **302 Found** is a temporary redirect. Historical user-agent behavior may change POST to GET.
- **307 Temporary Redirect** preserves the request method.

Examples include temporary service routing or short-lived operational conditions where the original URL should remain in use later. Do not leave a temporary redirect in place indefinitely simply because it was easier to implement. Reassess the actual permanence and change the response if the resource relationship becomes permanent. [1][3]

### 303 See Other

303 See Other redirects the client to another resource, typically retrieved using GET, to provide an indirect response to the original request. A common web application pattern is Post/Redirect/Get: after a form submission, the server returns a 303 to a result or confirmation page. It is not a generic substitute for a permanent page migration. [1]

### 304 Not Modified is not a redirect

A 304 Not Modified response is part of conditional request and caching behavior. It tells a client with a stored representation that it can reuse that representation because it has not changed according to the validation condition. It does not provide a new URL and should not be treated as a 3xx URL migration. [1][2]

## 5. Redirect implementation

### Prefer server-side HTTP redirects

Where possible, implement redirects at the web server, application routing, or edge/CDN layer so the response is returned before the browser must render a page or execute JavaScript. Server-side redirects are generally more direct, reliable, and easier to validate as HTTP responses.

Google documents multiple redirect methods, including server-side HTTP redirects, instant or delayed meta refresh, JavaScript location changes, and link-based “crypto redirects.” Its guidance prefers server-side redirects where possible and treats JavaScript redirects as a fallback when server-side and meta refresh options are unavailable. Rendering-dependent redirects can fail if the page is not successfully rendered. [3]

### Example: inspect a response

Use a request that does not automatically follow redirects to inspect the first response:

~~~bash
curl -sS -D - -o /dev/null https://www.example.com/old-path/
~~~

Then inspect the full chain separately:

~~~bash
curl -sS -L -D - -o /dev/null https://www.example.com/old-path/
~~~

The first command exposes the initial response headers. The second follows redirects and prints the response headers encountered along the chain. Tool behavior, proxy settings, cookies, user-agent selection, and request method can affect the result; reproduce the relevant production request context when debugging.

### Redirect rules should be deterministic

A maintainable redirect rule should:

- Match the intended source URL or clearly defined URL pattern.
- Resolve to one correct destination.
- Preserve meaningful path components and query parameters where appropriate.
- Avoid redirecting a URL to itself.
- Avoid loops and unnecessary intermediate hops.
- Avoid sending unrelated removed URLs to a generic destination.
- Avoid creating open redirects that allow arbitrary external destinations.
- Be tested against both expected matches and nearby non-matching URLs.

Broad pattern rules can be efficient, but a faulty expression can redirect large parts of a site incorrectly. Test rule precedence, encoded paths, trailing slashes, case handling, query strings, and host/protocol combinations before release.

### Redirect chains and loops

A chain occurs when one URL redirects to another URL that redirects again before reaching the final destination. A loop occurs when redirects eventually send the client back to a URL already visited.

Chains add latency, create more failure points, and may exceed client-specific limits. Google documents a default of up to 10 redirect hops for general web crawling but recommends avoiding chains and directing old URLs to the final destination. Its migration guidance advises keeping chains low—ideally no more than three and fewer than five hops—where a direct mapping is not possible. These are Google recommendations, not a universal protocol limit. [2][4]

A redirect loop prevents the client from reaching a final representation. Browsers typically stop after detecting repeated redirects or exceeding their own limits. Fix the rule conflict rather than adding more hops.

## 6. Match the response to the resource's real state

Redirects are not a universal solution for every unavailable URL.

| Resource condition | Appropriate approach | Avoid |
|---|---|---|
| Same resource moved to a new URL permanently | Permanent redirect to the replacement. | Leaving the old URL as an error or using a temporary redirect without reason. |
| Resource temporarily served elsewhere | Temporary redirect. | Signaling permanent replacement when the move is temporary. |
| Resource permanently removed with a genuine equivalent replacement | Redirect to the closest relevant replacement. | Redirecting to an unrelated category or homepage. |
| Resource permanently removed without a replacement | Return an accurate 404 or 410. | Fabricating a replacement destination. |
| Resource is private or restricted | Authentication and authorization. | Treating robots.txt or redirects as access security. |
| Temporary overload or maintenance | Appropriate 503 response; provide Retry-After when useful and accurate. | Returning 200 with a maintenance message or redirecting every page to a temporary generic page. |
| Request is malformed or invalid | Return the appropriate client-error response. | Redirecting malformed URLs into valid pages without understanding the input. |
| Content is duplicate but remains available at multiple URLs | Use the canonicalization policy covered in 10.6. | Using redirects when both URLs must remain independently accessible. |

### Soft 404s

A soft 404 occurs when a URL appears unavailable or has no meaningful content but returns a success response, commonly 200 OK. Examples include an empty product page, a missing-content template with a 200 response, or a broad redirect to a generic page that does not replace the requested resource. Google may classify such responses as soft 404s. [2][4]

A custom not-found page is useful for people, but it should return an actual 404 status when the requested resource does not exist. The visual design of the error page does not determine its HTTP semantics.

## 7. URL migration: define the change before choosing the redirect

A URL migration changes the address of existing resources. The scope may include:

- HTTP to HTTPS.
- www to non-www, or the reverse.
- Domain or subdomain changes.
- Path and URL structure changes.
- CMS or platform changes that alter URLs.
- Consolidation of multiple sites or hostnames.
- Merging, splitting, or restructuring content.

Not every infrastructure change is a URL migration. If a site changes hosting provider or CDN while keeping user-visible URLs unchanged, the primary work is infrastructure migration: prepare and test the new environment, move DNS or traffic, and verify consistent delivery. Google provides separate guidance for hosting changes without URL changes. [5]

Avoid combining a domain change, CMS replacement, URL restructuring, design overhaul, and content rewrite into one uncontrolled release unless there is a compelling operational reason. Changing one major dimension at a time makes failures easier to isolate. Google recommends this sequencing approach in its site-move guidance. [4]

## 8. Prepare an old-to-new URL mapping

A migration mapping is the source of truth for how each old URL should resolve.

### Build the source inventory

Do not rely on the current XML sitemap alone. Build a combined inventory using available evidence:

- Current and historical XML sitemaps.
- CMS or database exports.
- Application route definitions.
- Server access logs.
- Analytics landing pages and other important entry points.
- Internal links and navigation.
- URLs with external backlinks.
- Image, video, document, and downloadable asset URLs.
- Search Console data and other verified search-performance sources.
- Known legacy, campaign, parameterized, and alternate-host URLs.

Google recommends using sitemaps, logs, analytics, CMS inventories, and link data to identify URLs for a move. It also notes that embedded resources such as images, videos, JavaScript, and CSS may need migration planning. [4]

### Map each source to the correct outcome

For each old URL, record:

- Old URL.
- Intended new URL, if one exists.
- Resource relationship and reason for the mapping.
- Expected response (301, 308, 404, 410, or other appropriate status).
- Whether query parameters should be preserved, transformed, or discarded.
- Content owner or responsible system.
- Validation status and observed final response.

A simple example:

| Old URL | New URL / outcome | Expected behavior |
|---|---|---|
| https://example.com/guide-old/ | https://example.com/guides/new-guide/ | 301 |
| http://www.example.com/product/42 | https://example.com/products/42/ | 301 |
| https://example.com/retired-item/ | No replacement | 410 or 404 |
| https://example.com/temporary-outage/ | Temporary service page | 302 or 307 |

These are illustrative mappings. The actual destination must be selected from the content relationship and user intent, not from URL similarity alone.

### Do not force every old URL to the homepage

Redirecting many unrelated old URLs to one generic page can confuse users and may be treated as a soft 404. Redirect to a consolidated destination only when that destination genuinely replaces or incorporates the old content. Otherwise, return an accurate not-found or gone response. [4]

## 9. Migration preparation and launch

A disciplined migration separates preparation, cutover, and post-launch verification.

### Before launch

1. **Define scope:** identify every hostname, protocol, URL pattern, template, asset type, and environment affected.
2. **Inventory URLs:** combine sitemap, CMS, logs, analytics, internal links, and backlink evidence.
3. **Prepare the destination:** deploy the new site and test its content, routes, assets, response behavior, and capacity.
4. **Create the mapping:** assign every important old URL a destination or an accurate removal response.
5. **Implement redirects:** configure permanent server-side redirects for URLs that have permanently moved.
6. **Update publisher signals:** new pages should use the intended canonical URLs; update internal links, hreflang annotations where used, structured-data URLs, and sitemap entries.
7. **Review access and indexing controls:** remove temporary robots.txt blocks and noindex directives when the new site is ready for public launch.
8. **Verify Search Console properties:** confirm access to relevant old and new properties and preserve verification methods.
9. **Test at scale:** check representative templates and automate redirect tests across the mapping.
10. **Prepare rollback:** document how to restore the previous routing or infrastructure if the new environment fails.

Google recommends preparing and testing the new site, creating a URL mapping, implementing redirects, updating canonical annotations and internal links, and preparing a sitemap of new URLs. [4]

### During launch

- Activate the intended routing and redirect configuration.
- Verify DNS, TLS certificates, host routing, CDN/origin behavior, and application health.
- Confirm that new URLs return expected responses and old URLs resolve to the mapped destinations.
- Remove development-only crawl blocks and noindex directives.
- Submit the new sitemap where appropriate.
- For a domain or subdomain move, use Search Console's Change of Address process where applicable; it is not required for ordinary HTTP-to-HTTPS changes, www/non-www normalization, or path changes on the same domain. [4]
- Monitor user traffic, crawler requests, error rates, and server capacity.

### After launch

- Crawl old URLs and confirm each mapping.
- Crawl new URLs and confirm expected final responses.
- Check for unexpected 404/410, 5xx, redirect loops, chains, and soft 404s.
- Verify canonical declarations and sitemap URLs use the new preferred URLs.
- Update internal links to point directly to new destinations.
- Monitor server logs, Search Console reports, analytics, and external referral traffic.
- Keep old-domain infrastructure and redirects active for as long as required.

Google recommends keeping migration redirects in place for as long as possible and generally at least one year for a URL move. From a user perspective, keeping them indefinitely may be beneficial where feasible. This is Google migration guidance, not an HTTP protocol requirement. [4]

## 10. Domain, protocol, path, and hosting migrations are not identical

| Migration type | User-visible URL changes? | Main technical work | Search Console Change of Address |
|---|---|---|---|
| HTTP → HTTPS | Yes | TLS, permanent redirects, canonical/sitemap/internal-link updates, mixed-content checks. | Not required. |
| www ↔ non-www | Yes | Host normalization, redirects, canonical consistency, DNS/host configuration. | Not required. |
| Path restructuring | Yes | Old-to-new URL mapping, redirects, internal-link and sitemap updates. | Not required. |
| Domain or subdomain change | Yes | New-domain readiness, URL mapping, redirects, property verification, monitoring. | Applicable for eligible domain/subdomain moves. |
| Hosting provider or CDN change with same URLs | No | Copy/test environment, DNS or traffic cutover, access and capacity monitoring. | Not a URL-move requirement. |
| CMS migration with unchanged URLs | No, if routes remain stable | Preserve routes, status behavior, content, metadata, rendering, and infrastructure. | Not required solely for a hosting/CMS change. |

Google distinguishes URL-changing site moves from hosting changes that preserve user-visible URLs. For a hosting move, DNS propagation, origin availability, firewall rules, and server capacity are key operational concerns. [4][5]

## 11. Monitor migration outcomes without over-interpreting signals

A migration is not complete merely because the homepage loads or a redirect test passes for one URL. Monitor several evidence layers.

### HTTP and infrastructure evidence

- Status-code distribution by host and path.
- Redirect source, target, hop count, and final response.
- 4xx and 5xx rates compared with baseline.
- DNS resolution and TLS certificate validity.
- CDN cache behavior and origin response health.
- Application logs, upstream timeouts, and rate-limiting events.
- Traffic split between old and new infrastructure.

### Search-engine evidence

For Google, review:

- Crawl activity and server response patterns.
- Search Console Page indexing and URL Inspection results.
- Old and new sitemap processing.
- Indexed URL trends on old and new properties.
- Canonical selection for representative migrated URLs.
- Search impressions, clicks, and landing-page changes.

A temporary change in crawling, indexing, or search visibility can occur while URLs are recrawled and processed. Google notes that the move is handled per URL and that timing depends on factors including site size and server capacity. Do not interpret every short-term fluctuation as a permanent migration failure, but do investigate persistent errors and missing destination URLs. [4]

### Define migration success criteria in advance

Examples of useful criteria include:

- All high-priority old URLs have a valid mapped outcome.
- No unexpected redirect loops or unbounded chains remain.
- New canonical URLs return the expected response.
- Internal links and sitemaps use the new URL set.
- Important templates and assets are available.
- 4xx and 5xx rates remain within defined operational tolerances.
- Search Console and analytics trends are monitored against a documented baseline.

A successful technical cutover does not guarantee unchanged rankings, immediate indexing, or identical traffic. Those outcomes depend on search-engine processing, user behavior, content equivalence, and other factors outside the redirect configuration.

## 12. Common migration and redirect failure patterns

- **Wrong redirect type:** permanent and temporary semantics do not match the actual resource move.
- **Redirect to irrelevant destination:** many removed pages are sent to the homepage or a generic category.
- **Redirect chains:** old URLs pass through several intermediate destinations.
- **Redirect loops:** conflicting rules send requests back to previously visited URLs.
- **Incomplete mapping:** important legacy URLs, assets, parameters, or backlinks are omitted.
- **Path loss:** a domain-wide rule sends every source URL to the same destination instead of preserving or mapping paths.
- **Query-string corruption:** parameters required by the destination are lost, duplicated, or transformed incorrectly.
- **Canonical conflict:** the redirect destination emits a canonical pointing to an old or unrelated URL.
- **Old sitemap retained as the only sitemap:** the new URL inventory is not submitted or updated.
- **Development restrictions left active:** robots.txt blocks or noindex directives prevent the new site from being processed.
- **Incorrect error handling:** missing routes return 200, or valid routes return 404/410.
- **Capacity failure:** the new origin, CDN, firewall, or rate limiter cannot handle normal users and increased crawler activity.
- **Premature shutdown:** the old host or redirect layer is removed before users and crawlers can reliably reach the new destination.

## 13. Practical HTTP and migration QA checklist

### Response correctness

- [ ] Each tested URL returns the intended status.
- [ ] Redirect responses contain a correct Location target.
- [ ] Final destinations return the expected response and meaningful content.
- [ ] Missing and permanently removed resources return accurate 404/410 responses.
- [ ] Temporary maintenance and overload states use appropriate 503 behavior where applicable.
- [ ] Response headers and body do not contradict one another.

### Redirect integrity

- [ ] Permanent and temporary status codes reflect the intended permanence.
- [ ] Redirects preserve the correct path and required parameters.
- [ ] No self-redirects, loops, or unnecessary chains remain.
- [ ] No unrelated source URLs are redirected to generic destinations.
- [ ] Non-GET request behavior is tested where relevant.
- [ ] Redirect rules do not create open redirects or unintended host changes.

### Migration consistency

- [ ] The old-to-new URL map covers priority URLs and relevant assets.
- [ ] New pages use the intended canonical URLs.
- [ ] Internal links point directly to new URLs.
- [ ] Sitemaps contain the new preferred URL set.
- [ ] robots.txt and noindex controls reflect the launch state.
- [ ] Structured data and hreflang annotations are updated where applicable.
- [ ] Search Console properties and verification are ready.
- [ ] DNS, TLS, CDN, origin, and server capacity are validated.

### Monitoring and closure

- [ ] Representative old and new URLs are re-tested after production launch.
- [ ] 4xx, 5xx, redirect, and soft-404 trends are monitored.
- [ ] Server logs and analytics are compared with the pre-migration baseline.
- [ ] Search Console reports are reviewed without treating them as instant or complete proof.
- [ ] Redirects remain active for the planned retention period.
- [ ] Unresolved exceptions, owners, and rollback conditions are documented.

# 10.13 — Technical SEO Auditing & Quality Assurance

[← Domain 10 — Technical SEO](README.md)

A technical SEO audit is a scoped assessment of website implementation and delivery against explicit technical criteria. Quality assurance (QA) extends assessment into release checks, regression prevention, and verification that a remediation works in the environment that matters. An audit is only as reliable as its scope, sample, evidence, and method.

## 1. Define the audit scope

Before running tools, specify:

- Domain, host, protocol, and environments included.
- URL inventory and how it was generated.
- Page templates and content types represented.
- Device, browser, and crawler contexts.
- Date/time window and geographic context where relevant.
- Crawl configuration, rendering settings, and access credentials.
- Sampling method, exclusions, and known blind spots.
- Technical criteria and the expected behavior for each.

A crawl of a subset is not a full-site audit. A template test does not prove every route uses the same markup or response behavior. A staging result does not establish production behavior.

## 2. Build an evidence-led audit

Depending on the site and risk, audit dimensions may include:

- Availability, DNS/TLS, HTTP status codes, and redirect behavior.
- URL architecture, duplicate variants, and parameter handling.
- robots.txt, robots meta directives, and X-Robots-Tag.
- Sitemap validity and consistency with canonical/indexable URLs.
- Canonical declarations and indexability controls.
- Rendering, mobile parity, resource access, and JavaScript errors.
- Performance and Core Web Vitals.
- Structured-data syntax, visible-content consistency, and feature policies.
- Server logs, crawl diagnostics, and monitoring coverage.

Choose checks based on architecture and risk. Do not treat a vendor tool's default checklist or severity score as a universal audit standard.

## 3. Record and prioritize findings

For every finding, record:

- Affected URL(s), template(s), and environment.
- Expected behavior and observed behavior.
- Reproduction steps and evidence (request/response, HTML, logs, screenshots, reports).
- Whether the issue is confirmed, suspected, or merely a tool warning.
- Severity, confidence, reach, and potential user/search-system impact.
- Root-cause hypothesis and what would confirm it.
- Responsible owner, remediation plan, and verification method.

Prioritize based on reach, severity, confidence, user impact, and operational risk—not only a third-party tool label or aggregate score. A single high-impact defect affecting a core template may matter more than dozens of low-confidence warnings.

## 4. Turn findings into quality controls

Where practical, convert repeatable defects into automated or manual release checks:

- Assert expected status codes and redirect destinations.
- Detect redirect chains and loops.
- Check robots rules and sitemap validity.
- Verify canonical consistency across templates.
- Compare critical rendered content with expected output.
- Validate structured data and required properties.
- Test mobile layout and key interactions.
- Track performance budgets and field metrics.
- Check logs and alerts after deployment.

A test should specify its input, environment, expected result, tolerance, and failure handling. Tests need maintenance when routes, templates, or platform behavior change.

## 5. Verify remediation

Re-test the original affected URLs and representative neighboring templates. Confirm the production response after deployment, not only the local code or staging build. Compare before/after evidence using the same scope and method where possible.

A regression test verifies a defined condition in a defined environment. It does not prove every URL is correct, establish how a search engine will process a page, or guarantee indexing or ranking.

## 6. Reporting

A useful audit report includes executive findings, scope, method, sample, limitations, prioritized issues, evidence, ownership, remediation status, and unresolved risks. Distinguish completed fixes from fixes awaiting deployment or verification. Include a clear audit date because site behavior and search-engine documentation change.

## 7. Accessibility is a related but separate assessment

Accessibility affects whether people with disabilities can perceive, understand, navigate, and interact with a site. WCAG provides testable success criteria for accessibility conformance; a technical SEO crawl or Lighthouse score is not a WCAG conformance audit. If accessibility is in scope, define the applicable WCAG version/level, sample, assistive technology, manual tests, and evaluation method separately. [1]

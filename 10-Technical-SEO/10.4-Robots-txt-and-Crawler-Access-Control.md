# 10.4 — Robots.txt & Crawler Access Control

[← Domain 10 — Technical SEO](README.md)

The Robots Exclusion Protocol (REP) defines a mechanism through which service owners can communicate crawler access preferences. A robots.txt file is a conventionally located text resource that compliant crawlers may consult before requesting URLs. It is not authentication, authorization, or a security boundary. [1]

## 1. File location and scope

A robots.txt file applies to the origin (scheme, host, and port) from which it is served and is conventionally published at the root path, for example `https://example.com/robots.txt`. A file on one host does not automatically govern another host or protocol origin. [1][2]

A file contains user-agent groups and rules such as `Disallow` and `Allow`. The REP defines the general protocol; search engines may document implementation details and extensions. Do not assume that all crawlers interpret every rule identically. [1][2]

Illustrative example:

```text
User-agent: *
Disallow: /private-preview/
Allow: /private-preview/public-example.html

Sitemap: https://example.com/sitemap.xml
```

The example is not a security control. If a URL must remain confidential, require authentication or authorization at the server/application layer.

## 2. Matching and rule interpretation

REP matching is based on URL paths and defined matching rules, not on arbitrary natural-language intent. Rule order, group selection, path matching, percent-encoding, and the treatment of equivalent rules must be tested against the relevant specification and crawler documentation. Google documents its own interpretation, including behavior for multiple groups and matching rules. [1][2]

The standard also defines how crawlers should handle robots.txt retrieval failures and caching. A site's operational design should therefore monitor the robots.txt response itself: an unavailable or unexpectedly redirected file can change crawler behavior. Google publishes specific handling for HTTP response classes and redirects; those details are Google-specific. [2]

## 3. Robots.txt is not noindex

Robots.txt controls whether a compliant crawler may request matching URLs. It does not reliably prevent a URL from appearing in a search index: a search engine may know the URL from links or other sources even when it cannot fetch the page. To communicate an indexing restriction, a crawler generally needs to fetch the resource and see an applicable robots meta directive or `X-Robots-Tag` response header. If robots.txt blocks the fetch, the crawler may not see that directive. [3][4]

Use the controls according to their purpose:

- **robots.txt:** manage crawler requests to paths or resources.
- **robots meta / X-Robots-Tag:** communicate indexing or serving directives in a fetched response.
- **Authentication/authorization:** restrict access to protected resources.
- **Canonicalization:** indicate a preferred representative among duplicate or similar URLs.

These mechanisms solve different problems. [3][4]

## 4. Deployment and validation

Before publishing a change:

1. Identify the exact origin and crawler groups affected.
2. Test representative allowed and disallowed paths, including nested paths and exceptions.
3. Check whether important CSS, JavaScript, image, or API resources would become inaccessible.
4. Confirm that intended noindex directives remain fetchable.
5. Validate syntax and inspect the file from the public production origin.
6. Check crawler-specific tools and logs after deployment.
7. Preserve a known-good version and rollback procedure.

Test staging and production separately. A robots.txt file on a staging host does not control the production host, and a production rule copied into staging may have unintended effects.

## 5. Common errors

- Treating robots.txt as a password or confidentiality mechanism.
- Blocking a page while expecting its noindex directive to be read.
- Applying rules to the wrong hostname or protocol.
- Blocking resources required for rendering or page interpretation.
- Assuming a non-standard directive such as `crawl-delay` is supported by every crawler.
- Publishing malformed or overly broad disallow rules without testing affected paths.
- Forgetting that robots.txt itself must be reachable and served with an expected response.

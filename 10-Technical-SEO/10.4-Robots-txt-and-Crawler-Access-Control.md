# 10.4 — Robots.txt & Crawler Access Control

[← Domain 10 — Technical SEO](README.md)

The Robots Exclusion Protocol (REP) is a convention through which a service publishes rules that compliant automated crawlers can use to decide which URL paths they may request. On the web, those rules are commonly exposed in a plain-text file named `robots.txt` at the root of an origin.

Robots.txt is a crawler-coordination mechanism, not an access-control system in the security sense. It does not authenticate clients, authorize access to private data, or guarantee that a URL will be excluded from a search index. Its purpose, scope, and limitations must be understood before rules are deployed. [1][2]

## 1. What robots.txt controls—and what it does not

A robots.txt file communicates crawler access preferences for matching paths. A compliant crawler is expected to consult and follow applicable rules, but the protocol cannot technically force every automated client to cooperate.

Use the mechanism for a narrow set of purposes:

- Reduce unnecessary crawler requests to selected URL spaces.
- Prevent compliant crawlers from fetching paths that do not need to be crawled.
- Allow or disallow crawler access to selected public resources.
- Publish sitemap locations for crawlers that support the Sitemap record.

Do not use robots.txt to:

- Protect confidential files, account pages, customer records, staging systems, or administrative interfaces.
- Guarantee that a URL will not appear in search results.
- Replace authentication, authorization, firewall policy, or application-level access checks.
- Communicate a page-level `noindex` directive.
- Guarantee crawl scheduling, ranking, deindexing, or removal.

The distinction between crawling and indexing is fundamental. If a crawler is blocked from fetching a page, it cannot read a page-level robots meta directive or an `X-Robots-Tag` header on that response. A URL may still be known from external links or other references and may appear in an index without its content being fetched. If a resource must be private, enforce access at the server or application layer. If it is public but must not be indexed, use an applicable indexing directive that the crawler can fetch and read, or remove/protect the resource as appropriate. [1][2][3]

## 2. File location, origin, and scope

The conventional robots.txt URL is:

```text
https://www.example.com/robots.txt
```

The file must be located at the top-level path of the relevant service, not in a subdirectory such as `/docs/robots.txt`. It is associated with the origin context: protocol, host, and port. Consequently:

- `https://example.com/robots.txt` does not govern `https://www.example.com/`.
- An HTTPS robots.txt does not automatically govern the HTTP version.
- A file on the default HTTPS port does not govern a different non-standard port.
- Each subdomain that needs distinct rules requires its own applicable robots.txt resource.
- A robots.txt file on an IP-address host does not automatically apply to a domain name hosted on that IP address.

These scope rules are specified by REP and reflected in Google's implementation documentation. Inventory every canonical host, alternate host, protocol, and non-standard port before assuming one file covers the whole website. [1][2]

The filename is lowercase `robots.txt`. For Google, the file must be a UTF-8 plain-text resource. Avoid word processors that may add formatting, unexpected encodings, or typographic characters. Publish it as a directly accessible resource from the intended origin. [2][4]

## 3. File structure and core records

A robots.txt file consists of one or more groups. A group begins with one or more `User-agent` records and is followed by rules that apply to the identified crawler product tokens.

The main records are:

| Record | Purpose |
|---|---|
| `User-agent` | Identifies the crawler or crawler family to which the following group applies. |
| `Disallow` | Defines a path pattern that the designated crawler must not request when the rule matches. |
| `Allow` | Defines a path pattern that the designated crawler may request; useful for exceptions to broader disallow rules. |
| `Sitemap` | Publishes an absolute sitemap URL for crawlers that support this record. It is an extension commonly supported by major search engines, not a core REP access rule. |

A minimal example:

```text
User-agent: *
Disallow:

Sitemap: https://www.example.com/sitemap.xml
```

An empty `Disallow` value does not block any path. It is functionally equivalent to allowing the crawler unrestricted access under that group. A missing robots.txt file also does not create a disallow policy for Google; the file's retrieval outcome must be interpreted separately from its contents. [2][4]

### Group boundaries matter

Consecutive `User-agent` lines can identify multiple crawlers that share the rules which follow. A new group begins when another group of rules is introduced. Keep each intended policy readable and explicit; do not insert unrelated records in ways that make group boundaries ambiguous.

For Google, a crawler selects the most specific matching user-agent group. A specific Googlebot group is not combined with the wildcard `*` group. If multiple groups specifically match the same Google crawler, Google documents that their rules are combined. These are Google-specific interpretation details; other crawlers may apply their own documented behavior. [2]

Example:

```text
User-agent: *
Disallow: /internal-preview/

User-agent: Googlebot
Allow: /internal-preview/public/
```

Under Google's documented group selection, Googlebot uses its specific group rather than combining it with the wildcard group. Do not assume the wildcard disallow automatically remains in force for Googlebot in this example. If a shared restriction is required, repeat it in the specific group or redesign the groups so the intended policy is unambiguous. [2]

## 4. Path matching, specificity, and wildcards

Robots rules match URL paths according to the protocol and crawler implementation, not according to a human interpretation of page meaning.

Under RFC 9309, matching begins at the start of the URI path. Matching is case-sensitive as a recommendation, and the most specific matching rule—measured by the number of matching octets—takes precedence. When an `Allow` and `Disallow` rule are equivalent, the RFC says the `Allow` rule should be preferred. Google documents its own rule precedence and uses the least restrictive rule when conflicting matching rules have equivalent specificity. [1][2]

Google and other major search engines support two commonly used wildcard characters:

- `*` matches zero or more characters.
- `$` anchors a match to the end of the URL.

Examples:

```text
User-agent: *
Disallow: /account/
Allow: /account/help/

Disallow: /*.pdf$
```

Interpretation for crawlers that support these matching conventions:

- `/account/` blocks paths beneath that directory.
- `/account/help/` is a more specific exception.
- `/*.pdf$` matches paths ending in `.pdf`; a URL with a query string after the extension may not match the end-anchored pattern.

A missing trailing slash can change the affected URL set. For example, `Disallow: /fish` can match `/fish`, `/fish.html`, and `/fishheads`, while `Disallow: /fish/` targets the directory-style path and its descendants. Matching is case-sensitive in Google's documented implementation: `/Private/` and `/private/` are not interchangeable. [2]

### Query strings and URL encoding

Google's path matching includes the URL path and may include query-string characters in matching behavior. Rules that target parameters therefore require representative testing, especially where parameter order, encoding, or multiple values create variants. RFC 9309 describes percent-encoding behavior for non-ASCII and reserved characters; do not assume visually identical encoded and unencoded strings always match identically. [1][2]

Avoid deploying a broad parameter rule based on one observed URL without testing:
- Parameter present and absent.
- Different parameter order.
- Encoded and unencoded values.
- Uppercase and lowercase path variants.
- Trailing slash and file-extension variants.
- URLs with additional query parameters.

## 5. Crawler-specific rules and directive support

The `User-agent` record addresses a crawler product token, not a guaranteed identity or an authenticated client. A user-agent string can be imitated; robots.txt itself is not proof that a request came from a particular search engine.

Google documents support for `User-agent`, `Allow`, `Disallow`, and `Sitemap` records. It does not support the non-standard `Crawl-delay` directive. Other crawlers may support different extensions or interpret the same file differently. A directive that works for one bot should not be assumed portable to all bots. [2][5]

Use crawler-specific groups only when there is a real operational reason. More groups create more policy combinations to review and test. For Google crawler identity, verify requests using Google's published IP ranges and reverse/forward DNS procedures rather than trusting a user-agent string alone. Detailed request attribution belongs to 10.12. [6]

## 6. robots.txt retrieval outcomes and operational behavior

A robots.txt policy is useful only if the crawler can retrieve and parse the file. HTTP status, redirects, network availability, and caching can affect the rules a crawler applies.

RFC 9309 distinguishes several outcomes:

| Retrieval outcome | RFC 9309 behavior |
|---|---|
| Successful retrieval | The crawler must follow parseable rules. |
| Redirect | Crawlers should follow at least five consecutive redirects; if the file is reached within that limit, its rules apply in the context of the initial authority. |
| Unavailable response (for example, HTTP 4xx) | The crawler may access resources on the server. |
| Unreachable due to server/network errors (for example, HTTP 5xx) | The crawler must assume complete disallow while the file is unreachable, subject to the RFC's long-duration provisions. |
| Parsing errors | The crawler must try to parse each line and use the rules it can parse. |

These are protocol-level requirements and recommendations, not a promise that every crawler implements every case identically. [1]

Google publishes more detailed behavior for its own crawlers. For example, Google generally treats a robots.txt response in the 4xx class (except 429) as if no robots.txt file exists, while server/network failures can cause Google to temporarily stop crawling the host and continue using a previously fetched version where available. Google may cache robots.txt for up to 24 hours in normal circumstances and longer when refreshing is not possible. Consult the current Google specification for exact status handling rather than extrapolating from the RFC or another crawler. [2]

A robots.txt deployment should therefore be monitored like other production dependencies. An accidental 5xx from the robots endpoint can have a very different effect from a valid file containing an intentional `Disallow` rule.

## 7. File size, encoding, and caching

RFC 9309 requires crawlers to support a parsing limit of at least 500 KiB; this is a minimum crawler capability, not a guarantee that every crawler processes arbitrarily large files. Google enforces a 500 KiB robots.txt size limit and ignores content after that limit. A file that grows beyond the supported size can silently lose rules near its end. [1][2]

Operational safeguards include:

- Keep the file in UTF-8 plain text.
- Use conventional line endings and avoid a byte-order mark.
- Keep rules concise and consolidate repeated patterns where safe.
- Check the actual response body and byte size served from production.
- Confirm that CDN, proxy, and origin layers return the same intended file.
- Monitor caching headers and allow time for crawler caches to refresh after a change.

Do not assume that editing the file immediately changes every crawler's cached policy. Google normally refreshes its robots.txt cache frequently, but its cache may persist longer during retrieval failures. A Search Console recrawl request is available for certain critical Google-specific cases; it does not guarantee immediate recrawling of URLs that become allowed. [1][2][7]

## 8. robots.txt and adjacent technical controls

The controls below solve different problems and should not be treated as interchangeable.

| Requirement | Appropriate mechanism | Key limitation |
|---|---|---|
| Manage which paths compliant crawlers may request | robots.txt | Does not enforce confidentiality or guarantee deindexing. |
| Prevent a fetched page from being indexed | Robots meta `noindex` or `X-Robots-Tag` | The crawler must be able to fetch the response and read the directive. |
| Restrict access to private content | Authentication and authorization | Must be enforced by the application/server, not crawler convention. |
| Consolidate duplicate URL versions | Canonical signals and/or redirects | Search engines make their own canonical-selection decisions. |
| Help crawlers discover preferred URLs | Internal links and XML sitemaps | Discovery hints do not override robots rules or guarantee indexing. |
| Remove content that should no longer be publicly served | Remove the resource or return an accurate HTTP status; use supported removal tools where appropriate | A robots disallow rule does not remove the underlying resource or reliably remove its URL from an index. |

If a page must be deindexed, do not block it in robots.txt before the crawler has processed the intended `noindex` directive. If the page is confidential, do not publish it and hope a crawler obeys a disallow rule. Use proper authorization. Domain 10.6 owns indexability and canonicalization; 10.7 owns HTTP status and redirect semantics; 10.5 owns sitemap construction and submission. [3][4][8]

## 9. Deployment and validation workflow

Treat robots.txt as production configuration. A small text change can affect an entire directory, host, or crawler class.

1. **Define the objective.** State whether the goal is request management, crawl-space reduction, resource access, or something else. If the goal is privacy or deindexing, choose the correct control instead.
2. **Identify scope.** List affected protocol, hostname, port, crawler groups, URL patterns, and environments.
3. **Inventory affected URLs.** Use representative examples from logs, site routes, sitemaps, and generated URL patterns.
4. **Write the smallest rule set.** Prefer narrow path patterns over broad rules. Document why each restriction exists.
5. **Evaluate matching.** Test positive and negative cases, including exceptions, nested paths, case, query strings, wildcard anchors, and encoded characters.
6. **Review resource dependencies.** Confirm that CSS, JavaScript, images, and API endpoints needed to understand important pages are not unintentionally blocked.
7. **Validate the served file.** Fetch the exact production URL and inspect status, redirects, content type, encoding, body, and byte size.
8. **Use crawler-specific validation.** Check the applicable search-engine report or a compatible local parser; remember that a parser's result is scoped to that implementation.
9. **Deploy with rollback.** Preserve the prior version and a fast rollback path. Review changes as code/configuration, not as an informal content edit.
10. **Monitor after release.** Check robots fetch status, parse warnings/errors, crawl patterns, and affected URL behavior. Request a recrawl through Search Console only when the documented circumstances justify it.

Google's robots.txt report can show files found for a property's hosts, latest fetch status, fetch time, file size, and parsing issues. Its coverage is limited to the report's supported Search Console property scope and listed hosts; it is not a universal robots.txt validator for every crawler. [7]

## 10. Common failure patterns

- **Blocking the whole site:** a root-level `Disallow: /` can prevent compliant crawlers from fetching every path on the relevant origin.
- **Wrong host assumption:** a robots.txt on the apex domain does not automatically control `www`, a shop subdomain, or a separate protocol.
- **Accidental wildcard breadth:** a pattern such as `/private` may also match paths such as `/private-preview`.
- **Conflicting rules:** overlapping allow/disallow patterns may resolve differently across crawler implementations.
- **Broken group design:** assuming wildcard and specific Google groups are merged can expose or block paths unexpectedly.
- **Blocking render dependencies:** disallowing required scripts or styles can impair crawler rendering or page interpretation.
- **Using robots.txt for deindexing:** blocked URLs can remain known and potentially appear without a snippet.
- **Using robots.txt for security:** disallowing a path can advertise its existence while leaving it publicly retrievable.
- **Unsupported directives:** `Crawl-delay` is not supported by Google; do not rely on it for Googlebot rate control.
- **Oversized or malformed files:** rules after the parser limit or invalid lines may not have the intended effect.
- **Robots endpoint outage:** a 5xx or network failure can cause crawler behavior very different from a successfully fetched file with no restrictions.

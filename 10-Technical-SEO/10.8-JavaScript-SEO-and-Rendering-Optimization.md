# 10.8 — JavaScript SEO & Rendering Optimization

[← Domain 10 — Technical SEO](README.md)

JavaScript SEO examines whether important page content, metadata, links, and resources are available in the representations that browsers and search crawlers can process. It is a delivery and rendering problem, not a blanket argument for or against JavaScript frameworks.

## 1. Rendering models

Common delivery approaches include:

- **Server-side rendering (SSR):** the server generates HTML for a request. The browser can receive meaningful markup before client-side application code completes.
- **Static generation:** HTML is generated ahead of the request and served as a static representation, often with client-side enhancement.
- **Client-side rendering (CSR):** the browser downloads application code and constructs or updates the page after JavaScript executes.
- **Hybrid rendering:** different routes or components use combinations of server, static, and client rendering.

These labels describe common architectures, not guarantees about output quality. The web.dev rendering guide distinguishes server-side rendering, client-side rendering, static rendering, and hydration, and discusses their performance and implementation trade-offs. [3] A server-rendered page can still return incomplete or incorrect HTML; a client-rendered page can work well if the relevant crawler supports the required processing. Google documents a crawling and rendering process for Google Search that includes JavaScript execution; other clients may not share the same capabilities or timing. [1]

## 2. What must be available

For each important route, inspect whether the response and rendered page expose:

- Primary textual content and meaningful headings.
- A useful title and other supported metadata.
- Robots directives and canonical declarations.
- Crawlable links with real `href` destinations.
- Images and other resources required to understand the page.
- Correct status and error behavior for valid, missing, and redirected routes.

Google recommends making links crawlable and ensuring important content is available in rendered HTML. Do not assume that a crawler can trigger every user interaction or execute arbitrary application flows. [1][2]

## 3. Common rendering failure modes

- **Hydration mismatch:** server HTML and client-rendered state diverge, causing content or layout changes.
- **JavaScript exception:** runtime errors prevent required components from rendering.
- **API dependency failure:** primary content is fetched from an endpoint that fails, is blocked, or requires unavailable credentials.
- **Resource blocking:** CSS, JavaScript, or API resources needed for rendering cannot be fetched.
- **Interaction-only content:** important information appears only after a click, hover, or other action that the crawler does not perform.
- **Client-side route failure:** navigation works after app initialization, but direct requests return an error, empty shell, or incorrect status.
- **Delayed or unstable rendering:** content appears too late or changes repeatedly, making inspection unreliable.

The correct diagnosis compares network responses, initial HTML, rendered DOM, browser console output, and crawler-facing inspection tools. A screenshot alone does not reveal response codes, canonical tags, robots directives, or link destinations.

## 4. A repeatable inspection workflow

1. Fetch the URL directly and record status, headers, and initial HTML.
2. Render it in a current browser and inspect the final DOM.
3. Compare primary content, title, metadata, canonical, robots directives, and links.
4. Inspect network requests for failed scripts, stylesheets, APIs, fonts, and images.
5. Check console errors and route behavior, including direct loading and refresh.
6. Test representative templates, query states, and mobile viewports.
7. Use the relevant search-engine URL inspection tool for provider-specific rendering evidence.
8. Re-test after deployment; a local development build is not proof of production behavior.

Server rendering, static generation, or pre-rendering can improve initial HTML availability and reduce dependence on client execution, but the appropriate choice depends on application requirements, freshness, personalization, infrastructure, and measured performance. Avoid claiming one rendering architecture is universally best.

## 5. Ownership boundaries

Domain 07 owns authored page-level HTML elements and content semantics. Domain 10 owns delivery and rendering conditions. Domain 09 owns conceptual semantic models. A rendered page can faithfully expose a semantic model without taking over the model's conceptual ownership.

# 10.8 — JavaScript SEO & Rendering Optimization

[← Domain 10 — Technical SEO](README.md)

JavaScript SEO examines whether important page content, metadata, navigable links, and required resources are delivered in forms that browsers and search crawlers can retrieve and process. Rendering optimization concerns where and when an application turns data, templates, and code into the document users and automated systems consume.

JavaScript is a normal part of the modern web platform. Its presence does not automatically prevent search discovery, and choosing a server-rendered framework does not automatically make a page technically sound. The relevant questions are whether each public URL returns the correct response, whether its meaningful content can be rendered reliably, whether its links and signals remain coherent, and whether the delivery architecture meets user and operational requirements. [1][2]

This topic focuses on publisher-side JavaScript delivery, rendering architectures, crawler-facing output, and diagnostics. It does not own search-engine rendering internals (Domain 02), authored on-page content (Domain 07), semantic models (Domain 09), canonicalization policy (10.6), HTTP and redirect semantics (10.7), mobile implementation (10.9), Core Web Vitals methodology (10.10), structured-data implementation policy (10.11), or general audit methodology (10.13).

## 1. Rendering is a delivery process, not a framework label

A browser receives an HTTP response, parses the document, discovers resources, constructs a document object model (DOM), applies styles, and may execute JavaScript that changes the document and its behavior. A search crawler may perform some or all of these operations according to its own capabilities and policies.

For JavaScript-dependent pages, distinguish:

- **Initial response HTML:** markup delivered in the original HTTP response before client-side application code changes the document.
- **Rendered DOM:** document structure after the browser or rendering engine has parsed the response and executed applicable scripts.
- **Visual rendering:** browser layout and paint output, which is what a user sees.
- **Interactive state:** application state after scripts, event handlers, data requests, and user actions have been processed.

These representations overlap, but they are not interchangeable. A page can look complete in a screenshot while its initial response contains an empty application shell. A page can contain the expected text in its DOM while an important link lacks a real destination. A visually complete server-rendered page can still have broken hydration or inaccessible controls.

For search-oriented diagnosis, inspect the actual response and rendered DOM rather than inferring technical correctness from the visual result alone. Google documents a crawl, render, and indexing process for Google Search, and provides tools for inspecting resources, JavaScript output, exceptions, and rendered HTML. Other crawlers and clients may use different rendering capabilities. [1][2]

## 2. Rendering architectures and their trade-offs

Rendering architecture determines where page HTML is produced and how much work must happen in the browser. These are implementation patterns rather than search-engine eligibility categories.

### Server-side rendering (SSR)

With server-side rendering, the application generates HTML on the server in response to a request. The browser receives a document containing page markup rather than having to build the entire initial view from an empty shell.

Potential advantages include meaningful content and links in the first response, earlier display of page content, less initial client-side rendering work, and compatibility with clients that do not execute JavaScript.

Trade-offs include server work on the request path, potentially higher time to first byte (TTFB), compute and memory costs, complex caching, divergence between server and client implementations, and the possibility that hydration still delays interactivity. Personalized or highly dynamic pages can also be difficult to cache safely.

SSR is a delivery choice, not a guarantee of fast performance or complete content. Its actual outcome depends on server execution, caching, HTML size, data dependencies, and the work the browser must still perform. [3]

### Static rendering and static site generation

Static rendering generates HTML ahead of the request, commonly during a build or content-publication process. Generated documents can be served from a web server or content delivery network (CDN).

Potential advantages include predictable initial HTML, efficient caching and distribution, and content availability without requiring the browser to execute the application first.

Trade-offs include build coverage for every required route or URL variant, content freshness and regeneration requirements, and difficulty handling very large or unpredictable URL spaces. Personalization and request-specific data may require another delivery path.

Static rendering should not be confused with generating an empty shell that later boots a client application. A statically rendered page can provide useful content and navigation without requiring the full client application to initialize. [3]

### Client-side rendering (CSR)

With client-side rendering, the browser executes JavaScript to construct or update the page. Some applications initially return a minimal application shell and retrieve page data from APIs after the application starts.

CSR can support rich interactive experiences, client-side navigation, and reusable application state. However, meaningful content may depend on scripts and API requests completing; large bundles can delay rendering and interactivity; runtime exceptions or blocked resources can leave the page incomplete; and crawlers without compatible JavaScript execution may not see generated content.

Direct URL requests, refreshes, and client-side navigation can also behave differently if server routing is incomplete. The risk is not the label itself; it is making essential content and navigation depend on execution paths that are unreliable or unavailable to the relevant client. [1][3]

### Hybrid and incremental rendering

A hybrid architecture uses more than one rendering approach. A publisher may statically generate editorial pages, server-render frequently changing product pages, and use client-side rendering for authenticated application screens.

Rendering can be selected at route or component level. This avoids forcing every page into one architecture when content freshness, personalization, traffic, and interactivity requirements differ.

The decision should consider how often content changes, whether request-specific personalization is required, how much interactivity is essential, whether meaningful initial HTML can be generated, infrastructure and caching constraints, and which crawlers and browsers must process the output.

Hybrid rendering introduces coordination costs. Route rules, cache behavior, metadata, status handling, and content parity must remain consistent across delivery paths. [3]

### Prerendering, hydration, and rehydration

These terms describe different parts of a rendering lifecycle:

- **Prerendering:** executing an application ahead of time to produce an initial HTML representation. This differs from browser speculation for a future navigation.
- **Hydration:** running client-side scripts to attach application behavior and state to HTML that was already rendered, commonly on the server.
- **Rehydration:** often used informally as a synonym for hydration, but can describe further client-side updates after the initial takeover.
- **Streaming SSR:** sending parts of a server-generated response as they become available rather than waiting for the entire document to be assembled.

Hydration can combine early content availability with client-side interactivity. However, a page may look ready before event handlers are attached and the application can respond. Large client bundles, repeated data work, or hydration mismatches can erase some initial-response benefits. [3]

A hydration mismatch occurs when the client application expects a different initial DOM or state from what the server generated. Common causes include time-dependent output, random values, locale differences, inconsistent data snapshots, and browser-only state being used during the first client render. The result can range from warnings to replaced markup, visual changes, or broken interactions. Exact behavior depends on the framework.

### Architecture comparison

| Approach | Where initial HTML is generated | Typical strengths | Common trade-offs |
|---|---|---|---|
| SSR | On the server per request | Dynamic content with meaningful initial HTML | Server compute, TTFB, caching complexity |
| Static rendering | Ahead of requests | Cacheability and predictable initial HTML | Build coverage and content freshness |
| CSR | In the browser | Rich client-side application behavior | Rendering depends on JavaScript and data requests |
| Hybrid | Combination of server, build, and browser | Route-specific balance of requirements | More complex consistency and operations |
| SSR with hydration | Server first, then client attaches behavior | Early markup plus client interactivity | Hydration cost, mismatches, delayed interactivity |

No row is universally best. The correct architecture is the simplest one that meets content freshness, user experience, reliability, crawler compatibility, security, and operational requirements. [3]

## 3. How Google documents JavaScript processing

Google Search documents three broad phases for JavaScript applications:

1. **Crawling:** Googlebot requests a URL and receives its HTTP response, subject to crawler access rules.
2. **Rendering:** Google queues eligible pages for rendering and uses its Web Rendering Service (WRS), based on an evergreen version of Chromium, to execute JavaScript.
3. **Indexing:** Google processes the rendered HTML and other available information for possible indexing.

Google describes an initial processing stage that can extract links from the response and schedule a page for rendering. After rendering, Google can parse the rendered HTML again to discover additional links and process page content. This is a simplified description of Google's documented system, not a complete disclosure of its internal scheduling, resource allocation, or indexing pipeline. [1]

Important qualifications:

- Rendering is not necessarily immediate; a page may wait in a rendering queue.
- A successful fetch or render does not guarantee that the page will be indexed or served.
- A URL blocked by robots.txt is not fetched for rendering in the described Googlebot process; blocked JavaScript and other resources cannot contribute to the rendered page.
- Google may skip rendering for responses that are not successful, such as many 404 responses.
- Google Search's JavaScript support does not imply support for every browser API, interaction, permission prompt, or transport mechanism.
- Other search engines and automated clients may not execute JavaScript at all, or may implement different rendering behavior. [1][2]

Do not build a site around an assumed fixed rendering delay or a guarantee that every client will execute all scripts. Treat Google-specific behavior as provider documentation and validate the actual page with the tools and clients relevant to the project.

## 4. Make the initial response useful and the rendered result coherent

A robust page should not depend on a fragile chain of browser-only events before it exposes its primary purpose.

Where practical, include essential page identity and content in the initial HTML:

- A meaningful document title.
- The primary page heading and main textual content.
- Stable navigation and crawlable links.
- Important image and media references.
- Page-specific metadata and applicable indexing signals.
- A canonical declaration consistent with the intended URL policy.
- A useful fallback or error state where data is unavailable.

This does not mean every interaction or personalized element must be server-rendered. It means essential resource identity and content should not be needlessly hidden behind application startup, user interaction, or a fragile API dependency.

Compare the initial response with the final rendered DOM. Investigate cases where the initial response is an empty shell but the rendered DOM contains the intended page; JavaScript changes a title or canonical; content appears only after an interaction; server and client represent different content versions; or the rendered DOM removes useful initial content.

The relevant quality criterion is consistency and reliable availability, not a requirement that all pages use one rendering model.

## 5. Content, APIs, and resource dependencies

JavaScript applications often retrieve page data from APIs after the document loads. This can be appropriate, but it creates dependencies that should be explicit and testable.

For every important route, identify:

- The primary API or data source.
- Whether the endpoint is publicly accessible to the intended rendering client.
- Whether authentication, cookies, local storage, or session state is required.
- Whether cross-origin restrictions or network policies affect the request.
- How the application behaves when the endpoint is slow, unavailable, malformed, or returns no record.
- Whether the data is stable enough to cache and whether cached representations can become stale.
- Whether the content is essential to the page's purpose or only an optional enhancement.

### Do not make essential content depend on user-only state

Google's Web Rendering Service does not retain cookies, local storage, or session storage across page loads in the same way a normal returning user session might. A page that requires prior navigation, stored client state, or a user-specific session to reconstruct its primary content can therefore be unreliable for Google's rendering process. [2]

A public page should be reconstructible from its URL and the resources legitimately available to the rendering client. If content requires a signed-in user, payment, or private authorization, treat that as an access-control and product-design requirement rather than trying to expose private data to crawlers.

### Use supported network paths and graceful fallbacks

Google documents that Googlebot retrieves content through HTTP requests and does not support WebSockets or WebRTC as the mechanism for retrieving page content. If primary content depends on those connection types, provide an appropriate HTTP-accessible representation or fallback. Google also recommends feature detection and fallback behavior for critical browser APIs. [2]

Do not assume that a connection available to an interactive browser session is available to every crawler or rendering environment.

### Resource access and failure handling

A rendered page can fail even when its main HTML returns 200. Inspect JavaScript bundles and module imports, API requests, CSS required for meaningful layout or visibility, fonts and images that affect essential content, cross-origin requests and browser security errors, third-party scripts, runtime exceptions, and rejected promises.

Google's troubleshooting guidance notes that WRS may decide not to fetch resources that do not contribute to essential page content. Client-side analytics should therefore not be treated as a complete or authoritative record of all Googlebot and WRS resource activity. Use server logs and Search Console crawl diagnostics for their respective scopes. [2]

## 6. Crawlable navigation and client-side routing

A JavaScript application still needs stable, addressable URLs and ordinary navigational links.

Google's documented link guidance generally expects an HTML anchor element with a real href attribute. JavaScript may insert such links into the DOM, but script-only event handlers, non-anchor elements pretending to be links, and anchors without a usable href are not reliable substitutes. [1][4]

Preferred pattern:

~~~html
<a href="/products/category/shoes">Shoes</a>
~~~

Less reliable pattern:

~~~html
<div onclick="navigateTo('/products/category/shoes')">Shoes</div>
~~~

A client-side router can intercept a normal anchor click and update the view without a full document reload. The underlying link should still identify a real URL that can be requested independently.

### Use the History API for distinct views

For single-page applications, use the History API—such as pushState() and replaceState()—to represent navigable views with normal URL paths. Google advises against using URL fragments such as #/products as the primary mechanism for loading distinct page content. Its documentation recommends URL paths and History API routing instead. [1]

A valid client-side route also needs server support:

- Directly requesting the route should return the intended page response.
- Refreshing the route should not produce an accidental server 404.
- The application should resolve the route to the correct resource.
- Back and forward navigation should restore the correct view.
- Unknown routes should produce an appropriate not-found outcome.
- Canonical URLs and internal links should use the intended route format.

A router that works only after navigating from the homepage is incomplete for users who arrive from bookmarks, external links, or search results.

### Handle missing routes and soft 404s

A common SPA failure occurs when every route returns an HTTP 200 application shell, including URLs that do not represent real resources. The application may then display “not found” text without returning an actual 404 response. Google documents this as a source of soft 404 problems. [1][2]

Where possible, return the correct HTTP status from the server or routing layer for missing resources. If client-side logic must determine whether a resource exists, Google documents strategies such as redirecting to a URL that returns a 404 or adding a noindex robots meta tag to the error state. These are implementation-specific mitigations; a server response that accurately represents the resource state is preferable where feasible. [1][2]

HTTP status semantics and redirect selection are owned by [10.7 — HTTP Status Codes, Redirects & URL Migration](10.7-HTTP-Status-Codes-Redirects-and-URL-Migration.md).

## 7. Metadata, canonical signals, and robots directives in JavaScript

JavaScript can modify document metadata, but changes must be deterministic and consistent with the publisher's intended URL and indexing policy.

### Titles and descriptions

Google documents that JavaScript can set or change the document title and meta description. This capability does not remove the need for unique, descriptive, page-specific metadata. Validate that rendered metadata corresponds to the actual route and content rather than a generic application-shell default. [1]

### Canonical declarations

Keep JavaScript-generated canonical output consistent with the page's intended URL policy and avoid conflicting values between the initial and rendered representations. Canonical declaration rules, including Google's initial-HTML guidance, are covered in [10.6 — Indexability, Canonicalization & Duplicate URL Management](10.6-Indexability-Canonicalization-and-Duplicate-URL-Management.md).

Canonical ownership, duplicate URL relationships, and canonical selection are covered in [10.6 — Indexability, Canonicalization & Duplicate URL Management](10.6-Indexability-Canonicalization-and-Duplicate-URL-Management.md). This section covers only the rendering implications.

### Robots directives and noindex

JavaScript can add or change a robots meta element, but timing matters. Google's documentation warns that when Google encounters a noindex directive, it may skip rendering and JavaScript execution. If a page is intended to be indexable, do not put noindex in its initial HTML and expect JavaScript to remove it later. [1]

A dynamically added noindex can be used for a client-detected error state in certain SPA implementations, but it should not replace accurate server-side status behavior when that is practical. The broader directive semantics and crawler-access requirements are covered in 10.6 and 10.4.

## 8. Lazy-loaded content, infinite scroll, and dynamic components

Lazy loading can reduce unnecessary work by deferring non-critical resources until they are near the viewport. However, content that is loaded only after a user scrolls, clicks, or performs another interaction may not be available to a crawler that does not interact with the page.

Google recommends that relevant lazy-loaded content load when it becomes visible in the viewport, without depending on user actions. Documented approaches include browser-native lazy loading, the Intersection Observer API, and libraries that load content as it enters the viewport. Avoid lazy-loading content that is likely to be visible immediately on page load. [5]

### Infinite scroll needs addressable chunks

If an interface progressively loads multiple content sections or result sets, provide a paginated URL for each distinct chunk. Google's guidance recommends persistent, unique URLs, stable content for a given URL, and sequential links that allow search engines to discover the pages in the set. The History API can update the displayed URL when a new chunk becomes the primary visible content. [5]

An infinite-scroll interface should not be the only way to reach content that is expected to be discoverable. Provide stable URLs and crawlable links for the relevant pages.

### Test the actual rendered output

Use relevant search-engine inspection tools to verify that expected content has loaded. For Google, URL Inspection can show rendered HTML; for image and video elements, check that the expected resource URL appears in the rendered src attribute. A page that looks complete after manually scrolling is not proof that a crawler can access every deferred section. [5]

## 9. Structured data and web components

JavaScript can generate structured data and insert it into the rendered DOM. Verify that the expected markup is present after rendering and that the requests required to generate it succeed; do not infer final output from the source template alone. [6]

Structured-data meaning, supported properties, validation, feature-specific requirements, and the implications of dynamically generated Product details belong to [10.11 — Structured Data Implementation & Validation](10.11-Structured-Data-Implementation-and-Validation.md). This topic covers only the rendering dependency.

### Web components and shadow DOM

Google's troubleshooting documentation says its Web Rendering Service flattens light DOM and shadow DOM. Component output should therefore be checked in rendered HTML, especially where slotted content or component-specific rendering behavior is involved. Google's guidance points to the slot mechanism and component documentation when light DOM content is not exposed as expected. [2]

Do not assume that a component's appearance in a browser guarantees that its meaningful content is represented as expected in crawler-facing rendered HTML.

## 10. Rendering reliability, caching, and security considerations

### Cache versioning and stale resources

Google documents aggressive caching to reduce network requests and resource use. Its Web Rendering Service may ignore caching headers, which can result in an older JavaScript or CSS resource being used. Content fingerprinting—placing a content-derived hash in the asset filename—helps ensure that a changed file receives a new URL. [1][2]

For example:

~~~text
/assets/app.2bb85551.js
/assets/app.8f4a91c2.js
~~~

The filenames above are illustrative. A production build system should generate fingerprints from actual asset content and update references atomically.

### Feature detection and progressive fallback

Do not assume every browser API or capability is available in every rendering environment. Feature detection allows an application to determine whether a required capability exists and select a fallback where one is possible. Google recommends feature detection and appropriate fallbacks or polyfills for critical APIs. Some features cannot be meaningfully polyfilled; in those cases, the application needs an alternate way to expose its essential content. [2]

### Permission-dependent interfaces

Google advises developers to expect Googlebot to decline user-permission requests. A page should not require access to a camera, microphone, geolocation, or another permission-gated capability before it reveals its primary public content. Permission-dependent features may enhance the experience, but should not be the only path to essential information. [2]

### Security boundaries remain real

Do not expose private or authenticated data merely to make a page render for a crawler. Client-side hiding is not access control: if confidential content is already present in the delivered HTML or API response, it may be accessible even if the interface later hides it. Enforce authorization at the server or API boundary.

A rendering strategy must preserve the same legitimate access policy for users and crawlers. Do not serve materially different content to crawlers in an attempt to manipulate search results. Google's dynamic-rendering guidance distinguishes equivalent rendered output from serving unrelated content to crawlers, which can constitute cloaking. [7]

## 11. Dynamic rendering is a workaround, not the default architecture

Dynamic rendering detects crawler requests and routes them to a renderer that produces an HTML version, while ordinary users receive the JavaScript application. Google describes this as a historical workaround for cases where JavaScript-generated content was not available to relevant crawlers, not a recommended long-term solution. It adds infrastructure and maintenance complexity. Google recommends considering server-side rendering, static rendering, or hydration instead. [7]

Dynamic rendering should not be confused with ordinary server-side rendering or with serving the same meaningful content through different technical paths. If used as a compatibility workaround, rendered content should remain equivalent in substance to the content users receive. Serving a different page to crawlers to influence search results can be cloaking. [7]

For most implementations, first investigate whether the page can be delivered reliably through SSR, static generation, or a hybrid architecture. Select dynamic rendering only when a specific compatibility requirement justifies its additional operational burden and policy risks.

## 12. A practical JavaScript SEO diagnosis workflow

Use a repeatable process that separates server delivery, browser execution, and crawler-specific evidence.

### Step 1 — Identify the route and expected result

Record the exact URL, expected content, intended status, canonical policy, access requirements, and important links. Include both normal routes and representative error or unavailable routes.

### Step 2 — Inspect the original HTTP response

Fetch the URL without relying on browser rendering. Record HTTP status and redirects; response headers, including caching and indexing directives; initial HTML and primary content; script, stylesheet, and resource references; and title, canonical, and robots metadata where present.

HTTP status and redirect correctness are handled in 10.7; indexing directives and canonical policy are handled in 10.6.

### Step 3 — Render in a browser

Load the same URL in a current browser and inspect final DOM and primary content, document title and metadata, canonical and robots elements, crawlable links and their href values, console exceptions and rejected requests, network failures and API responses, and route behavior on direct navigation, refresh, and back/forward actions.

Compare the result with the initial response. Identify exactly which scripts or requests are responsible for adding or changing essential content.

### Step 4 — Test failure and constrained conditions

Where appropriate, test JavaScript disabled or blocked; slow network and CPU throttling; API timeout, empty response, and server error; missing or invalid route parameters; first visit without stored client state; direct access to a nested route; permission prompts declined; and required browser APIs unavailable.

The purpose is not to require every feature to work without JavaScript. It is to discover whether a failure in a non-essential enhancement can accidentally hide or corrupt the primary page.

### Step 5 — Inspect crawler-facing rendering

For Google Search, use URL Inspection in Search Console and the Rich Results Test where relevant. Review rendered HTML, loaded resources, console output, and exceptions. Google also recommends auditing JavaScript errors encountered by users and crawlers where practical. [2]

These tools provide provider-specific evidence. A successful test does not guarantee indexing, ranking, or identical behavior from another crawler.

### Step 6 — Validate route and template coverage

Test representative templates and route families, not only the homepage. Include content pages, product or category pages, paginated views, parameterized routes, and known error states as applicable.

### Step 7 — Re-test after release

Repeat the same checks against the deployed environment. A local development server or staging build does not establish production behavior. Record the release version, URL sample, date, test environment, findings, and unresolved limitations.

## 13. Common JavaScript rendering failure patterns

- **Empty application shell:** initial HTML contains no meaningful content and rendering depends on a long client-side startup sequence.
- **Broken script delivery:** bundles fail because of incorrect paths, MIME types, access rules, or deployment references.
- **Runtime exception:** a JavaScript error prevents essential content or metadata from being created.
- **API dependency failure:** primary content is unavailable because a data request fails or requires user-only state.
- **Unsupported API dependency:** essential content depends on a browser feature or connection unavailable to the rendering client.
- **Hydration mismatch:** server output and client state disagree, causing replacement, inconsistency, or broken interactions.
- **Stale asset cache:** an old script or stylesheet is reused after a deployment.
- **Interaction-gated content:** content appears only after a click, scroll action, hover, or permission request.
- **Uncrawlable navigation:** script events update the interface without real anchor elements and href destinations.
- **Fragment-based routing:** distinct page content is addressed only through hash fragments.
- **Direct-route failure:** a nested route works after client navigation but fails on direct request or refresh.
- **Soft 404:** a missing route displays an error message but returns a successful HTTP response.
- **Conflicting metadata:** the initial HTML and rendered DOM contain different titles, canonicals, or robots directives.
- **Unreliable structured data:** markup is generated too late, conflicts with visible content, or depends on unstable data requests.
- **Incomplete lazy loading:** relevant content is never loaded unless a human performs an interaction.
- **Component content omission:** shadow DOM or slot behavior does not expose expected content in the rendered representation.

## 14. Practical JavaScript SEO and rendering QA checklist

### Initial response and rendering

- [ ] Important public routes return the intended HTTP response.
- [ ] Initial HTML contains useful page identity and, where practical, primary content.
- [ ] Rendered DOM contains the expected content and metadata.
- [ ] Server and client output remain consistent during hydration.
- [ ] Required scripts, stylesheets, and API resources load successfully.
- [ ] Runtime errors do not prevent essential content from rendering.

### Navigation and URL behavior

- [ ] Important links use anchor elements with real href values.
- [ ] Client-side routes have stable, addressable URLs.
- [ ] Direct route requests and page refreshes work.
- [ ] Back and forward navigation restore the correct view.
- [ ] Unknown routes produce an appropriate not-found outcome.
- [ ] URL fragments are not used as the only identifier for distinct content pages.

### Metadata and directives

- [ ] Titles and descriptions correspond to the rendered page.
- [ ] Canonical declarations are consistent between initial HTML and rendered output.
- [ ] No duplicate or conflicting canonical elements are injected.
- [ ] Initial robots directives do not contradict the intended indexing state.
- [ ] A page intended for indexing does not rely on JavaScript to remove an initial noindex.

### Resources and dynamic content

- [ ] Primary content does not depend on user-only storage or prior navigation state.
- [ ] Essential data has a reliable HTTP-accessible retrieval path.
- [ ] Required browser APIs have appropriate feature detection and fallback behavior.
- [ ] Lazy-loaded content appears when relevant content enters the viewport.
- [ ] Infinite-scroll content has persistent paginated URLs and crawlable sequential links.
- [ ] Web components expose expected content in rendered HTML.
- [ ] JavaScript-generated structured data is validated separately under the 10.11 process.

### Release verification

- [ ] Representative templates and route families have been tested.
- [ ] Browser rendering and crawler-facing rendering have been compared.
- [ ] Search Console URL Inspection or the relevant provider tool has been used where available.
- [ ] Tests have been repeated against the deployed environment.
- [ ] Findings include URL, environment, release, evidence, owner, and limitations.

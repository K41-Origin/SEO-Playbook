# 09.5 — Ontologies, Taxonomies & Controlled Vocabularies

> **Domain:** 09 — Semantic SEO  
> **Status:** Documented; source-checked  
> **Previous topic:** [09.4 — Semantic Relationships & Relationship Modeling](09.4-Semantic-Relationships-and-Relationship-Modeling.md)

## 1. Why These Structures Exist

A knowledge model needs more than a pile of terms and relationships. It also needs a defensible way to define what its concepts mean, group them, distinguish levels of abstraction, and keep terminology consistent.

Three structures often appear in that work:

- **Ontology:** a conceptual model that defines the kinds of things in a domain and the formal relationships or constraints that describe them.
- **Taxonomy:** a classification structure that arranges concepts or items into categories, commonly through broader–narrower hierarchies.
- **Controlled vocabulary:** an intentionally maintained set of preferred terms and their alternatives, definitions, scope notes, and usage rules.

They overlap, but they are not interchangeable. An ontology can include a taxonomy-like hierarchy. A taxonomy can use terms from a controlled vocabulary. A controlled vocabulary can exist without a formal ontology. Choosing the right structure depends on the problem, not on which label sounds most advanced. [1][2]

This topic defines these structures at the conceptual and knowledge-model level. It does not define individual relationship assertions (09.4), graph representation and serialization (09.6), or technical implementation in website markup (Domain 10).

## 2. Ontology: Define the Conceptual Rules

In knowledge representation, an ontology is a formal description of a domain: the vocabulary used to describe it and the statements that specify how its elements are related. In OWL 2, these descriptions can include classes, properties, individuals, and axioms, with formally defined semantics. [1]

An ontology answers questions such as:

- What kinds of things exist in the domain being modeled?
- Which concepts are classes, and which are individual instances?
- What properties can connect or describe them?
- What constraints or logical statements define the model?
- Which conclusions follow from the statements already represented?

### 2.1 Common ontology components

| Component | Meaning | Example in a bicycle domain |
|---|---|---|
| Class | A category whose members are instances | Bicycle, Component, Manufacturer |
| Individual | A specific modeled instance | A particular bicycle or manufacturer |
| Object property | A relation between individuals | hasComponent, manufacturedBy |
| Data property | A property assigning a data value | frameSize, modelYear |
| Axiom | A formal statement about classes, properties, or individuals | Every RoadBicycle is a Bicycle |
| Class expression | A composed description of a class | Bicycle with a particular component type |

These are conceptual examples, not a complete OWL specification. OWL distinguishes classes, individuals, object properties, data properties, and axioms; its formal semantics determine what the statements mean and what can be inferred from them. [1]

### 2.2 Ontology is not just a hierarchy

A hierarchy can say that Road Bicycle is a narrower category than Bicycle. An ontology can go further by expressing that a bicycle has components, that a particular component belongs to a component category, or that certain classes are disjoint.

The extra power comes with extra responsibility. A formal statement can affect what a reasoning tool considers consistent or inferable. A poorly defined class boundary or axiom can make the model misleading or inconsistent. OWL's reasoning capabilities are useful, but they are not a substitute for domain expertise and careful modeling. [1]

### 2.3 When an ontology is justified

Consider an ontology when the project needs one or more of the following:

- Several systems or teams must share precise definitions.
- Concepts have non-trivial relationships or constraints.
- The model must distinguish classes from individual instances.
- Automated consistency checking or logical inference is a real requirement.
- The domain has enough complexity that informal descriptions repeatedly cause ambiguity.

Do not choose OWL simply because the project uses the phrase *Semantic SEO*. If a spreadsheet, a controlled term list, or a straightforward hierarchy solves the actual problem, adding a formal ontology is just complexity cosplay.

## 3. Taxonomy: Classify Concepts into Categories

A taxonomy organizes concepts or items into categories, commonly through hierarchical broader–narrower relationships. It is useful when people need to browse, classify, or understand how a subject is divided into more specific groups. SKOS explicitly supports knowledge organization systems such as taxonomies and classification schemes, including concept hierarchies. [2]

A simple taxonomy might look like this:

- Bicycle
  - Road Bicycle
  - Mountain Bicycle
  - Hybrid Bicycle
- Bicycle Component
  - Frame
  - Wheel
  - Brake

The example is illustrative. It is a useful classification only if the categories are defined consistently and the hierarchy reflects the project's actual classification purpose.

### 3.1 Parent–child logic must hold

A narrower category should genuinely be a type or subset of its broader category under the chosen classification rule. RDF Schema provides vocabulary for classes and subclass relationships, while richer ontology languages such as OWL add more expressive modeling constructs; the appropriate formalism depends on the semantics the project actually needs. [1][3]

A useful test is:

> If an item belongs to the narrower category, should it also belong to the broader category?

If the answer is no, the hierarchy may be expressing something other than classification—perhaps ownership, location, topic association, or composition. Give that relationship a more accurate model rather than forcing every connection into a parent–child tree.

### 3.2 Hierarchy is not always a single tree

A taxonomy can require multiple broader categories for one concept. For example, a component might be classified by both function and product area. This is often called **polyhierarchy**.

Polyhierarchy can be useful, but it needs clear rules:

- Explain why each parent category applies.
- Avoid duplicate concepts created only to fit separate branches.
- Distinguish multiple valid classifications from accidental cycles or contradictory paths.
- Keep the taxonomy navigable for its intended users.

SKOS provides broader and narrower properties for direct hierarchical links. Its `skos:broader` and `skos:narrower` properties are not themselves transitive; the specification provides separate transitive properties for representing indirect ancestry. This distinction matters when a model needs to preserve immediate parentage instead of flattening every ancestor into a direct parent. [2]

### 3.3 Taxonomy versus topic grouping

A taxonomy classifies concepts according to a defined scheme. A loose collection of related topics is not automatically a taxonomy.

For example, “cycling”, “bike repair”, “cycling holidays”, and “helmet safety” may be related topics, but their co-occurrence does not establish a valid parent–child classification. The classification rule must explain why one concept belongs under another.

Keyword clusters and search-intent groups are also not automatically taxonomies. Domain 05 owns query research and search-intent classification; this topic concerns the classification of concepts in a semantic knowledge model.

## 4. Controlled Vocabulary: Keep Terminology Consistent

A controlled vocabulary is a maintained set of terms used consistently within a defined context. It can specify preferred labels, alternative labels, definitions, scope notes, and editorial rules.

It answers practical questions such as:

- Which term should editors use as the preferred label?
- Which synonyms or variants should be recognized?
- Does a term have a narrower or domain-specific meaning?
- Which similar terms must remain distinct?
- When should a term be deprecated or replaced?

SKOS provides a standard model for representing concepts and knowledge organization systems. It supports concept identifiers, preferred and alternative labels, hidden labels, definitions, notes, and semantic relationships between concepts. [2]

### 4.1 Common vocabulary elements

| Element | Purpose | Example |
|---|---|---|
| Preferred label | Main approved human-readable term | Bicycle |
| Alternative label | Recognized synonym or variant | Bike |
| Hidden label | Variant useful for matching or retrieval but not preferred for display | A known misspelling |
| Definition | States what the concept means | A human-powered vehicle with two wheels |
| Scope note | Explains intended use and boundaries | Use for complete bicycles, not individual components |
| Editorial note | Records internal guidance for maintainers | Prefer “Bicycle” in formal category labels |
| Notation | A code or symbol used by a defined notation system | An internal category code |

The examples are illustrative. A vocabulary does not need every element, and labels must be selected according to language, audience, and domain context.

### 4.2 Preferred label is not the same as the only valid wording

A preferred label establishes the term used as the main display or editorial choice. It does not mean every alternative expression is wrong or that real users always use the preferred wording.

SKOS distinguishes `prefLabel`, `altLabel`, and `hiddenLabel`. Its data model allows no more than one preferred label per language tag for a resource, and the three label properties are pairwise disjoint. These are SKOS model conditions, not a universal editorial rule for every spreadsheet or CMS. [2]

### 4.3 Definitions and scope notes prevent term drift

A term without a definition can silently change meaning between teams, pages, or editorial cycles.

A useful entry should clarify:

- What the term denotes.
- What it does not denote.
- Which contexts make the term appropriate.
- Which alternative terms are accepted.
- Which near-synonyms must remain separate.
- Who can approve changes.

For example, a product catalogue may distinguish “bicycle frame” from “bicycle”. Treating them as interchangeable would create classification and content errors, even if casual language sometimes uses them loosely.

## 5. The Three Structures Compared

| Dimension | Ontology | Taxonomy | Controlled vocabulary |
|---|---|---|---|
| Primary job | Define a domain's concepts and formal semantics | Classify concepts or items | Standardize terminology |
| Typical structure | Classes, individuals, properties, axioms | Categories and broader–narrower hierarchy | Concepts, labels, definitions, notes |
| Formality | Can be highly formal and machine-interpretable | Ranges from informal to formally represented | Ranges from editorial list to standardized concept scheme |
| Main question | What exists in the model, and what statements define it? | What category does this belong to? | Which term should we use, and what does it mean? |
| Useful when | Constraints, precise shared semantics, or reasoning matter | Browsing, grouping, and classification matter | Terminology consistency and synonym management matter |
| Common risk | Over-modeling or incorrect axioms | Forced or misleading hierarchy | Ambiguous terms and unmanaged variants |

The boundaries are practical, not absolute. An ontology may contain a class hierarchy. A taxonomy may be represented using SKOS. A controlled vocabulary may provide labels for concepts used in a larger ontology. W3C describes SKOS as usable on its own or alongside formal knowledge-representation languages such as OWL. [1][2]

## 6. How They Work Together

A project may combine the three structures without collapsing them into one.

**Illustrative bicycle catalogue model:**

1. **Controlled vocabulary** standardizes labels such as “Bicycle”, “Road Bicycle”, “Mountain Bicycle”, “Frame”, and “Brake”. It records approved alternatives such as “Bike” and defines the scope of each term.
2. **Taxonomy** organizes product concepts into a browseable classification, such as Bicycle → Road Bicycle and Bicycle → Mountain Bicycle.
3. **Ontology** defines the richer conceptual rules where needed: Bicycle is a class; Road Bicycle is a subclass; a specific product is an individual; a product has components; and selected constraints describe valid model relationships.

The layers serve different jobs:

- Vocabulary stabilizes the language.
- Taxonomy organizes the categories.
- Ontology formalizes the conceptual rules.

They can be maintained as separate artifacts or represented using compatible standards. The choice depends on interoperability, tooling, complexity, and maintenance needs. [1][2]

## 7. Choosing the Simplest Adequate Structure

Use the problem to select the model—not the other way around.

| Project requirement | Starting point | Add complexity only when… |
|---|---|---|
| Editors need consistent names and synonyms | Controlled vocabulary | Terms require formal concept relationships or cross-system exchange |
| Users need to browse a category hierarchy | Taxonomy | Concepts need richer constraints or multiple semantic relations |
| Teams need precise shared domain definitions | Ontology | Formal axioms, reasoning, or interoperability requirements justify the cost |
| Product catalogue needs labels and categories | Vocabulary + taxonomy | Product types, components, and constraints need formal semantics |
| Several systems must exchange a concept scheme | SKOS-based vocabulary/taxonomy | Richer domain semantics require OWL or another formal model |

A practical decision sequence:

1. **Name the actual problem.** Is it inconsistent terminology, poor classification, ambiguous definitions, or a need for formal reasoning?
2. **Define the scope.** State which subject area and use cases the model covers.
3. **Start with concepts and terms.** Identify what needs a stable definition before building complex relationships.
4. **Add hierarchy only when classification logic supports it.** Do not turn every association into a parent–child relationship.
5. **Add formal ontology constructs only when required.** Document what the axioms mean and what consequences they permit.
6. **Test with real examples and edge cases.** A model that only works for the easy examples is not ready.
7. **Assign ownership and maintenance.** Decide who can add, merge, rename, deprecate, or redefine concepts.

## 8. Governance: A Model Needs Someone to Maintain It

A taxonomy or vocabulary can become inconsistent even if its initial design is sound. New products, changing terminology, regional differences, and editorial decisions can introduce duplicate terms or contradictory categories.

At minimum, define:

- **Scope:** what the scheme includes and excludes.
- **Ownership:** who is accountable for definitions and changes.
- **Preferred-term policy:** how labels are selected and localized.
- **Classification policy:** what qualifies a concept for a category.
- **Change process:** how additions, renames, merges, splits, and deprecations are reviewed.
- **Versioning:** how changes are recorded and communicated.
- **Evidence:** sources or subject-matter decisions supporting definitions and classifications.
- **Review cadence or triggers:** when the model is reconsidered.

SKOS includes documentation properties such as definitions, scope notes, editorial notes, and change notes. These provide vocabulary-level mechanisms for recording meaning and maintenance context. [2]

Do not silently repurpose an existing concept when its meaning changes materially. Create a new concept or versioned record where needed, preserve the change history, and assess downstream dependencies.

## 9. Common Modeling Failures

| Failure | Why it fails | Better approach |
|---|---|---|
| Calling every category system an ontology | Hides the actual structure and its level of formality | Describe the model by what it defines and supports |
| Forcing a hierarchy onto related topics | Association does not prove broader–narrower classification | Define the classification rule or use an appropriate associative relationship |
| Treating synonyms as separate concepts | Creates duplicate concept records | Maintain preferred and alternative labels where they denote the same concept |
| Treating similar terms as synonyms | Collapses concepts with different scope | Write definitions and scope notes; preserve distinctions |
| Using multiple preferred terms without language/context rules | Creates inconsistent labels | Define preferred-label policy and language handling |
| Building a formal ontology for a simple editorial list | Adds cost without solving a real problem | Start with a vocabulary or taxonomy |
| Treating an editorial category as a universal truth | Confuses a local classification choice with an objective fact | Record the scheme's purpose and perspective |
| Letting categories grow without governance | Produces duplicates, dead branches, and term drift | Assign owners, change control, and review criteria |
| Treating a taxonomy as a URL plan | Mixes conceptual classification with website architecture | Domain 09.9 translates validated models into website information architecture |

## 11. Key Takeaways

- Ontology, taxonomy, and controlled vocabulary solve related but different modeling problems.
- Ontologies define concepts and formal semantics; taxonomies classify; controlled vocabularies standardize terms.
- A taxonomy is not automatically an ontology, and a list of synonyms is not a complete knowledge model.
- Hierarchical classification requires a defensible broader–narrower rule.
- Preferred labels, alternative labels, definitions, and scope notes help prevent terminology drift.
- SKOS supports lightweight knowledge organization systems and can be combined with OWL where richer formal semantics are justified.
- Choose the simplest structure that solves the real problem. Complexity is a cost, not a trophy.
- Model governance is part of model quality; unmanaged terminology eventually becomes inconsistency at scale.
- These structures improve the clarity and consistency of a website-side knowledge model. They do not, by themselves, prove a Google ranking benefit.

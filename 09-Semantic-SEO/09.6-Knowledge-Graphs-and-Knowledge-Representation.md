# 09.6 — Knowledge Graphs & Knowledge Representation

**Domain:** [09 — Semantic SEO](README.md)  
**Topic ID:** 09.6  
**Status:** Documented; source-checked  
**Review date:** 2026-11-21

A semantic model describes the subjects, concepts, and relationships a project cares about. A **knowledge graph** gives that model a graph-shaped representation: things are represented as nodes, and meaningful connections are represented as edges or predicates. The graph is useful only when represented statements have clear meaning, identity, context, and evidence. More nodes do not magically produce more knowledge.

This topic covers graph-based knowledge representation at the conceptual and data-model level. It uses RDF as a standards-based example, not as the only possible graph technology. It does not re-define relationship meaning (09.4), ontology and vocabulary design (09.5), search-engine knowledge graph internals, retrieval algorithms (Domain 04), or website structured-data implementation (Domain 10).

## 1. What Is a Knowledge Graph?

A **knowledge graph** is a graph-structured representation of entities or concepts and the relationships or properties that connect or describe them. In practice, the term is used across different systems and implementations; it does not identify one universal storage engine, schema, query language, or mandatory serialization format.

RDF provides a precise graph data model: an RDF graph is a set of subject–predicate–object triples. Each triple represents a statement, and a graph can be visualized as nodes connected by directed, labeled arcs. RDF 1.1 also defines datasets that organize a default graph and zero or more named graphs. [1]

The useful distinction:

- **Knowledge model:** the conceptual account of what the project intends to represent.
- **Knowledge graph:** a graph-shaped representation of selected model statements and data.
- **Graph technology:** the software, storage, query, and processing infrastructure used to manage a graph.

These layers can be related, but they are not synonyms. A project can have a conceptual knowledge model without deploying a graph database. It can also store graph-shaped data without having a coherent knowledge model. The second option is basically a pile of connected records wearing a smarter outfit.

## 2. Graph Building Blocks

### 2.1 Nodes

A **node** represents a modeled resource or value. In an RDF graph, nodes can be IRIs, blank nodes, or literals. IRIs can identify resources; literals represent values such as strings, dates, or numbers. Blank nodes represent resources for which the graph does not provide a global IRI identifier. [1]

Typical knowledge-graph nodes include:

- Entities: a specific organization, person, product, place, or event.
- Concepts or classes: Bicycle, Manufacturer, or Product Category.
- Documents or digital resources: a product page, dataset, or report.
- Literal values: a model number, date, language-tagged label, or measurement.

Do not treat every value as an entity node. A product's weight can usually be represented as a literal value with an appropriate datatype and unit policy; it does not automatically need its own entity record. Create a separate node when the value itself has identity, relationships, or lifecycle significance.

### 2.2 Edges and predicates

An **edge** represents a connection between nodes. In RDF, the predicate in a triple names the relationship or property and points from the subject to the object. Direction and predicate meaning matter. [1]

For example, an illustrative catalogue may represent:

- a bicycle model **has component** a frame;
- a manufacturer **manufactures** a bicycle model;
- a bicycle model **has model year** the literal value 2026.

The first two objects are resources; the model-year value is a literal. The graph representation makes the distinction visible without changing the underlying meaning of the assertions.

The semantics of a predicate must already be defined. Topic [09.4 — Semantic Relationships & Relationship Modeling](09.4-Semantic-Relationships-and-Relationship-Modeling.md) owns how relationship assertions are named, directed, qualified, and evidenced. This topic explains how those assertions are represented as graph connections.

### 2.3 Graph structure is not proof

A graph can make relationships easier to inspect and traverse, but the visual presence of an edge does not establish that the statement is true. Graph structure is a representation choice, not an evidence mechanism.

For each important statement, preserve the source, context, validity period, confidence or review status where relevant. The graph should distinguish a directly sourced statement from an inferred, disputed, or unresolved one. This is a project modeling recommendation; the exact metadata structure depends on the use case.

## 3. From Triples to a Graph

### 3.1 The RDF triple pattern

RDF represents a statement using three positions:

| Position | Role | Illustrative value |
|---|---|---|
| Subject | Resource being described | ex:RoadBikeModelA |
| Predicate | Property or relationship | ex:hasComponent |
| Object | Related resource or value | ex:FrameModelB |

An RDF graph is a set of such triples. The same subject can participate in many statements, and the same resource can appear as a subject in one statement and an object in another. This creates connected graph structures rather than isolated rows. [1]

Original illustrative Turtle-like fragment (not a complete production ontology):

    @prefix ex: <https://example.org/id/> .

    ex:RoadBikeModelA ex:manufacturedBy ex:MakerA ;
                      ex:hasComponent ex:FrameModelB ;
                      ex:modelYear "2026" .

This fragment expresses three assertions. It does not by itself define what counts as a manufacturer, component, or model year. Those meanings belong to the vocabulary and ontology layer described in [09.5 — Ontologies, Taxonomies & Controlled Vocabularies](09.5-Ontologies-Taxonomies-and-Controlled-Vocabularies.md).

### 3.2 Resource identity and identifiers

A graph needs a stable way to distinguish resources within its declared scope. RDF commonly uses IRIs for this purpose. A human-readable label is not a reliable identifier: two different resources may share a name, and one resource may have multiple labels or aliases. [1]

Use identifiers deliberately:

- Define what each identifier denotes: a product model, a sellable variant, or an individual physical unit.
- Keep identifiers stable when labels change, where the underlying identity remains the same.
- Do not reuse one identifier for distinct subjects.
- Record external identifiers and mappings with their source and scope.
- Avoid minting global-looking identifiers when the project only needs local identifiers.

Blank nodes can be useful for resources that do not need a globally named identity, but they are not a shortcut for entities that must be referenced consistently across datasets. RDF defines blank nodes as graph resources without an IRI identifier. [1]

### 3.3 Literals, datatypes, and language

A literal represents a value, such as text, a date, or a number. RDF supports datatype IRIs and language tags, allowing a graph to distinguish values such as a plain label, a language-tagged label, and a typed numeric value. [1]

Do not store every value as an unqualified string if the distinction matters. For example, the text string "2026" and a typed integer value are not necessarily interchangeable in downstream processing. Measurement data should also have an explicit unit convention; the number 12 without a unit or measurement context is incomplete information.

## 4. Graphs, Datasets, and Named Graphs

An RDF graph is one set of triples. An RDF dataset groups a default graph and zero or more named graphs. A named graph pairs a graph name with a graph; importantly, RDF does not automatically prescribe that the graph name denotes its publisher, provenance, or contents. Any such interpretation requires an explicit application convention or additional metadata. [1]

Named graphs can help organize data by source, version, scope, or trust boundary, but those are design patterns—not meanings guaranteed by the RDF data model. If a project uses graph names to represent source attribution, document that convention and preserve provenance at the statement level where needed.

A dataset design should answer:

- Which statements belong in the default graph?
- What do named graphs represent in this application?
- Can data from different sources be kept separate?
- How are updates, snapshots, and conflicting statements handled?
- What metadata describes the graph, its creator, and its version?

Do not assume that placing statements in separate named graphs automatically resolves contradictions or validates their sources.

## 5. Provenance and Context

A knowledge graph often combines statements from multiple sources. Without provenance, a consumer may be unable to tell who asserted a fact, when it was collected, which process transformed it, or which source version was used.

W3C PROV-O provides an ontology for representing provenance information, including entities, activities, and agents, and can be specialized for application-specific provenance needs. [2]

A practical provenance record may capture:

| Field | What it helps answer |
|---|---|
| Source | Where did the statement come from? |
| Agent | Who or what was responsible for producing or asserting it? |
| Activity | Which collection, transformation, or review process generated it? |
| Recorded time | When was it added to this dataset? |
| Valid time | When is the statement claimed to apply in the modeled world? |
| Status | Is it supported, inferred, disputed, or unresolved? |
| Version | Which source or model version was used? |

This table is a project-level design aid, not a mandatory PROV-O field list. PROV-O supplies reusable provenance concepts; the application must decide which details are necessary and how to represent them. [2]

### 5.1 Conflicting statements

Two sources may make incompatible claims about the same subject. Do not silently overwrite one statement merely because another source arrived later.

Instead:

1. Preserve source attribution.
2. Check whether the claims refer to the same entity, property, context, and time.
3. Distinguish actual contradiction from different valid periods or scopes.
4. Record the resolution decision and evidence.
5. Keep unresolved conflicts visible until they can be evaluated.

A graph can represent competing claims, but it does not decide which source is correct by itself.

## 6. Querying a Knowledge Graph

A graph becomes operationally useful when users or systems can retrieve patterns across connected resources. For RDF data, SPARQL is a W3C-standard query language. It supports graph-pattern matching and can query data stored as RDF or exposed as RDF through middleware. [3]

A query can ask questions such as:

- Which bicycle models are manufactured by a particular company?
- Which models include a component from a selected category?
- Which product records have no recorded manufacturer?
- Which statements came from a particular source graph?

Original illustrative SPARQL query:

    PREFIX ex: <https://example.org/id/>

    SELECT ?model
    WHERE {
      ?model ex:manufacturedBy ex:MakerA ;
             ex:hasComponent ?component .
    }

The query pattern asks for resources that have both stated connections. It does not prove the source statements are accurate, complete, current, or relevant to a particular user. Query results are only as trustworthy as the data, definitions, and retrieval conditions behind them. [3]

SPARQL is specific to RDF. Other graph systems may use different query languages and data models; do not assume that a SPARQL endpoint, RDF store, property-graph database, and every product marketed as a “knowledge graph” are interchangeable.

## 7. Validation and Quality Control

A graph can be syntactically valid while still being incomplete, inconsistent with project rules, or semantically misleading. Separate at least three quality questions:

1. **Representation validity:** Is the graph encoded in a form the selected data model accepts?
2. **Model conformance:** Does the data satisfy the project's declared structural and value constraints?
3. **Knowledge quality:** Are the identities, statements, sources, and meanings actually defensible?

W3C SHACL defines a way to validate RDF data graphs against shapes graphs containing constraints. It can report violations such as missing required values or values of an unexpected type. SHACL validation checks declared constraints; it does not independently establish that the real-world claims are true. [4]

A practical validation checklist:

- Required identifiers exist and are unique within the intended scope.
- Predicates are drawn from the approved vocabulary.
- Subjects and objects have the expected kinds of values.
- Required properties and cardinalities are satisfied.
- Datatypes, language tags, and units follow the project rules.
- Relationship direction and class membership are not accidentally reversed.
- Provenance is available for claims that require traceability.
- Duplicate, conflicting, stale, or orphaned records are reviewed.
- Model changes do not silently break dependent applications or content structures.

SHACL is an RDF validation standard, not a universal validator for every graph technology. Choose validation tools that match the data model and the constraints that actually matter. [4]

## 8. A Practical Knowledge-Graph Workflow

1. **Declare the use case.** State what decisions, questions, or integrations the graph must support.
2. **Set the scope.** Define which entities, concepts, sources, and time periods are in or out.
3. **Reuse the semantic model.** Start from the entity definitions, relationship semantics, ontology, taxonomy, and vocabulary established in 09.2–09.5.
4. **Choose a representation.** Decide whether a graph is justified and select an appropriate model or standard. RDF is one standards-based option, not an automatic requirement.
5. **Define identifiers.** Establish resource identity, identifier policy, and handling for external references.
6. **Map model elements to graph structures.** Decide which concepts become nodes, which relationships become predicates, and which values remain literals.
7. **Attach context and provenance.** Preserve sources, time, status, and transformation history where required.
8. **Load and query representative data.** Test the graph against real use cases, not only a tidy demo.
9. **Validate and review.** Apply structural constraints and separately review factual accuracy, coverage, and ambiguity.
10. **Govern changes.** Version the model, track breaking changes, assign ownership, and monitor dependent systems.

Not every website needs a knowledge graph. A controlled vocabulary, taxonomy, relational database, or well-maintained content model may be sufficient. Build a graph when connected data, flexible traversal, shared semantics, or cross-source integration justify the operational cost.

## 9. Illustrative Example: A Bicycle Product Knowledge Graph

The following is an original simplified example, not a production schema or a claim about search-engine data.

A bicycle catalogue might model:

- **Resources:** Bicycle Model A, Manufacturer A, Frame Model B, Brake Model C.
- **Relationships:** Manufacturer A manufactures Bicycle Model A; Bicycle Model A has Frame Model B; Bicycle Model A has Brake Model C.
- **Literal values:** model year, frame size, product description, and a measured weight with an explicit unit.
- **Vocabulary:** preferred product labels and accepted alternatives.
- **Ontology/schema:** definitions of Bicycle Model, Manufacturer, Frame, Brake, and the properties allowed between them.
- **Provenance:** product-manufacturer source, retrieval date, and editorial review record.
- **Validation:** required manufacturer, valid model-year datatype, and approved component categories.

The graph can support questions that cross several product records. But if the catalogue only contains a few dozen products and no integration or traversal requirement, a simpler database or CMS model may be cheaper and easier to maintain. The representation should earn its complexity.

## 10. Common Failure Modes

| Failure | Why it matters | Better approach |
|---|---|---|
| Treating every node as a distinct real-world entity | Literal values and abstract concepts are different kinds of graph elements | Define node identity and value representation deliberately |
| Using labels as identifiers | Labels can collide or change | Use stable identifiers with clear scope |
| Treating every edge as a proven fact | Graph topology does not validate truth | Preserve evidence, provenance, and assertion status |
| Mixing predicates with vague meanings | Consumers interpret edges inconsistently | Reuse the governed relationship vocabulary from 09.4–09.5 |
| Assuming named graph names encode provenance | RDF does not assign that meaning automatically | Document graph-name conventions and model provenance explicitly |
| Flattening conflicting sources into one value | Loses disagreement, context, and auditability | Preserve source-specific assertions and resolution history |
| Turning every literal into a node | Inflates the model without adding useful identity | Use literals for ordinary values; create nodes when they need identity or relationships |
| Assuming RDF is the only graph model | Confuses one standard with the broader design space | Choose representation based on interoperability and application requirements |
| Treating validation as fact-checking | Structural conformance does not prove real-world truth | Combine validation with source review and domain expertise |
| Building a graph with no use case | Adds storage, governance, and query costs without clear benefit | Start from required questions and integration needs |

## 12. Key Takeaways

- A knowledge graph represents modeled resources and their connections in graph form; it is not one mandatory technology stack.
- RDF is a standards-based graph data model built from subject–predicate–object triples.
- Nodes may represent resources or literal values; not every value needs its own entity node.
- Identifiers, predicate semantics, provenance, and context determine whether a graph remains interpretable and auditable.
- RDF datasets can contain default and named graphs, but graph names do not automatically carry provenance semantics.
- SPARQL queries RDF graph patterns; query results do not certify factual accuracy.
- SHACL can validate RDF data against declared structural constraints, not independently verify real-world truth.
- Choose graph representation when its integration and traversal benefits justify the maintenance cost.
- A website knowledge graph does not, by itself, establish a Google ranking benefit.

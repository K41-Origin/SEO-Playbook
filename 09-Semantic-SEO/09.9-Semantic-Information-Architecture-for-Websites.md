# 09.9 — Semantic Information Architecture for Websites

A topical model explains how subject matter is related. A website still needs additional decisions: which information should become a page, how pages should be grouped, how people find them, and what distinct function each page serves.

That is the work of **semantic information architecture (semantic IA)**. It does not mean turning every knowledge-graph node into a URL. That is a quick way to build a complicated site, not a useful one.

## 1. What Is Semantic Information Architecture?

**Semantic information architecture** translates a validated knowledge model into a website's information structure: content groups, page types, page roles, relationships between pages, labels, conceptual metadata, and content-architecture specifications.

Within Domain 09, this process uses the topical model from [09.7 — Topical Modeling & Knowledge Domains](09.7-Topical-Modeling-and-Knowledge-Domains.md), checked through [09.8 — Topical Coverage & Semantic Completeness](09.8-Topical-Coverage-and-Semantic-Completeness.md). The output is a website information design—not yet HTML, final URLs, internal-link rules, or an editorial calendar.

Information architecture is broader than a navigation menu. It can be represented through sitemaps, hierarchies, wireframes, navigation, and metadata; navigation is only one way the structure becomes visible to users. [1]

### 1.1 The translation problem

Do not conflate three layers:

| Layer | Main question | Output |
|---|---|---|
| Knowledge model | What concepts, entities, attributes, and relationships exist in this subject? | Conceptual/topical model |
| Website information architecture | How should this knowledge be divided, grouped, assigned roles, and presented as website information? | Conceptual sitemap, content types, page roles, taxonomy, architecture specification |
| Technical and editorial implementation | How are pages written, built, given URLs, markup, navigation, and links? | Briefs, content assets, templates, URLs, HTML, navigation, links |

A knowledge model does not automatically determine one correct website structure. The same model can be translated into different architectures depending on audience, tasks, service type, content scale, team capabilities, and platform constraints. This is a design decision requiring rationale and validation, not a mechanical graph output.

### 1.2 What makes it semantic?

Here, *semantic* means that the website structure preserves important meaning and relationships from the knowledge model:

- Distinct concepts are not merged merely because their terms look similar.
- The same concept is not split into many pages without a clear information reason.
- Parent–child, part–whole, prerequisite, comparison, and association relationships are translated according to their respective functions, not forced into one hierarchy.
- Every page role serves a defined information need.
- Category and page labels reflect the concepts they actually represent.

W3C SKOS shows that a concept scheme can include preferred/alternative labels, semantic relations, collections, and mappings. This is useful for understanding vocabulary structure, but SKOS is not a sitemap template or mandatory website rule. [2]

## 2. Start with People and Information Needs

Do not start with the company menu, department structure, or keyword list. Start with who uses the information and what they need to accomplish.

One subject may serve multiple user groups with different needs. Beginners may need an overview and definitions, while technicians need specifications, procedures, limitations, and troubleshooting. Both relate to the same concepts but may not need the same page or navigation path.

Potential sources of user needs:
- Audience research, customer-support questions, interviews, and observed tasks.
- Existing site search, Search Console queries, on-site search logs, and content-usage data, with each dataset's limitations understood.
- Domain experts, product/service owners, policies, standards, and primary documentation.
- Competency questions and coverage requirements from 09.8.
- Existing content inventory and known user journeys.

Search queries help reveal audience language and questions, but should not be the sole definition of knowledge structure. They remain Domain 05 inputs, not a replacement for a conceptual model. [3]

**Practical output:** an audience/task/information-need list identifying who needs what information, in which context, and which decision or action they want to complete.

## 3. Translate the Model into Website Structures

Not every concept needs a page. One page may explain several related concepts; one concept may need multiple pages when genuinely distinct information needs exist.

### 3.1 Concept groups → content groups

Group concepts according to meaningful relationships and information goals for the audience. Do not automatically copy every topical-model subdomain into a navigation category.

A group may become:
- a primary section or category;
- a subsection;
- a collection or listing;
- part of one comprehensive page;
- metadata or a filter that helps users find content;
- nothing exposed as a website category.

SKOS provides models for concept schemes, collections, labels, and semantic relations. These can inform controlled vocabularies and website taxonomies, but structure and labels must still fit the use context. [2]

### 3.2 Concepts and information needs → page roles

Define each page's *job* before choosing its title or URL.

| Page role | Information function | Example need |
|---|---|---|
| Overview / hub | Introduce a domain and orient users to subtopics | “What are the main parts of a braking system?” |
| Concept explanation | Explain one concept or mechanism in focus | “How does hydraulic braking work?” |
| Procedure / how-to | Help users complete a sequence of tasks | “How do I inspect brake pads?” |
| Reference / specification | Provide data, definitions, parameters, or requirements for reference | “What is this component's torque specification?” |
| Comparison | Compare alternatives using clear criteria | “How do disc and drum brakes differ?” |
| Troubleshooting | Help identify symptoms, possible causes, and inspection steps | “Why do my brakes feel spongy?” |
| Glossary / terminology | Explain terms and label variations | “What does brake fade mean?” |

These are example design patterns, not a universal list or required page types. Select page roles based on information needs, not a target number of URLs.

### 3.3 Relationships → navigation and contextual pathways

Not every knowledge-model relationship must become navigation or a hyperlink.

| Model relationship | Possible website expression | Caution |
|---|---|---|
| Broader / narrower concept | Category, subsection, parent-child grouping | Do not force every relationship into one tree |
| Prerequisite / dependency | Learning sequence, “before you start” reference | Only when order matters to the task |
| Part–whole | Component overview and component detail | Decide whether detail merits a separate page |
| Comparison | Comparison page or structured comparison section | Criteria must be comparable and clear |
| Related concept | Related-content module or contextual reference | Relevance must be real; do not generate links automatically from co-occurrence |
| Alternative label | Synonym handling, search vocabulary, redirect or label guidance | An alternative label does not automatically imply a separate URL or page |

Domain 11 owns internal-link strategy, anchor text, and hyperlink implementation. Domain 09.9 defines information relationships and pathway needs at the architecture level only.

## 4. Choose an Information Organization Model

A website may combine multiple patterns. Choose according to the information and user task, not because a diagram looks impressive.

### 4.1 Hierarchical structure
Organizes information from broad categories to more specific ones.

Suitable when concepts have stable broader–narrower relationships, users need orientation from overview to detail, and categories can be labeled without excessive overlap.

Risks include forcing all relationships into one parent-child tree, creating excessive category depth, and confusing users when content legitimately belongs in multiple contexts.

### 4.2 Sequential structure
Organizes information by task, process, or learning order.

Suitable when genuine prerequisites exist, users must complete stages in sequence, or order prevents errors and loss of context.

Do not impose sequence merely because content can be numbered. Not every subject is a tutorial.

### 4.3 Database or faceted structure
Organizes items by attributes and allows users to filter or explore across dimensions such as product type, compatibility, location, or status.

Suitable when many items have consistent attributes, users have multiple valid ways to narrow choices, and data can be maintained consistently.

Risks include filter combinations producing many URLs or thin pages, facets without clear search or user value, and inconsistent or overlapping attribute values.

Google documents that irrelevant filter and parameter combinations can create very large numbers of similar URLs and burden crawling. Faceted-architecture decisions should therefore involve Domain 10 before being exposed as crawlable URLs. [4]

### 4.4 Networked or cross-linked structure
Allows users to move between related concepts without forcing everything into one tree.

Suitable when concepts have multiple important relationships, users arrive from different entry points, and cross-references add context or help tasks.

Risks include linking every page to every other page without priority, loss of user orientation, and confusing conceptual relationships with a requirement for hyperlinks.

Most websites need a combination: hierarchy for orientation, sequence for tasks, facets for dataset exploration, and contextual relationships for related explanations.

## 5. Define Page Boundaries and Content Ownership

The important question is not “how many pages can we create?” but what information deserves to be one page unit.

Use these questions:
1. Are the information need and user task materially different?
2. Can the concept be explained independently without losing essential context?
3. Is there evidence users need to find or reference this information separately?
4. Would a new page provide distinct value rather than merely split one explanation?
5. Is the information better as a section, table, definition, or component on an existing page?
6. Who owns the information and its authoritative source?
7. Would a new page create duplication or conflicting versions?

Apply **single primary home** as an information-management principle: assign one primary location responsible for the authoritative version, then use contextual references when that information is relevant elsewhere. This does not prohibit summaries, quotations, or data reuse; it avoids multiple pages claiming to be the primary source for identical information without a reason. Google also recommends reducing confusing duplication and identifying one canonical URL for each piece of content. [3]

### 5.1 One concept does not always equal one page

A definition of “brake fade” may be sufficient as a section in a braking guide. If users also need symptom diagnosis, causes, prevention, and inspection procedures, a separate troubleshooting page may be justified. The decision depends on information needs, depth, and access patterns—not entity count.

### 5.2 One page can cover multiple concepts

An overview page may explain several components that form one system. When relationships and concept boundaries remain clear, there is no reason to split it into many small pages.

## 6. Labels, Taxonomy, and Metadata

Labels are the language interface between the model and the user. Category names, menu names, page titles, breadcrumb labels, tags, and filters should clearly indicate what users will find.

### 6.1 Label design
- Use terms familiar to the audience, not internal organizational jargon.
- Make labels specific and consistent.
- Distinguish terms that refer to different concepts.
- Define preferred and alternative labels where the vocabulary needs synonyms.
- Avoid broad labels such as “Resources,” “Solutions,” or “Other” when they provide too little context.
- Do not create a category merely because two terms often co-occur.

SKOS distinguishes preferred, alternative, and hidden labels and provides semantic relations for concept schemes. It can inform vocabulary management conceptually, but applying SKOS technically to every website is not mandatory. [2]

### 6.2 Taxonomy versus navigation
Taxonomy organizes classification or terminology; navigation helps users move through and find information. They may support one another but are not identical. A detailed internal taxonomy does not all need to appear in a menu.

### 6.3 Metadata
Metadata may describe and manage pages, for example:
- content type / page role;
- primary concept or topic;
- related entities and concepts;
- audience or user group;
- product, service, location, or version;
- content owner;
- review date and lifecycle status;
- language or market.

Metadata needs definitions, allowed values, ownership, and maintenance rules. Do not add fields merely because the CMS offers an empty box. Inconsistent metadata just moves disorder elsewhere.

## 7. Translate Architecture into a Page and Content Model

Before production, document the design so editorial, UX, design, and engineering teams work from a shared specification.

Minimum page/content architecture specification:

| Field | What to record |
|---|---|
| Page ID | Stable internal identifier for proposed page or content type |
| Working title | Temporary descriptive title |
| Page role | Overview, concept, procedure, reference, comparison, troubleshooting, etc. |
| Primary subject | Main concept/entity the page owns |
| Supporting concepts | Secondary concepts needed for explanation |
| User and task | Intended audience and information need |
| Scope | What the page covers and explicitly excludes |
| Parent grouping | Primary category or section, if applicable |
| Relationships | Required conceptual/contextual relationships |
| Content requirements | Facts, explanations, examples, data, procedures, evidence |
| Source of truth | Authoritative owner or reference for critical information |
| Overlap check | Existing pages that may already meet the need |
| Proposed URL pattern | Optional structural proposal, pending Domain 07 and 10 review |
| Implementation notes | Dependencies, CMS fields, localization, technical constraints |
| Validation method | How page role and grouping will be tested |

This specification is an architecture handoff, not a finished editorial brief. Domain 08 turns approved page requirements into editorial planning and briefs; Domain 05 owns query research and keyword-to-page mapping; Domain 07 owns page elements and URL wording; Domain 10 owns technical delivery.

## 8. A Practical Semantic IA Workflow

1. **Confirm the validated knowledge model.** Use 09.7 and coverage findings from 09.8. Record unresolved concepts, disputed relationships, and exclusions. Do not silently turn uncertain assertions into website facts.
2. **Identify audiences and tasks.** List main user groups, contexts, and information needed to understand, compare, decide, or act.
3. **Map information requirements to concepts.** Identify concepts, entities, attributes, relationships, and evidence needed for each requirement. This connects user needs to the model without making query strings the architecture.
4. **Group information.** Create candidate sections, categories, collections, or content types. Use conceptual coherence and user tasks; avoid unnecessary depth.
5. **Assign page roles.** Decide whether each need belongs in an overview, focused explanation, procedure, reference, comparison, troubleshooting page, or existing section.
6. **Define page boundaries and ownership.** Resolve overlap, choose primary homes for authoritative information, and document exclusions.
7. **Design relationships and pathways.** Specify parent-child groupings, prerequisite sequences, contextual relationships, and discovery pathways. Mark whether each is structural, navigational, or conceptual only.
8. **Define labels and metadata.** Create controlled category and page labels; record synonyms, definitions, metadata values, and ownership as needed.
9. **Produce the architecture specification.** Create a conceptual sitemap, content-type model, page inventory/page-role matrix, and relevant taxonomy/metadata specification. Keep proposed URLs provisional until page-level and technical review.
10. **Validate with users and delivery teams.** Test whether people can predict where information belongs, understand labels, find representative information from likely entry points, distinguish similar concepts, and complete key tasks without unnecessary detours.
11. **Hand off implementation and editorial work.** Domain 05 handles query research and mapping; Domain 08 handles planning, briefs, production, review, and lifecycle; Domain 07 handles page elements and URL wording; Domain 10 handles routing, URL behavior, structured data, crawl/index controls, and technical validation; Domain 11 handles internal-link architecture and implementation; Domain 14 handles performance measurement after release.
12. **Record decisions and unresolved risks.** Keep the mapping from model concept → information requirement → page role → proposed page visible. Record rejected alternatives, rationale, assumptions, owner, and review triggers.

Use methods appropriate to the project, such as card sorting, tree testing, prototype testing, task-based usability testing, expert review, and content audits. These are validation options, not mandatory for every project. UK government design-history work illustrates comparing task-led, category-led, goal-led, role-led, and other structures rather than assuming one layout is universally correct. [1]

## 9. Example: Bicycle-Braking Website Architecture

**Illustrative example only.** This is an architecture translation exercise, not a prescribed website structure.

Assume the validated knowledge model includes braking systems; disc and drum brakes; hydraulic and mechanical actuation; pads, rotors, calipers, cables, and fluid; braking performance, brake fade, maintenance, inspection, and troubleshooting.

Audience and tasks:
- New bicycle owners need an overview and basic terminology.
- Riders need to understand differences between braking systems.
- Mechanics need specifications, inspection procedures, and troubleshooting information.

Possible architecture:

| Section | Page role | Primary information responsibility |
|---|---|---|
| Braking systems | Overview hub | Explain the system and point to major components and types |
| Braking systems / Types | Comparison | Compare disc and drum braking using explicit criteria |
| Braking systems / Disc brakes | Concept explanation | Explain disc-brake operation and major components |
| Components / Brake pads | Reference + maintenance | Identify pad types, wear indicators, compatibility, and replacement context |
| Maintenance / Brake inspection | Procedure | Guide a defined inspection task |
| Troubleshooting / Brake fade | Troubleshooting | Explain symptoms, plausible causes, diagnostic checks, and safety boundaries |
| Braking systems / Hydraulic actuation | Concept explanation | Explain hydraulic actuation and its relationship to other components |

The taxonomy may show that brake pads are part of a disc-brake assembly, but that alone does not prove a separate page is needed. A page is justified when its information responsibility and user need are distinct enough. Brake fade may be a section in a performance guide or a dedicated troubleshooting page depending on scope and tasks.

This sitemap is not the only valid translation. A specialist workshop, consumer education site, and ecommerce catalogue may use different page roles and groupings while representing the same subject accurately.

## 10. Quality Checks for Semantic Information Architecture

Evaluate the architecture against explicit criteria. Do not invent a universal IA score.

### Model alignment
- [ ] Important in-scope concepts and relationships from the validated model have an appropriate information destination.
- [ ] Uncertain or disputed relationships are not presented as established facts.
- [ ] The website does not distort concept identity or collapse meaningful distinctions.

### User and task alignment
- [ ] Main audiences and representative information needs are documented.
- [ ] Labels make sense in the intended users' language.
- [ ] Representative tasks can be completed from plausible entry points.
- [ ] Navigation does not merely mirror the organization's internal chart.

### Page boundaries and ownership
- [ ] Every proposed page has a distinct information responsibility.
- [ ] Existing pages were checked before proposing new ones.
- [ ] Each authoritative information item has a clear primary home and owner.
- [ ] Page roles do not overlap without an explicit reason.

### Structural coherence
- [ ] Hierarchy is used where broader/narrower relationships are meaningful.
- [ ] Sequential structures reflect real task or learning dependencies.
- [ ] Facets use controlled, consistent attributes.
- [ ] Cross-links and related pathways have a clear user or information purpose.
- [ ] The architecture does not force every relationship into one hierarchy.

### Delivery readiness
- [ ] Page/content types and metadata have clear definitions.
- [ ] Proposed URL patterns fit the architecture but remain subject to technical review.
- [ ] Editorial, page-level, technical, and internal-link responsibilities are assigned to the correct domains.
- [ ] Localization, maintenance, and ownership requirements are visible.

## 11. Common Mistakes

| Mistake | Why it fails | Better approach |
|---|---|---|
| Turning every entity/concept into a URL | Entity count is not a page-need metric | Decide by user need, information responsibility, and useful differentiation |
| Copying the knowledge graph into a sitemap | Graph relationships and website hierarchy serve different purposes | Select relationships that should shape website organization |
| Treating navigation as the entire IA | Page roles, labels, metadata, content groups, and relationships also matter | Document the full information structure |
| Building categories from keyword clusters alone | Query similarity does not establish conceptual equivalence or stable taxonomy | Combine audience evidence with the validated topical model |
| Mirroring internal departments | Internal organization may not match user mental models or tasks | Organize around user needs and subject relationships |
| Creating a page for every keyword variation | Creates overlap and weak boundaries | Map multiple expressions to one information need where appropriate |
| Making every related concept a link | Creates noisy pathways and confuses association with navigational value | Prioritize pathways by task and context |
| Overusing filters and facets | Creates user complexity and many similar URLs | Expose useful facets only and coordinate crawl/index behavior with Domain 10 |
| Changing URLs to fit a new taxonomy without migration planning | URL changes have technical and operational consequences | Coordinate page-level URL design with technical migration planning |
| Treating architecture as permanent | Knowledge, user needs, products, and services change | Define owners, review triggers, and change control in 09.10 |

## 13. Key Takeaways

- Semantic IA translates a validated knowledge model into a website information structure.
- Knowledge model, website IA, and implementation are separate layers.
- User needs and information tasks determine page roles and boundaries—not entity counts or keyword lists.
- Hierarchies, sequences, facets, and networks can coexist when each solves a real information problem.
- Taxonomy, navigation, metadata, page roles, and content ownership are related but not interchangeable.
- One primary information home helps prevent competing authoritative versions; contextual references can still expose information elsewhere.
- Google documents useful practices for logical site organization, descriptive URLs, links, and duplicate-content handling, but does not prescribe one universal semantic IA or promise ranking gains from a particular sitemap. [3][4]
- The final step is to validate and govern the model and its website representation in 09.10.

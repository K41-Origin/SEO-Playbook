# 02.2 — Search Engine Architecture

A search engine is not one giant search function. It is a system of cooperating components that acquire information, prepare it for search, answer queries, and deliver results.

Understanding the architecture means understanding **which components exist at a conceptual level, what each one is responsible for, and how information moves between them**. It does not mean pretending we know the private service map or internal code of Google. We don't.

## 1. What Search Engine Architecture Means

**Search engine architecture** is the logical organization of the components, data stores, and processing paths that allow a search system to collect or access information and return results in response to a query.

A useful architecture model answers four questions:

1. **Where does searchable information come from?**
2. **How is that information processed and organized?**
3. **How does a query find relevant candidate information?**
4. **How does the system turn those candidates into a response?**

This document uses a generalized web-search architecture. It is a conceptual model for understanding system responsibilities—not a claim that every search engine uses the same components, boundaries, or implementation.

Google publicly describes Search through crawling, indexing, and serving. Microsoft describes Bing through crawling, index construction, and ranking. Those high-level descriptions support a shared functional pattern, but they do not establish identical internal architectures. [1][3]

## 2. The Major Architectural Components

A web search engine can be understood through the following logical component groups.

| Component group | Primary responsibility | Typical input | Typical output |
|---|---|---|---|
| **Discovery system** | Identify resources that may be worth processing. | Links, known URLs, submitted URL lists, feeds, or other discovery sources. | Candidate URLs or resource references. |
| **Crawler / fetcher** | Request and retrieve accessible resources. | Candidate URLs and crawl instructions. | Retrieved responses, metadata, and resource content. |
| **Document processing system** | Interpret retrieved resources and extract useful information. | HTML, documents, media, response metadata, rendered content. | Structured representations and extracted features. |
| **Indexing system** | Organize processed information so it can be searched efficiently. | Processed document representations and associated data. | Searchable indexes and supporting data structures. |
| **Query processing system** | Interpret and prepare an incoming search request. | User query and relevant request context. | A normalized or otherwise prepared query representation. |
| **Retrieval system** | Find candidate items in searchable collections. | Prepared query and index structures. | Candidate documents or records. |
| **Ranking and evaluation systems** | Assess and order candidates for the request. | Candidate items, query, and contextual information. | An ordered or selected candidate set. |
| **Result generation and serving system** | Construct and deliver the response. | Selected candidates and presentation data. | Results returned to the user or requesting client. |

These are **functional responsibilities**, not a list of confirmed Google services. A real search engine may combine several responsibilities, split one responsibility across many services, or use additional components. Google's public documentation, for example, describes a large index distributed across thousands of computers, but does not publish a complete service-by-service architecture. [1]

## 3. The Two Main Processing Paths

The architecture is easier to understand when separated into two connected paths: the **content preparation path** and the **query-time path**.

### 3.1 Content Preparation Path

The content preparation path builds and maintains the information that can later be searched.

**Conceptual flow:**

`Discovery → Crawling → Document Processing → Indexing → Searchable Collections`

1. **Discovery** identifies URLs or other resources that may enter the system.
2. **Crawling** requests those resources and retrieves what the crawler can access.
3. **Document processing** interprets the retrieved material and extracts information that downstream components can use.
4. **Indexing** organizes the processed information into structures that support later search.

The output is not necessarily one simple database containing copies of every page. Search systems may maintain multiple indexes or collections for different kinds of information and use different acquisition methods. Google states that its Search information comes not only from web crawling but also from partnerships, data feeds, and sources such as the Knowledge Graph. [2]

The important architectural idea: **query-time search depends on information prepared before the query arrives**. A web search engine generally does not rebuild its entire view of the web from scratch every time someone searches.

### 3.2 Query-Time Path

The query-time path turns a user's request into a delivered search response.

**Conceptual flow:**

`User Query → Query Processing → Retrieval → Ranking / Evaluation → Result Generation → Serving`

1. **Query processing** prepares the request for the search system.
2. **Retrieval** locates candidate information in the searchable collections.
3. **Ranking and evaluation** assess candidate results for the request.
4. **Result generation** prepares the selected information for presentation.
5. **Serving** returns the response to the user.

Google describes serving as searching its index for matching pages and returning results it considers relevant. Bing describes matching the user's query against webpages in its index and using ranking algorithms to generate results. These are vendor-level descriptions; the detailed internal stages and their boundaries are not fully disclosed. [1][3]

Ranking appears here because it is an architectural responsibility in the query-time path. Its algorithms, signals, and evaluation mechanisms belong in **03 — Search Engine Algorithms** once that domain's documentation exists. This page does not attempt to explain how ranking works.

## 4. How the Two Paths Connect

The content preparation path and query-time path are connected through searchable indexes and related data stores.

The content path supplies information that the query path can search. The query path depends on the prepared data being sufficiently available and current for the system's purpose. When new or changed content is discovered and processed, the searchable collections may be updated; later queries can then use the updated information.

This relationship creates an ongoing cycle:

`Discover / Acquire → Process → Organize → Search → Refresh → Process Again`

It is a cycle, not a one-time publishing pipeline. The web changes, resources are added or removed, and existing content is updated. Google describes crawling as an ongoing process that revisits known pages and discovers new ones; it also explains that its information sources extend beyond crawling. [2]

Do not read the diagram as a strict schedule. The exact timing, update strategy, and coordination mechanisms vary by search engine and are not fully public.

## 5. Logical Components Are Not the Same as Physical Systems

An architecture diagram describes **what responsibilities a system must perform**. It does not automatically reveal **how those responsibilities are deployed**.

For example:

- A single logical crawler function may be carried out by many crawler processes.
- A logical index may be distributed across multiple machines or storage systems.
- Document processing may involve several specialized operations.
- Query handling may coordinate multiple services before a response is returned.

Google confirms that its crawling uses a huge set of computers and that its index is hosted across thousands of computers. This demonstrates large-scale distribution in Google's implementation, but it does not reveal the complete topology, service boundaries, or internal communication design. [1]

The distinction matters because a neat diagram can create false confidence. A box labeled “Indexing System” is a useful explanation of responsibility—not evidence that the provider runs one product or server with that exact name.

The deeper distributed computing, storage, networking, and operational questions belong in [02.10 — Search Engine Infrastructure](README.md#knowledge-structure).

## 6. Cross-Cutting Responsibilities

Not every important function fits neatly into one stage. Search systems also need responsibilities that influence multiple components.

Examples include:

- **Scheduling and coordination:** deciding which work should happen and when.
- **Access and policy handling:** applying rules or restrictions that affect what can be acquired or shown.
- **Quality and abuse controls:** identifying information or behavior that should affect processing or availability.
- **Monitoring and reliability:** detecting failures and maintaining service operation.
- **Data freshness and update management:** keeping stored information aligned with changes in source material.

These are generalized architectural responsibilities, not a claim that Google or Bing uses these exact component names or implements them in one particular way. Vendor documentation describes examples of such concerns: Google discusses crawl scheduling and access restrictions, while Bing documents content interventions and policy considerations in its search approach. [1][3]

Their detailed mechanisms are outside this page's scope. The point is that search architecture is more than a straight line from crawler to index to results.

## 7. Google Search as a Documented Example

Google's public explanation provides a useful real-world reference for the generalized model:

| General responsibility | What Google publicly documents |
|---|---|
| Discovery and acquisition | Google discovers URLs through previously known URLs, links, and submitted sitemaps; Googlebot may then crawl them. |
| Retrieval of source content | Googlebot fetches pages and may render them, including running JavaScript. |
| Processing and interpretation | Google analyzes page text, content attributes, images, videos, and other information. |
| Organization | Information about canonical pages and related signals may be stored in the Google index. |
| Query-time response | Google's systems search the index for matching pages and return results considered relevant to the query. |

This is a mapping between the conceptual component model and Google's published explanation—not a disclosure of Google's full internal architecture. Google groups several activities under its three public stages: crawling, indexing, and serving. [1]

Bing's public explanation offers a comparable high-level pattern: Bingbot crawls the web, information is used to build the Bing index, and algorithms generate results by matching queries with indexed webpages. That comparison supports the broad functional similarities while leaving implementation differences open. [3]

## 8. What This Architecture Model Does Not Tell Us

A conceptual architecture is useful, but it has clear limits.

It does **not** tell us:

- The exact number or names of Google's internal services.
- The complete structure, schema, or physical layout of any search index.
- The precise communication protocols between internal components.
- The complete scheduling, caching, replication, or failure-recovery design.
- The exact sequence of every operation for every query or document.
- The full ranking algorithms, signals, weights, or decision logic.

Those details should not be invented to make an architecture diagram look more technical. Public documentation supports a functional explanation; it does not grant access to proprietary implementation details.

## Summary

- Search engine architecture describes how system responsibilities and data flows fit together.
- A generalized web-search architecture has a content preparation path and a query-time path.
- The content path discovers, retrieves, processes, and organizes information.
- The query-time path prepares a query, retrieves candidates, evaluates them, and serves a response.
- Searchable indexes connect the two paths, while update processes keep information from becoming permanently stale.
- Logical components describe responsibilities; they do not reveal a provider's physical deployment or internal service map.
- Google and Bing publicly describe similar high-level functions, but their documentation does not establish identical implementations.

**Bottom line:** the search box is the visible tip. Underneath it is a system that continuously prepares information so a separate query-time process can find and deliver useful results.

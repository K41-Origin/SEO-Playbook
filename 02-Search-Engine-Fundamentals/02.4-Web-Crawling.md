# 02.4 — Web Crawling

Discovery puts a URL on a search engine's radar. **Crawling is the act of requesting and retrieving that resource.** Knowing a URL exists does not mean a crawler has visited it, and a successful visit does not guarantee that the content will be indexed.

This document explains the crawler's role, request lifecycle, access controls, response handling, revisit behavior, and crawl constraints. It uses Google Search as the primary documented example while keeping provider-specific behavior separate.

## 1. What Is Web Crawling?

**Web crawling** is the automated process of requesting resources from websites and retrieving their responses for possible downstream processing.

A crawler (also called a robot or spider) is software that automatically discovers and scans websites. In a search system, it typically works through a set of known or candidate URLs, requests resources, and makes retrieved data available to later processing stages. [1]

Crawling is not the same as:

- **Discovery:** learning that a URL exists. See [02.3 — Web Discovery](02.3-Web-Discovery.md).
- **Document processing:** interpreting the retrieved response, parsing content, or rendering a page. See [02.5 — Document Processing & Rendering](02.5-Document-Processing-and-Rendering.md).
- **Indexing:** deciding what information is organized and made searchable. See **02.6 — Search Indexing**.

A crawler retrieves. Other parts of the search system decide what happens next.

## 2. The Crawler and Its Inputs

A crawler operates on URLs or other resource references that the search engine already knows about. Those references may come from discovery mechanisms described in 02.3, previously crawled URLs, or internal scheduling and revisit systems.

A generalized crawler may consider:

- The URL and its host.
- Applicable crawl restrictions, including robots.txt rules.
- The crawler's own request schedule and available resources.
- The host's ability to respond reliably.
- Whether a resource has been requested before and may need revisiting.

This is a functional model, not a disclosure of any provider's internal queue, scheduler, or prioritization algorithm. Search engines do not publish every detail of how individual URLs are selected for fetching.

### 2.1 Crawler Identity

Crawlers identify themselves through request metadata such as the HTTP `User-Agent` header. Google documents Googlebot Smartphone and Googlebot Desktop as its two Google Search crawler types. Most Google Search crawling uses the smartphone crawler, reflecting Google's mobile-first indexing approach. [2]

A user-agent string alone is not proof that a request came from the named crawler: it can be spoofed. Google recommends verifying Googlebot requests through reverse DNS lookup or comparison with its published IP ranges. [2]

## 3. The Crawling Request Lifecycle

The following sequence is a generalized explanation of a crawl operation. Actual search engines may distribute, repeat, or combine these activities.

1. **Select a URL:** the crawler receives a URL selected for a crawl attempt.
2. **Check applicable access rules:** the crawler checks the relevant robots.txt policy and other provider-specific controls.
3. **Resolve and connect:** the crawler resolves the host and establishes a network connection using a supported protocol.
4. **Send an HTTP request:** the crawler requests the resource from the server.
5. **Receive the response:** the server returns an HTTP status code, headers, and—when available—a response body.
6. **Handle the outcome:** the crawler or its surrounding systems interpret the response, including redirects, errors, and rate-limiting signals.
7. **Pass retrieved material downstream:** successful responses may be handed to document processing. The crawler may also record information relevant to future crawl decisions.

Google documents that its crawlers use distributed machines across datacenters and support HTTP/1.1 and HTTP/2. This illustrates how large-scale crawling is implemented by Google; it should not be assumed to describe every search engine. [3]

## 4. Robots.txt and Crawl Access

The Robots Exclusion Protocol (REP), commonly implemented through a `robots.txt` file, lets website operators publish rules that request compliant crawlers not to access specified URL paths. Google states that its automated crawlers fetch and parse robots.txt before crawling a site. [4]

A few distinctions matter:

- **robots.txt controls crawling access, not guaranteed index removal.** A blocked URL may still be known to a search engine and may appear in results without its page content.
- **robots.txt is not authentication.** It is a publicly accessible set of crawler instructions, not a security boundary.
- **Rules are scoped.** For Google, a robots.txt file applies to the host, protocol, and port where it is served; a file on one subdomain does not automatically control another.
- **Crawler behavior is provider-specific.** Search engines may differ in how they interpret directives and handle errors when retrieving robots.txt. [2][4]

Do not confuse robots.txt with a `noindex` directive. Google must be able to crawl a page to see a page-level `noindex` instruction. If crawling is blocked, the crawler cannot read that instruction from the page. Google explicitly distinguishes using robots.txt to prevent crawling from using `noindex` to prevent indexing. [2]

The detailed syntax and implementation of robots directives belong with the relevant technical SEO documentation. Here, the key system-level point is that crawl access is governed by rules that crawlers must interpret before requesting resources.

## 5. HTTP Responses and Crawl Outcomes

A crawl request does not always return a usable page. The HTTP response tells the crawler what happened at the request level.

| Response category | General meaning | Google Search behavior documented by Google |
|---|---|---|
| `2xx` | Request succeeded. | Google may pass the received content to downstream processing. A successful response does not guarantee indexing. |
| `3xx` | Resource redirects elsewhere. | Google generally follows redirects and processes the final target rather than the redirecting response body. |
| `4xx` | Client-side request/resource error. | Google does not use content returned with these responses; previously indexed URLs may be removed over time. `429` is treated as a server-overload signal. |
| `5xx` | Server-side failure. | Google temporarily slows crawling; persistent server errors can eventually affect indexed URLs. |

These are broad categories. Individual status codes have distinct meanings and handling rules, so do not treat every response in a category as interchangeable. Google's documentation provides the detailed behavior for common status codes. [5]

Network and DNS failures can also prevent a crawler from obtaining a response at all. In those cases, there may be no HTTP status code because the request did not reach a functioning HTTP response stage. [5]

### 5.1 Conditional Requests and Unchanged Content

Some crawlers can use conditional HTTP requests to avoid downloading a full response when content has not changed. Google documents support for `If-Modified-Since` and `If-None-Match` in applicable crawling situations. When the server returns `304 Not Modified`, it indicates that the previously retrieved representation remains current, so the crawler does not need a new response body. Google notes that these headers are not sent on every crawl attempt. [7]

This is an efficiency mechanism, not a signal that a page should rank better.

## 6. Crawl Scheduling, Capacity, and Demand

Crawlers cannot request every known URL continuously. Search engines must allocate finite time, network capacity, and computing resources across many hosts while avoiding unnecessary load on websites.

For Google, the documented crawl-budget model combines two concepts:

- **Crawl capacity limit:** how much crawling a site can handle without being overloaded. Google says this is affected by server health, response times, latency, server errors, and rate-limiting responses such as HTTP 429.
- **Crawl demand:** how much Google wants to crawl a site. Google identifies factors including perceived URL inventory, popularity, content staleness, site size, and update frequency.

Google defines crawl budget through the interaction of crawl capacity and crawl demand. A healthy server alone does not force Google to crawl more; demand also matters. [8]

Google's crawl-budget guidance is primarily intended for very large or frequently updated sites. It says most sites do not need to actively manage crawl budget and should not treat it as a universal SEO problem. The size examples in Google's guide are rough classifications, not hard thresholds. [8]

### 6.1 Crawl Rate Is Not a Ranking Factor

Crawling is necessary for a page to be considered for Google's Search index, but increasing crawl rate does not itself improve ranking. Google explicitly rejects the idea that crawling is a ranking factor. [9]

More crawler requests are not automatically better. The useful question is whether important resources are being fetched reliably and often enough for the search engine's needs—not whether a site can generate an impressive crawl count.

### 6.2 Crawl Controls Differ by Search Engine

Google documents that its crawlers do not process the non-standard `Crawl-delay` directive in robots.txt. Do not assume that a crawler directive or control supported by one provider will be recognized by another. [9]

That difference is exactly why crawler rules should never be assumed to work identically across providers.

## 7. Revisiting Known URLs

Crawling is not a one-time event. Search engines may revisit known URLs to check for changes, refresh stored information, or respond to updated discovery and scheduling signals.

A revisit is not guaranteed on a fixed schedule. Google describes crawl demand as influenced by factors such as popularity, staleness, and update frequency; crawl capacity and server health also constrain what can be fetched. [8]

When a crawler revisits a URL, the response may indicate that:

- The resource is unchanged.
- The resource has changed and returns updated content.
- The URL redirects to another location.
- The resource no longer exists.
- The server is temporarily unavailable or limiting requests.

The crawler's response handling then determines what can be passed to later stages. A recrawl does not itself guarantee re-indexing, ranking changes, or faster visibility.

## 8. What Crawling Does—and Does Not—Guarantee

Crawling establishes that a crawler requested and retrieved—or attempted to retrieve—a resource. It does not establish that the resource will be indexed or shown in search results.

Keep these states separate:

| State | What it means |
|---|---|
| Discovered | The search engine knows the URL may exist. |
| Crawled | A crawler has requested the URL. The request may still have failed or returned an error. |
| Successfully fetched | The crawler received a successful response with content. |
| Processed | The retrieved material has been interpreted by downstream systems. |
| Indexed | The search engine has included selected information in its searchable index. |

The distinctions are not merely semantic. Google explicitly states that not every crawled page is indexed, and a successful HTTP response does not guarantee indexing. [5][8]

## 9. What This Means for SEO

From an SEO perspective, crawling is a search-engine-side process influenced by both crawler decisions and website availability.

At a high level, useful considerations include:

- Make important URLs discoverable through the mechanisms described in [02.3 — Web Discovery](02.3-Web-Discovery.md).
- Avoid unintentionally blocking resources that crawlers need to access.
- Return appropriate HTTP status codes for the actual state of each resource.
- Keep servers reliably available and avoid persistent overload responses.
- Avoid generating unnecessary URL variations that expand the crawlable URL inventory without adding distinct value.
- Verify crawler identity before treating automated requests as Googlebot or Bingbot traffic.

These points describe system interactions, not a complete implementation guide. Site architecture, robots.txt configuration, server response implementation, log analysis, and crawl diagnostics belong in **10 — Technical SEO** and related operational topics.

## Summary

- Web crawling is the automated requesting and retrieval of known web resources.
- Crawlers use request metadata and operate under access rules such as robots.txt.
- HTTP responses, redirects, network failures, and server availability affect crawl outcomes.
- Crawl scheduling balances crawler capacity, host health, and demand for revisiting content.
- Crawl budget is a specific Google concept primarily relevant to large or frequently updated sites—not a universal crisis for every website.
- Search engines differ in their crawler controls; for example, Google does not support robots.txt `Crawl-delay`, while Bing documents support.
- Crawling does not guarantee processing, indexing, ranking, or search visibility.

**Bottom line:** discovery tells a search engine where a resource might be. Crawling is when its crawler actually knocks on the server's door. Whether anything useful happens next is a separate question.

# 02.11 — Search Engine Types & Models

Not every search engine is trying to search the same universe. Some cover the public web. Others search one website, a company's private documents, a scholarly collection, or several independent databases at once.

The useful question is not just **what is this search engine called?** It is **what information can it search, how does that information enter the system, and where does the query get executed?**

## 1. What Search Engine Types & Models Describe

Search engines can be classified by several independent dimensions:

- **Search scope:** the subject or environment the system is designed to search.
- **Corpus:** the actual collection of documents, records, or other information available to the system.
- **Acquisition model:** how information enters the searchable collection.
- **Search architecture:** whether information is searched from a prepared index, queried from remote sources, or handled through a combination of both.

These dimensions overlap. An enterprise search system can be specialized, use a central index, and combine crawler-based acquisition with data connectors. A metasearch service can query multiple general-purpose web indexes without maintaining a comparable independent web index of its own.

So, treat the categories below as ways to describe a system—not as mutually exclusive boxes.

## 2. Types by Search Scope

### 2.1 General-Purpose Web Search Engines

A **general-purpose web search engine** is designed to help users find information across a broad portion of the publicly accessible web.

Its searchable corpus is assembled from web resources discovered and processed by the provider, alongside other information sources where applicable. Google describes its Search system as using automated crawlers to discover pages, adding selected information to an index, and searching that index when users submit queries. [1]

Examples include Google Search and Microsoft Bing. Both operate web-search services, but their public descriptions should not be treated as proof that their internal systems are identical.

**Typical characteristics:**

- Broad, continuously changing web corpus.
- Automated discovery and acquisition of web resources.
- Large searchable indexes.
- Queries that can concern many subjects and content types.
- Results selected from the provider's available corpus, not from every page on the internet.

General-purpose does not mean universal coverage. A web search engine cannot return information it has not acquired or cannot access, and indexing is not guaranteed. [1]

### 2.2 Vertical or Specialized Search Engines

A **vertical search engine** focuses on a defined subject, industry, content type, or resource collection instead of attempting to cover the web broadly.

Examples of vertical search contexts include:

- Scholarly articles and academic publications.
- Products, retailers, and shopping catalogs.
- Travel listings and accommodation inventory.
- Jobs, careers, and professional opportunities.
- Images, videos, maps, or other media collections.

A vertical engine may build its corpus from focused crawling, licensed data, publisher feeds, APIs, structured catalogs, or a combination of sources. The acquisition method depends on the collection and the rights or access arrangements involved. NISO's library discovery guidance, for example, describes central indexes assembled from content supplied by multiple publishers and providers. [2]

**Why specialization matters:** a narrower corpus can support metadata, filters, terminology, and workflows that make sense for that subject. But the system is only as comprehensive as its sources and coverage. A specialized search engine is not automatically more accurate; relevance still depends on the quality, freshness, and scope of its underlying data.

### 2.3 Site Search

**Site search** lets users search content within a particular website or web application.

The corpus is usually limited to the site's own pages, products, help articles, or other exposed content. Depending on the implementation, the system may crawl site URLs, ingest content through an API or connector, or query an application's own data store. Site search can be powered by a dedicated search platform or by functionality built into the website itself. [3]

Site search is not the same as public web search:

- Its corpus is controlled by the site or service.
- Its search behavior can be tailored to the site's content and user tasks.
- Its results are not automatically part of a public search engine's index.

A search box on a website is an interface, not proof of a particular search architecture. The backend could be a full-text index, a database query, a third-party service, or a hybrid implementation.

### 2.4 Enterprise Search

**Enterprise search** helps people find information across an organization's data sources, which may include internal documents, databases, collaboration systems, knowledge bases, and business applications.

Unlike public web search, enterprise search commonly operates over restricted or permission-controlled information. Systems may use crawlers, APIs, connectors, or direct data ingestion to build searchable collections. Results must respect the access rights associated with the underlying information. [3]

Enterprise search can be implemented in several ways:

- **Siloed search:** users search individual repositories separately.
- **Federated search:** one query is sent to multiple repositories or search services.
- **Unified or centrally indexed search:** content from multiple sources is brought into a common index and presented through one search experience.

These labels describe common design patterns, not a universal product taxonomy. Vendors may use the terms differently, so inspect the actual data flow before assuming how a system works. [3]

### 2.5 Metasearch and Federated Search

**Metasearch** and **federated search** let a user search across multiple underlying sources through one interface.

In a typical federated flow, the system:

1. Receives a query.
2. Selects the sources that should be searched.
3. Translates or adapts the query for those sources when necessary.
4. Sends requests to multiple remote systems.
5. Collects the returned results.
6. Coordinates, deduplicates, groups, or merges those results for presentation.

NISO defines federated search around sending appropriately structured queries to multiple remote search engines and coordinating the results. It notes that *metasearch* is sometimes used as a synonym, although the term can also describe searching multiple sources held in one location. Terminology is not perfectly consistent across fields. [2]

A key distinction: a metasearch system may rely on other engines' indexes rather than maintaining a full independent index of the underlying content. Its work is therefore heavily concerned with source selection, query distribution, and result aggregation. [2][4]

Federated search has trade-offs:

- It can reach sources that are not combined into one central index.
- Source-specific access rules and coverage can be preserved.
- Query translation and result merging can be difficult.
- Response time can depend on remote systems and network conditions.
- Different sources may return overlapping results or incompatible relevance scores.

NISO's library discovery guidance documents performance and integration limitations associated with real-time metasearch across multiple resource targets. These constraints are implementation-dependent, not a claim that every federated system performs poorly. [2]

## 3. Types by Corpus and Acquisition Model

Search scope tells us *what* a system searches. Corpus and acquisition describe *which information is actually available* and *how it gets there*.

| Corpus or acquisition model | Description | Common context |
|---|---|---|
| **Open-web corpus** | Public web resources acquired and processed by a web search provider. | General-purpose web search. |
| **Focused or curated corpus** | A collection limited by topic, content type, provider, or editorial scope. | Scholarly, product, travel, and media search. |
| **First-party corpus** | Content owned or published by the organization operating the search experience. | Site search and product catalogs. |
| **Private organizational corpus** | Internal or access-controlled organizational information. | Enterprise and workplace search. |
| **Aggregated corpus** | Content or metadata supplied by multiple independent providers. | Library discovery and specialized indexes. |
| **Remote-source corpus** | Information remains in separate systems and is queried when a search request arrives. | Federated and metasearch systems. |

These are descriptive categories, not a standardized classification. A system may combine several of them. For example, an enterprise index can aggregate internal documents from multiple repositories while preserving document-level permissions. [2][3]

Acquisition also differs:

- **Crawling:** the system discovers and fetches accessible resources.
- **Feeds and data submissions:** providers supply structured records or updates.
- **APIs and connectors:** the search system imports or synchronizes information from other applications.
- **Federated querying:** the system requests results from remote sources at query time rather than first consolidating all source content into one index.

Google's public web-search documentation is a clear example of crawler-based acquisition for general web search. Enterprise and library discovery systems demonstrate why crawling is not the only way to build searchable collections. [1][2][3]

## 4. Search Architecture Models

The same search scope can be implemented using different architectures. Two broad models help explain the main difference.

### 4.1 Centrally Indexed Search

In a **centrally indexed model**, information from one or more sources is collected and organized into an index that the search system can query.

**Simplified flow:**

`Source systems → Acquisition / ingestion → Processing → Central index → Query → Results`

The index may contain full text, metadata, or other representations of source content. NISO describes central-index discovery services that aggregate content from multiple providers into a common searchable index. [2]

**Potential advantages:**

- Query-time search does not need to contact every source independently.
- Information from different providers can be searched through a more consistent interface.
- The system can apply common processing and retrieval behavior across the indexed corpus.

**Trade-offs:**

- The index must be built and maintained as source data changes.
- Newly changed information may not appear until the index is updated.
- Access rights and licensing conditions must be reflected in what can be indexed or displayed.
- The index may not contain every item available from every source. [2]

Google's web search is a documented example of an index-based model: Google explains that it crawls and processes web pages, stores selected information in its index, and searches that index when a query arrives. This is a public high-level description, not a disclosure of Google's complete internal architecture. [1]

### 4.2 Federated or Query-Time Search

In a **federated model**, the system sends a query to multiple source systems when the user searches, then coordinates their responses.

**Simplified flow:**

`User query → Source selection → Query distribution → Remote searches → Result aggregation → Response`

The system may maintain metadata about sources or their capabilities, but the content being searched can remain in the remote systems. NISO's definition of federated search explicitly describes query restructuring, dispatch to remote search engines, and coordination of returned results. [2]

**Potential advantages:**

- Sources can retain control over their own content and systems.
- Results may reflect source data without first copying the full collection into a central index.
- A single interface can search otherwise separate repositories.

**Trade-offs:**

- Remote response times affect the overall search experience.
- Query syntax and capabilities may differ between sources.
- Results may need normalization, deduplication, and merging.
- A failed or slow source can reduce the completeness of the response. [2][4]

### 4.3 Hybrid Search Architectures

A **hybrid architecture** combines central indexing with query-time access to one or more external sources.

For example, a system might search a local index for most content while querying a remote database for records that must remain in the source system. This is a general architectural pattern derived from the centrally indexed and federated models; its exact behavior depends on the implementation. [2]

The practical lesson: real search products do not have to choose one pure architecture. Their design can vary by source, data type, licensing, freshness requirements, and access constraints.

## 5. A Search Engine Can Fit More Than One Category

Consider these examples:

| System description | Scope type | Corpus / architecture |
|---|---|---|
| A public engine searching across the web | General-purpose web search | Broad web corpus; crawler-based acquisition and maintained index. |
| A service searching research papers from multiple publishers | Vertical / specialized search | Curated or aggregated corpus; central index, federation, or both. |
| A retailer's product search | Site search / vertical search | First-party product catalog, often ingested into a dedicated index. |
| An employee portal searching internal files and applications | Enterprise search | Private corpus; connectors, central index, federated queries, or hybrid design. |
| A single interface forwarding queries to several independent search providers | Metasearch | Remote-source model; query distribution and result aggregation. |

The table is a conceptual classification, not a claim about the architecture of any named commercial product.

## 6. What These Models Do Not Tell Us

Knowing that a system is a web search engine, vertical engine, site search, or federated service does not reveal its complete retrieval behavior.

This topic does **not** explain:

- The mathematical foundations of Boolean, vector-space, probabilistic, or language-model retrieval. Those belong in **04 — Information Retrieval**.
- How ranking signals and ranking systems order results. That belongs in **03 — Search Engine Algorithms**.
- How a query is interpreted or how search intent is classified. Query handling is covered in **02.7 — Query Processing**; SEO search intent belongs in **05 — Keyword & Search Intent**.
- The detailed infrastructure required to operate distributed search services. That belongs in **02.10 — Search Engine Infrastructure**.
- How results are visually arranged into a search results page. That belongs in **06 — SERP & Search Features**.

Terms such as *lexical*, *semantic*, *vector*, and *hybrid retrieval* describe retrieval approaches or capabilities, not search-scope categories. They should not be mixed into the same taxonomy without explaining which dimension is being classified.

## 7. Why This Matters for SEO

For SEO, the most important distinction is whether the target is a **public web search engine** or another kind of search system.

- **Public web SEO** concerns making public web content accessible and understandable to web search engines such as Google. Their discovery, crawling, indexing, and serving processes determine whether content can enter their searchable collections. [1]
- **Site search optimization** concerns helping visitors find information within a specific website or application. It is a product and information-architecture concern, not automatically a Google ranking task. [3]
- **Enterprise search** concerns internal information discovery, data integration, and permission-aware access. It is not the same discipline as public-web SEO. [3]
- **Vertical search** depends on the data sources, metadata, eligibility rules, and coverage of the specialized system. Do not assume that public-web SEO practices transfer unchanged to every vertical platform.

A page appearing in Google Search does not mean it will appear in a retailer's product search, a scholarly database, or an organization's internal search. Different systems search different corpora and operate under different constraints.

**Bottom line:** before optimizing for a search system, identify what it actually searches. Optimizing for the wrong corpus or architecture is just doing work for an audience that does not exist.

## Summary

- Search engines differ by scope, corpus, acquisition method, and architecture.
- General-purpose web engines search broad web collections; vertical engines focus on a defined subject or content type.
- Site search covers a website or application, while enterprise search covers organizational information that may be private or permission-controlled.
- Metasearch and federated search query multiple sources and coordinate their responses; terminology varies across fields.
- Centrally indexed systems search information consolidated into a maintained index. Federated systems query remote sources at search time. Hybrid systems combine both.
- These categories overlap. A system can be specialized, enterprise-focused, and hybrid at the same time.
- Search type alone does not reveal the system's ranking algorithms or detailed retrieval model.

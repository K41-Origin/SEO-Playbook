# 07.6 — URL Structure & Page-Level URL Optimization

A URL is not a place to pile up keywords. It is an address for a resource. Its design should be understandable to people, consistent with site structure, and avoid unnecessary variations.

This domain covers editorial decisions about **page URL wording and structure**. Redirects, canonicalization, technical parameters, crawl controls, and indexing remain owned by Domain 10 — Technical SEO.

## 1. What a Page URL Represents

A URL (Uniform Resource Locator) identifies a resource's location and how it can be accessed. RFC 3986 (IETF STD 66) defines the generic URI syntax used as the standards reference for URLs. [5] For a web page, the published URL is an address that can be shared, linked, saved, and requested by browsers and crawlers.

One page may have several URLs that return the same or similar content. URL design therefore involves more than creating a readable slug; address consistency and the site's technical behavior also matter. Google explains that complex URLs can create many variations for the same or similar content and make crawling less efficient. [1]

## 3. Principles for Descriptive URL Design

### 3.1 Make the path understandable
Use words that describe the page's content or function. Google recommends descriptive URLs with readable words rather than long IDs that provide no context. [1]

- Clear: /blog/technical-seo-audit/
- Opaque: /p?id=84729&x=19

Numeric IDs remain valid when required by a system. The point is not to ban IDs, but to avoid sacrificing readability without a reason.

### 3.2 Use language your audience understands
Choose language appropriate to the audience and site context. Google recommends using the audience's language in URLs; transliteration may be appropriate where relevant. [1] There is no requirement that every site use English. Audience comprehension and consistency matter more than copying another site's URL style.

### 3.3 Separate words with hyphens
For multiword slugs, use hyphens (-) as separators. Google explicitly recommends hyphens over underscores (_) because they mark word boundaries more clearly. [1]

- Recommended: /technical-seo/
- Less preferred: /technical_seo/
- Avoid ambiguous joining: /technicalseo/

This is Google's URL recommendation, not evidence that replacing underscores with hyphens automatically improves rankings.

### 3.4 Keep paths concise without removing meaning
Remove words or segments that do not help distinguish the page. Do not remove so much context that the URL becomes ambiguous.

- Too vague: /guide/
- More descriptive: /guide/url-structure/
- Needlessly verbose: /complete-ultimate-definitive-guide-to-url-structure-for-everyone/

Google does not define a universal URL character limit. Do not invent a length threshold and present it as an official ranking rule.

### 3.5 Organize paths logically
Directories can group pages according to meaningful site structure, for example /products/, /support/, or /blog/.

Google notes that logical directory structures can help explain how site content is grouped and how URLs in a directory change. But folder structure is not a reason to create excessive path depth. [2] Paths should reflect real information architecture, not decoration.

### 3.6 Be consistent with casing
URLs are case-sensitive in Google's URL handling. /Guide/ and /guide/ may therefore be treated as different URLs. If a server treats them the same, Google recommends consistent casing to make URL identity clearer. [1]

For new designs, lowercase is usually a simple editorial convention. Do not mass-change existing URLs merely to alter capitalization without a proper technical plan.

## 4. Slug Design and Naming

A slug is the path segment commonly used to identify a particular page, such as url-structure in /guides/url-structure/.

Slug workflow:
1. Define the page's purpose and main topic.
2. Choose the clearest term representing the page.
3. Remove additions that do not help identification.
4. Separate words with hyphens.
5. Use consistent language and casing.
6. Check for conflicts or ambiguity with other pages.
7. Preserve stable slugs unless there is a strong reason to change them.

Illustrative examples:

| Page context | Clear slug | Note |
|---|---|---|
| URL structure guide | /guides/url-structure/ | Topic is immediately understandable |
| Running shoe category | /shoes/running/ | Represents category within site hierarchy |
| Keyword research article | /blog/keyword-research-basics/ | Describes topic without forcing every query variation |

These are not mandatory templates. Choose a pattern that fits the site's content model and navigation.

## 5. Keywords in URLs: Useful Context, Not a Ranking Hack

Words in a URL can help people understand a page's purpose and provide additional resource context. Google also recommends descriptive URL wording. [1] However, this documentation does not provide a ranking weight, formula, or promise of position gains for keywords in URLs.

Therefore:
- use the main term when it makes the address more descriptive;
- do not insert every keyword variation into the slug;
- do not repeat the same word several times;
- do not create a new URL for each query variation when one page meets the same need;
- do not change a stable slug solely to chase an exact-match keyword without a stronger reason.

Target keywords and page mapping come from [Domain 05 — Keyword & Search Intent](../05-Keyword-and-Search-Intent/README.md). Domain 07 translates that context into sensible page elements; it does not turn URLs into keyword lists.

## 6. URL Parameters and Fragments: Know the Boundary

Query parameters appear after a question mark, for example: /products?color=black&sort=price-low.

Parameters may genuinely change page content or display, such as product filters. Others may be used only for tracking or sessions and do not change content. Google recommends reducing unnecessary parameters because excessive URL variations can cause crawlers to spend resources on similar URLs. [1][3]

For page-level decisions:
- do not add parameters that serve no real page function;
- do not assume all parameters are bad; filters, internal search, and application functions may require them;
- keep user-visible URL patterns understandable;
- document parameters that materially change content so the technical team can review them.

A fragment uses a hash, such as /guide#examples, and can point to a section within a document. Google says URL fragments generally are not supported as a way to change page content in Search. For JavaScript applications that change content, Google recommends the History API rather than relying on fragments as distinct page URLs. [1]

Faceted-navigation crawling, parameter normalization, robots.txt, canonicalization, and application routing belong to Domain 10. Do not try to solve these technical problems by changing a slug.

## 7. URL Design for Multilingual and Multi-Regional Sites

Multilingual or multi-regional sites need a consistent, understandable URL pattern. Google describes several possible patterns, including country-code top-level domains, subdomains, and subdirectories. Each has operational trade-offs; no single pattern is automatically best for every site. [4]

Examples:
- Country-code domain: example.de
- Subdomain: de.example.com
- Subdirectory: example.com/de/

Domain 07.6 covers readability and path-pattern consistency only. Language/country targeting, hreflang, cross-language canonicalization, and regional configuration belong to Domain 10 and Domain 13 — International & Local SEO.

## 8. URL Changes: Do Not Rename Pages Casually

Changing a slug changes a resource address. Old links, bookmarks, external references, and tracking systems may be affected. A new URL does not automatically replace the old one in search engines.

Before changing a published URL, establish a clear reason—for example, the old address is misleading, the content structure has permanently changed, or a site migration requires it.

The change plan must involve the technical team to:
- map old URLs to the most relevant destination URLs;
- prepare appropriate permanent redirects;
- update internal references and sitemaps;
- check canonical signals and HTTP responses;
- monitor crawling, indexing, and errors after launch.

Google says redirects and rel=canonical are strong canonicalization signals, while sitemaps are weaker signals. Implementation details belong to Domain 10. [3]

Do not change a URL merely because the old slug lacks a target keyword. Migration risk needs a proportionate reason.

## 9. Practical URL Design Workflow

For a new page:
1. **Confirm page purpose.** Ensure its function is clear and does not duplicate another page.
2. **Review site architecture.** Select a category or directory based on real content structure.
3. **Draft a descriptive slug.** Use specific, audience-familiar, concise wording.
4. **Apply naming conventions.** Follow site rules for hyphens, casing, language, and trailing slashes.
5. **Check uniqueness.** Ensure the address does not conflict or create ambiguity.
6. **Review query parameters.** Distinguish functional parameters from unnecessary ones.
7. **Confirm technical feasibility.** Ask the Domain 10 owner to validate routing, response status, canonical, and redirects.
8. **Record the decision.** Document the final URL and reasons for any deviation from site conventions.

For an existing live page, begin by auditing the current URL. Do not start with a bulk rename.

## 10. Quality-Control Checklist

This checklist assesses design quality, not ranking.

- [ ] URL accurately describes the page.
- [ ] Wording is understandable to the audience.
- [ ] Slug is not unnecessarily long or ambiguous.
- [ ] Words are separated with hyphens where appropriate.
- [ ] Casing follows site conventions consistently.
- [ ] Path reflects a sensible site structure.
- [ ] No keyword stuffing or purposeless repetition.
- [ ] Unnecessary parameters are not added.
- [ ] Final URL is unique within site routing.
- [ ] A live URL change has a technical plan and old-to-new URL mapping.

## 11. Common Misconceptions

| Misconception | Reality |
|---|---|
| URLs must be shorter than a specific character count. | Google sets no universal URL length limit as a ranking rule. Prioritize clarity and function. |
| Keywords in URLs guarantee higher rankings. | Google recommends descriptive URLs but does not promise ranking gains from slug keywords. |
| Every URL must use English. | Google recommends the audience's language; choice depends on site context. |
| Hyphens are a ranking boost. | Hyphens are recommended as word separators; do not turn this into an automatic ranking claim. |
| All parameters must be removed. | Functional parameters may be necessary. Focus on unnecessary parameters and excessive variations. |
| Deeper folders are always better. | Structure should be logical, not as deep as possible. |
| Changing a slug always improves SEO. | Address changes have consequences and need a reason and proper migration implementation. |
| Canonical is the editor's preferred slug. | Canonicalization is a technical process and search-system decision; a slug is only part of an address. |

## Key Takeaways

- URL design is part of page experience and structure, not a keyword trick.
- Use descriptive, readable, consistent paths in the audience's language.
- Google recommends hyphens as word separators and reducing unnecessary parameters.
- There is no universal URL character limit or ranking guarantee from keywords in URLs.
- Do not change live URLs without a reason and technical migration plan.
- Canonicalization, redirects, parameter handling, and crawl/index controls belong to Domain 10.

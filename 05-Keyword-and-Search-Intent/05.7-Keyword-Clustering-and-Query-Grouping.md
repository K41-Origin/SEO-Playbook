# 05.7 — Keyword Clustering & Query Grouping

A keyword list is not a content plan. Before deciding which queries belong together, establish whether they represent the same underlying need and whether one page could satisfy them without becoming a confused mess.

This topic explains how to group related search queries into practical SEO keyword clusters. It combines intent, SERP overlap, task relevance, and lexical or semantic similarity while preserving meaningful differences between queries.

**A cluster is a research decision—not proof that Google treats every query in it as identical, and not an automatic instruction to publish one page.**

## 1. What Is Keyword Clustering?

**Keyword clustering** is the process of grouping related queries into sets that share a sufficiently similar search goal, task, topic focus, or result pattern for a defined SEO research purpose.

A **keyword cluster** is the resulting group. Depending on the project, it may represent:

- Queries that express the same need with different wording.
- Variations of a query that lead to substantially similar SERP result sets.
- Closely related subtopics that can reasonably be addressed by one focused page.
- A main query and its supporting long-tail formulations.

The grouping criterion must be explicit. “These keywords look similar” is not a defensible methodology by itself.

In search research, query groups can represent different facets or senses of an ambiguous query. Academic work on query-subtopic mining shows that web queries can be ambiguous and multifaceted, and that query refinements and clicked URLs can provide evidence about distinct subtopics. That research concerns search-log data and search-system applications; it supports the existence of query facets, not a universal SEO clustering formula. [1]

## 2. Why Clustering Matters

Clustering turns a large candidate-query set into a structure that can support later decisions.

It helps researchers:

- See which query variations may be served by one coherent page.
- Separate queries that look alike but represent different tasks.
- Identify broad topics with multiple distinct subtopics.
- Reduce redundant page-targeting proposals.
- Preserve secondary and ambiguous intents instead of flattening them.
- Prepare a traceable handoff to prioritization in 05.8 and keyword-to-page mapping in 05.9.

Clustering does **not** prove that publishing one page per cluster is always correct. A cluster is a research hypothesis about query relationships and potential page scope. Page assignment still requires business context, site architecture, content feasibility, and a final review in 05.9.

## 3. The Evidence Used to Group Queries

No single signal is sufficient in every case. Use several evidence types and record what each one can—and cannot—tell you.

### 3.1 Search Intent

Use the intent hypotheses from [05.5 — Search Intent Concepts & Taxonomies](05.5-Search-Intent-Concepts-and-Taxonomies.md) as an early grouping signal.

Queries are stronger cluster candidates when their primary goals align. For example, two queries seeking product comparisons may be closer to one another than a comparison query and a query seeking a repair tutorial—even if both contain the same product name.

Check:

- Primary intent.
- Secondary or mixed intent.
- The task the searcher appears to be trying to complete.
- The expected depth and type of answer.
- Whether one query expresses a materially different stage of decision-making.

Intent labels are hypotheses, not hard-coded truth. If the labels are uncertain, keep that uncertainty visible rather than forcing a clean-looking cluster.

### 3.2 SERP Overlap

SERP overlap compares the result URLs returned for two queries under comparable search conditions. If two queries repeatedly surface many of the same relevant pages, that overlap can be evidence that the search engine is satisfying them with similar result sets.

Use the observations from [05.6 — SERP-Based Intent Analysis & Validation](05.6-SERP-Based-Intent-Analysis-and-Validation.md). Compare the same search engine, market, language, device, collection period, and result depth. Otherwise, differences in collection conditions can masquerade as query differences.

A simple set-based measure is the **Jaccard similarity**, which compares the intersection of two sets with their union. [5]

`J(A,B) = |A ∩ B| / |A ∪ B|`

Where:

- `A` is the set of unique organic result URLs observed for query A.
- `B` is the set of unique organic result URLs observed for query B.
- `A ∩ B` is the set of URLs present in both result sets.
- `A ∪ B` is the set of URLs present in either result set.

The score ranges from 0 (no shared URLs) to 1 (identical URL sets). It is a descriptive comparison of the collected sets—not a Google metric, ranking signal, or calibrated probability that two queries need one page.

A practical workflow may also record the number of shared URLs within the top *k* results. If using ranked overlap measures, document the formula and weighting. Do not compare scores produced with different result depths or different collection contexts as though they were equivalent.

Treat any SERP-overlap threshold as a team- or vendor-defined heuristic unless its calibration and validation are documented. Calibrate it against manual review and the actual market; do not present a tool's threshold as a search-engine rule.

### 3.3 Lexical Similarity

Lexical similarity examines shared words, phrases, modifiers, and query structure.

Examples of useful clues:

- Singular and plural forms.
- Word-order variations.
- Common abbreviations or spelling variants.
- Closely related modifiers.
- Question forms that preserve the same task.

Lexical similarity is useful for finding candidates, but it can over-group ambiguous terms. “Coffee grinder repair” and “best coffee grinder” share words while expressing different tasks. A matching vocabulary is not the same as a matching need.

### 3.4 Semantic and Task Similarity

Semantic similarity asks whether queries express related meanings. Task similarity asks whether a searcher could reasonably complete the same underlying task with one focused answer.

These signals can help identify relationships that exact wording misses. They can also create false positives: two queries may be semantically close while requiring different evidence, page formats, or actions.

Computational similarity models are aids for candidate discovery and review. Their scores depend on the representation, model, language, and data used. The formal theory and mechanics of retrieval representations and similarity methods belong to Domain 04; this topic focuses on how SEO researchers use such evidence in practical grouping decisions.

### 3.5 Business and Audience Context

A cluster also needs a defined research purpose. Consider:

- The product, service, or subject the site genuinely covers.
- Audience segment and market.
- The task the business can credibly help with.
- Whether a query is relevant to the site's offering.
- Whether the apparent subtopic belongs in the current research project.

Business relevance does not change what a query means. It determines whether that query group is in scope for this site's research.

### 3.6 Evidence Comparison

| Evidence | What it helps establish | Main limitation |
|---|---|---|
| Search intent | Whether queries appear to express similar goals | Intent is inferred and can be mixed or ambiguous |
| SERP overlap | Whether observed result sets share destinations | SERPs vary by context and time; overlap is not a universal page rule |
| Lexical similarity | Whether queries share wording and patterns | Similar words can hide different tasks |
| Semantic similarity | Whether queries express related meanings | Model similarity does not guarantee one-page satisfaction |
| Task similarity | Whether one answer could satisfy the underlying tasks | Requires human interpretation and subject knowledge |
| Business context | Whether the group is relevant to the site's scope | Relevance to the business does not prove query equivalence |

## 4. Practical Clustering Approaches

Different approaches solve different parts of the problem. Use the simplest method that gives a defensible result; complexity is not a substitute for judgment.

### 4.1 Manual Clustering

A researcher reviews queries, intent labels, SERP observations, and task meaning, then assigns queries to groups.

Best suited to:

- Small or strategically important query sets.
- Ambiguous queries.
- New markets with limited data.
- Final review of machine-generated clusters.

Strength: context-sensitive judgment.

Limitation: slower and potentially inconsistent between reviewers. Define grouping rules and record rationale to improve repeatability.

### 4.2 Rule-Based Clustering

Rules group queries using explicit conditions, such as shared seed terms, modifiers, intent labels, or known query patterns.

Best suited to:

- Normalizing obvious variants.
- Separating clearly different modifiers or tasks.
- Preparing a candidate set for manual or SERP-based review.

Strength: transparent and repeatable.

Limitation: rules can become brittle. A rule that groups every query containing the same product term will happily merge comparison, purchase, troubleshooting, and informational queries. It has no shame; it also has no understanding.

### 4.3 SERP-Overlap Clustering

Queries are grouped when their observed organic result sets share enough relevant URLs under a consistent observation protocol.

Best suited to:

- Comparing close query variants.
- Testing whether similar wording produces similar result sets.
- Reviewing whether separate queries may be served by a common page type.

Strength: uses observed search results rather than wording alone.

Limitation: collection is time- and context-sensitive; result overlap can change; a shared URL may address only one part of a mixed query. A numerical threshold does not eliminate the need for review.

### 4.4 Semantic or Embedding-Assisted Clustering

A language model or embedding-based system can identify candidate groups based on represented meaning.

Best suited to:

- Large query sets where manual first-pass review is impractical.
- Discovering paraphrases or related formulations with limited word overlap.
- Generating candidate relationships for human validation.

Strength: can surface relationships that simple string matching misses.

Limitation: model similarity is not proof of shared search intent, SERP equivalence, or page suitability. Record the model, version, language, preprocessing, and threshold if the result materially informs decisions. Human review remains necessary for high-impact clusters.

### 4.5 Hybrid Clustering

A hybrid process uses lexical and semantic signals to generate candidates, intent and task analysis to assess meaning, and SERP overlap to test observed result similarity.

For most practical SEO research, this is a strong default because it avoids treating one signal as the whole answer. It is a recommended workflow in this playbook, not a published Google method or a proven universally optimal algorithm.

## 5. A Practical Keyword Clustering Workflow

### Step 1 — Start With a Clean Query Set

Use the expanded and evaluated query candidates from [05.3 — Keyword Expansion & Query Variations](05.3-Keyword-Expansion-and-Query-Variations.md) and [05.4 — Keyword Data Sources & Metrics](05.4-Keyword-Data-Sources-and-Metrics.md).

Before clustering:

- Preserve the original query text.
- Normalize formatting without erasing meaningful wording.
- Remove exact duplicate records while retaining source provenance.
- Keep meaningful modifiers and qualifiers.
- Separate different markets and languages unless cross-market grouping is intentional.
- Retain source, date, and metric context where available.

Do not collapse singular/plural, spelling, or word-order variants automatically. Check whether the variant changes meaning, intent, or observed SERP behavior.

### Step 2 — Attach Intent and Task Evidence

Bring forward the primary and secondary intent hypotheses from 05.5 and the validation outcomes from 05.6.

For each query, record:

- Primary intent.
- Secondary intent, if meaningful.
- Underlying task.
- Confidence and rationale.
- SERP validation status.
- Market and language.

If a query has not been validated, mark it as unvalidated. Do not quietly treat missing evidence as confirmation.

### Step 3 — Generate Candidate Relationships

Use one or more discovery signals:

- Shared lexical patterns and modifiers.
- Similar task descriptions.
- Semantic similarity.
- Similar SERP result URLs.
- Shared audience or product context.

At this stage, produce candidate pairs or groups. Do not force every query into a final cluster immediately.

### Step 4 — Compare the SERPs Where It Matters

SERP review is especially useful when:

- Two queries have similar wording but may express different goals.
- A proposed cluster will influence an important page decision.
- Automated similarity signals disagree.
- The query is broad, ambiguous, or mixed-intent.
- The market or language has substantial variation.

Use the same observation context defined in 05.6. Record the result depth and date. If the SERP data is stale or collected under incompatible conditions, treat the comparison as weak evidence.

### Step 5 — Apply the Same-Task Test

Ask:

1. Are the queries seeking substantially the same outcome?
2. Could one focused page satisfy both without diluting either answer?
3. Would the same page format and depth make sense for both?
4. Do their observed SERPs support a common result pattern?
5. Is any difference merely wording, or does it change the task or decision?
6. Would combining them create a page trying to do two incompatible jobs?

If the answer to the same-task questions is unclear, keep the queries separate or mark the relationship as provisional.

### Step 6 — Assign Cluster Structure

A useful cluster record can include:

- **Cluster ID:** stable identifier for tracking.
- **Cluster label:** concise description of the shared topic or task.
- **Primary query:** representative query selected for research convenience.
- **Member queries:** all queries currently assigned to the group.
- **Primary and secondary intent:** the best-supported goal labels.
- **Task statement:** what the searcher is trying to accomplish.
- **SERP evidence:** overlap observations and representative destinations.
- **Grouping rationale:** why the queries belong together.
- **Confidence:** high, medium, or low, with a written reason.
- **Exceptions:** queries or modifiers that do not fit cleanly.
- **Status:** provisional, validated, split, merged, or rejected.
- **Next action:** review, prioritize in 05.8, or map in 05.9.

The primary query is a label for the cluster, not a claim that every member is a synonym or that the page should repeat every variant.

### Step 7 — Review Cluster Boundaries

Check for:

- Different primary intents hidden under one broad topic.
- Product research mixed with troubleshooting.
- Informational questions mixed with action or transaction tasks.
- Local and non-local queries mixed without market rationale.
- Different audiences or use cases requiring distinct answers.
- A broad query whose subtopics deserve separate treatment.
- Low-confidence assignments driven by wording alone.

Split a cluster when its members require materially different answers or page purposes. Merge clusters when their apparent differences are only wording and the evidence supports a shared task and result pattern.

### Step 8 — Preserve the Decision History

Do not overwrite the reasoning when a cluster changes. Record:

- Original candidate grouping.
- Evidence that supported the grouping.
- Evidence that challenged it.
- Queries added, removed, split, or merged.
- Date and reviewer.
- Reason for the decision.

This makes later changes explainable when SERPs, markets, or the research scope change.

## 6. Cluster Boundaries: When to Merge, Split, or Keep Separate

### Merge when

- The queries express substantially the same task.
- Their primary intent and expected answer are aligned.
- SERP observations show meaningful overlap under comparable conditions.
- One focused page could satisfy the member queries without sacrificing clarity.
- Differences are mainly wording, spelling, or close modifiers that do not change the task.

### Split when

- The queries require different tasks or outcomes.
- Primary intents materially differ.
- SERP result sets consistently surface distinct destination types or page purposes.
- One page would need incompatible structures or calls to action.
- The queries represent distinct subtopics that deserve separate treatment.

### Keep provisional when

- Intent is mixed or uncertain.
- SERP evidence is unavailable, stale, or inconsistent.
- Queries have low data coverage.
- Automated methods disagree.
- Market, language, or device context has not been controlled.
- There is not enough evidence to distinguish a meaningful difference.

A provisional cluster is better than false certainty dressed up as a tidy spreadsheet.

## 7. Over-Clustering and Under-Clustering

### 7.1 Over-Clustering

**Over-clustering** happens when queries that should remain separate are forced into one group.

Common causes:

- Grouping solely by shared words or seed keywords.
- Treating a broad topic as one search task.
- Ignoring mixed or distinct intent.
- Using a loose semantic-similarity threshold without review.
- Assuming every shared SERP URL means the same page can satisfy every query.

Consequences may include unclear page scope, mismatched content, and poor research decisions. These are practical risks, not guaranteed ranking outcomes.

### 7.2 Under-Clustering

**Under-clustering** happens when close query variants that could reasonably be handled together are split into too many groups.

Common causes:

- Treating every wording variation as a separate topic.
- Overreacting to small SERP differences from one snapshot.
- Ignoring shared tasks and intent.
- Splitting queries because their metrics differ, even when their underlying need is similar.

Consequences may include unnecessary page proposals, duplicated research, and an unnecessarily fragmented content plan.

### 7.3 The Goal Is Not the Largest or Smallest Cluster

A useful cluster is as broad as it can be **without combining materially different needs**, and as narrow as it needs to be **to preserve a coherent task and page purpose**.

There is no universal ideal number of keywords per cluster. Cluster size depends on the query set, topic, market, available evidence, and the research decision being made.

## 8. Worked Example: Home Espresso Grinder Queries

The following example is fictional and illustrative. It is not based on a live SERP audit, real keyword metrics, or an actual business.

### Candidate queries

| Query | Preliminary task / intent hypothesis |
|---|---|
| best espresso grinder | Compare available grinders; commercial investigation |
| espresso grinder reviews | Evaluate products using reviews; commercial investigation |
| espresso grinder for home | Find a suitable home-use grinder; mixed investigation / transaction |
| buy espresso grinder | Purchase a grinder; transactional |
| how to clean espresso grinder | Learn a maintenance task; informational |
| espresso grinder not grinding fine enough | Troubleshoot a problem; informational / troubleshooting |
| espresso grinder burr replacement | Find a replacement part or repair guidance; mixed task |
| espresso grinder price comparison | Compare prices and offers; commercial investigation / transaction |

### Candidate grouping

| Provisional cluster | Queries | Reasoning |
|---|---|---|
| Product comparison | best espresso grinder; espresso grinder reviews; espresso grinder for home; espresso grinder price comparison | Similar evaluation goal is plausible, but the “for home” and price-comparison queries need SERP review before final assignment. |
| Purchase | buy espresso grinder | Direct purchase wording suggests a distinct action-oriented task; inspect SERP evidence before deciding whether it belongs with a comparison group. |
| Cleaning and maintenance | how to clean espresso grinder | A specific instructional task, distinct from product selection. |
| Troubleshooting | espresso grinder not grinding fine enough | Problem diagnosis and resolution, not product comparison. |
| Parts and repair | espresso grinder burr replacement | Could mean buying a replacement burr set or learning how to replace it; remains provisional until intent and SERP evidence clarify the task. |

### What happens next?

This initial grouping is not a final page map. SERP observations may support merging the purchase query with a broader product group, or may confirm a distinct purchase destination. The burr-replacement query may need separate purchase and instructional variants if the expanded query set and SERPs show distinct tasks.

The point is to preserve the ambiguity until evidence resolves it—not to invent certainty because a table looks nicer when every row is finalized.

## 9. What Keyword Clustering Is Not

### 9.1 Not Search Intent Classification

Intent labels are established and interpreted in 05.5, then tested against observed results in 05.6. Clustering uses those findings as evidence; it does not replace the earlier analysis.

### 9.2 Not Semantic Entity or Topic Modeling

Keyword clusters group queries for SEO research and potential targeting decisions. They are not a complete model of entities, attributes, relationships, or topical architecture. Semantic SEO and entity/topic modeling belong to Domain 09.

### 9.3 Not Search-Engine Query Clustering

Search engines may cluster queries, refinements, documents, or subtopics for their own system purposes. Academic studies of search-log query clustering demonstrate particular research methods using behavioral data such as clicks and session co-occurrence. Those methods are not equivalent to an SEO practitioner grouping exported keyword lists, and the underlying search logs are not generally available to an outside researcher. [1][2]

### 9.4 Not URL Canonicalization or Duplicate-Page Clustering

Google's canonicalization process groups duplicate or very similar **pages/URLs** and selects a representative URL. That is a search-engine indexing process, not the same thing as an SEO researcher grouping **queries** into keyword clusters. [3]

A keyword cluster may later inform page planning, but it does not itself determine canonical URLs, redirects, or indexation behavior.

### 9.5 Not a Command to Create One Page Per Cluster

Clusters inform page planning; they do not dictate it. A final page decision must consider whether a page is useful, distinct, feasible, and aligned with the site's purpose. Avoid generating near-identical pages simply to target slightly different query variants. Google's spam policies identify doorway abuse as creating pages for similar queries that funnel users to the same destination, and scaled content abuse as producing large amounts of unoriginal content without user value. [4]

## 10. Output and Handoff

A completed clustering pass should produce:

- A normalized query inventory with source provenance.
- Cluster IDs and concise cluster labels.
- Primary query and member-query lists.
- Primary and secondary intent labels.
- A task statement for each cluster.
- SERP overlap evidence and observation context where collected.
- Lexical, semantic, and business-context notes where used.
- Merge, split, and provisional decisions with rationale.
- Confidence and unresolved exceptions.
- A change history for material cluster revisions.
- A handoff for opportunity assessment in [05.8 — Keyword Opportunity & Prioritization](README.md#domain-structure) and page mapping in [05.9 — Keyword-to-Page Mapping & Research Deliverables](README.md#domain-structure).

The output should let another researcher understand not only which queries were grouped, but **why** they were grouped and what evidence could change the decision.

## Key Takeaways

- Cluster queries by shared need and task—not just shared words.
- Use intent, SERP overlap, lexical similarity, semantic similarity, and business context as complementary evidence.
- SERP-overlap scores are descriptive heuristics; no universal threshold guarantees a shared page target.
- Keep SERP comparisons consistent in engine, market, language, device, date, and result depth.
- Split groups when queries require materially different answers or page purposes.
- Keep uncertain groups provisional rather than manufacturing certainty.
- Keyword clustering is not semantic entity modeling, search-engine query processing, or URL canonicalization.
- A cluster informs prioritization and page mapping; it does not automatically dictate page creation.

**Bottom line:** a useful cluster represents a coherent search task. If the group only makes sense because the spreadsheet says so, the grouping is not ready.

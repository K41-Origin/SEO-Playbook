# 11.7 — Internal-Link Auditing and Analysis

**Domain:** [11 — Internal Linking](README.md)  
**Topic:** 11.7  
**Status:** Researched draft  
**Canonical focus:** A repeatable, evidence-based method for collecting, validating, analysing, classifying, and reporting a website's internal-link relationships.

An internal-link audit examines the hyperlinks that connect pages within a defined website scope. It turns a collected set of source-to-target relationships into evidence that publishers can use to understand link implementation, identify relationship-level defects, evaluate structural patterns, and decide what deserves further investigation.

An audit is not simply a crawler export, a tool score, or a list of URLs. Its conclusions depend on the population examined, crawl configuration, link-extraction rules, URL normalization, rendering conditions, data sources, and validation of findings.

This topic owns the **publisher-side audit of internal hyperlink relationships**. It does not replace the conceptual explanations of orphan pages, link depth, and coverage in [11.6 — Orphan Pages, Link Depth, and Link Coverage](11.6-Orphan-Pages-Link-Depth-and-Link-Coverage.md), nor does it redefine technical SEO auditing, search-engine crawling, or ranking-system link analysis.

## 1. Audit Objectives and Scope

Start with the decision the audit is intended to support. Different objectives require different evidence and coverage.

Common objectives include:

- Establishing a baseline of internal-link relationships across a website.
- Finding internal links that point to broken, redirected, or otherwise unintended destinations.
- Identifying pages with unexpected inbound or outbound link patterns.
- Reviewing anchor text and link placement across page groups.
- Comparing internal-link patterns across templates, sections, locales, or page types.
- Validating internal-link changes after a content release, redesign, migration, or URL restructuring.
- Investigating a specific relationship or navigation problem reported by users or stakeholders.

Before collection begins, record:

| Scope field | What to define |
|---|---|
| Property boundary | Protocols, hostnames, subdomains, subdirectories, locales, applications, and environments included. |
| Page population | Intended page classes, URL sources, exclusions, and treatment of redirects, duplicates, non-indexable pages, and utility URLs. |
| Link population | Which link types count: HTML anchor links, navigation, contextual links, pagination, image links, rendered links, or other explicitly selected relationships. |
| Crawl entry points | Homepage, section roots, locale roots, uploaded URL lists, or a combination. |
| Rendering and state | HTML-only or rendered extraction, viewport, authentication, cookies, interaction states, and user-agent configuration. |
| Crawl controls | Robots handling, allowed paths, crawl limits, rate limits, timeouts, retries, and excluded URL patterns. |
| Observation window | Collection date, release/version context, and whether the site changed during the audit. |
| Acceptance criteria | What constitutes a finding, its evidence requirements, and who decides whether it needs remediation. |

A crawl beginning at one homepage does not necessarily represent every subdomain, locale, authenticated area, or disconnected application. A list-mode crawl may inspect supplied URLs without discovering every page reachable through ordinary navigation. State these limits explicitly.

## 2. Understand the Audit Data Model

A useful audit preserves both page-level summaries and the underlying link records.

### 2.1 Page records

A page record represents a URL or a documented normalized page identity. Depending on the audit, useful fields may include:

- Observed URL and normalized URL.
- Host, path, locale, and page type.
- Response status and final destination, when HTTP validation is in scope.
- Declared canonical URL, where collected.
- Indexability or robots directives, when relevant to interpretation.
- Crawl depth from the selected start point.
- Number of incoming and outgoing link records.
- Unique source-page count and unique target-page count.
- Template, section, or other grouping metadata.
- Collection timestamp and observation context.

These fields are not interchangeable. For example, a URL's response status, canonical declaration, and presence in the internal-link graph answer different questions. Technical interpretation of response behavior and canonicalization belongs to Domain 10.

### 2.2 Link records

A link record represents an observed relationship from a source page to a destination URL. Preserve, where available:

- Source URL.
- Raw destination URL as written in the link.
- Resolved destination URL.
- Normalized destination identity used for grouping.
- Link text or anchor text.
- Link element/type, such as text link or linked image.
- Link position or component, such as navigation, main content, sidebar, or footer.
- Relevant link attributes, such as `rel` values.
- Whether the link was present in source HTML or appeared after rendering.
- Extraction timestamp and crawl context.

Do not collapse all link observations into a single count too early. A page may contain several link instances to the same target, while the target may receive links from only one unique source page. Both counts can be useful, but they describe different things.

### 2.3 Distinguish link instances, unique source pages, and page relationships

Consider a site-wide header that links to the same destination from 500 pages:

- **Link instances:** the number of observed occurrences of that hyperlink across source pages.
- **Unique linking pages:** the number of distinct source pages that link to the destination.
- **Unique page relationships:** the number of distinct source-to-target page pairs.

If multiple anchors on one source page point to the same target, they may be separate link instances but one unique page relationship. The audit should retain the raw records and state which unit each reported metric counts.

Repeated template links can dominate raw counts. Do not interpret a large instance count as evidence of many independent editorial relationships or strong user relevance.

## 3. Collect Internal-Link Evidence

### 3.1 Use a crawler as an observation instrument

A crawler can follow and record internal links according to its own extraction rules and configuration. It does not reveal every possible link or every state a user can reach.

For example, Screaming Frog documents that its default internal-hyperlink collection is based on URLs contained in HTML anchor elements, and that internal scope, subdomain handling, nofollow behavior, rendering, and crawl limits depend on configuration. These are tool-specific implementation details, not universal properties of every crawler. [3]

Before collecting data, review the crawler's documentation for:

- Internal-domain and subdomain scope.
- HTML versus JavaScript-rendered extraction.
- Link types included or excluded.
- Nofollow and other link-attribute handling.
- Robots.txt and authentication behavior.
- Crawl-depth and URL-count limits.
- URL parameter handling and exclusions.
- Redirect handling and canonical extraction.
- Rate limits, retries, and resource constraints.

Record the configuration or export it alongside the crawl. Without it, another analyst may be unable to reproduce the same link population.

### 3.2 Select the collection approach

| Collection approach | Useful for | Important limitation |
|---|---|---|
| Website crawl from declared roots | Discovering and recording relationships reachable by the crawler's rules | Cannot reveal links outside the crawl boundary or in unobserved states. |
| URL-list or list-mode crawl | Inspecting a known URL set and collecting links on those pages | Does not by itself prove the supplied pages are fully connected or that all site pages were found. |
| Rendered crawl | Observing links inserted into the rendered page under the chosen browser and interaction state | Results depend on rendering, scripts, timing, viewport, and state configuration. |
| CMS or application export | Comparing intended content inventory with observed links | A content record is not proof that a hyperlink is implemented or visible. |
| Search Console Links report | Supplementary view of internal links known to Google | It is not a comprehensive or real-time export of every internal link. |
| Sitemap inventory | Identifying URLs the publisher declares in a sitemap | Sitemap entries are not internal hyperlink records. |

Google's Search Console Links report includes a table of top internally linked pages and lets users inspect pages linking to a selected URL. Google also documents important limitations: the report is a sample rather than a comprehensive list, tables are limited, URLs are grouped by canonical URL, duplicate links are combined, and reported links may have been found over time and since changed. Treat it as supplementary Google-observed evidence, not the audit's complete link database. [1]

### 3.3 Reconcile separate inventories

A strong audit may compare several URL populations:

- URLs found through the internal-link crawl.
- URLs listed in XML sitemaps.
- URLs exported from the CMS or application.
- URLs included in a curated list of important pages.
- URLs surfaced by Search Console or analytics reports.

These inventories have different purposes and collection rules. A URL present in a sitemap or CMS export but absent from a crawl is a candidate for investigation, not automatically an orphan or a defect. It may be outside the crawl scope, blocked from the crawler, dependent on an unobserved state, or intentionally standalone.

Google explains that properly linked important pages can usually be discovered through navigation or links on pages, while sitemaps can supplement discovery for larger or more complex sites. That guidance concerns Google's discovery process; it does not make a sitemap equivalent to an internal hyperlink. [2]

## 4. Validate the Collected Dataset

Do not interpret a crawler export until the data population and extraction behavior have been checked.

### 4.1 Check crawl coverage

Review:

- Whether the declared start URLs were successfully fetched.
- Whether expected hostnames, subdomains, locales, and sections were included.
- Whether crawl limits stopped collection before the intended scope was reached.
- Whether robots rules, authentication, redirects, or exclusions affected the population.
- Whether important templates and page types appear in the dataset.
- Whether pagination, filters, infinite scroll, and interaction-dependent routes require separate treatment.
- Whether a second crawl or representative manual inspection reveals missing link types.

A crawl that terminates normally can still be incomplete relative to the intended audit scope.

### 4.2 Validate link extraction

Inspect representative source pages and compare their actual links with the extracted records. Include different templates and link positions, not only the homepage.

Check for:

- Standard anchor elements with valid `href` destinations.
- Links inserted or modified by JavaScript.
- Links exposed only after user interaction.
- Linked images and their associated text alternatives.
- Fragment-only links and links to page sections.
- Repeated navigation, footer, and sidebar links.
- Links with `nofollow` or other `rel` attributes.
- Links to URLs outside the declared internal boundary.

Google documents that it can generally parse links implemented as an HTML `<a>` element with an `href` attribute, including links inserted dynamically when they use that markup. It warns that other elements or script-event-only patterns may not be reliably extracted by Google. This is Google-specific guidance; a crawler's extraction behavior must be checked separately. [4]

### 4.3 Normalize URLs carefully

URL normalization affects whether the audit treats two observed destinations as the same page. Document how the dataset handles:

- HTTP versus HTTPS.
- Hostname and subdomain variations.
- Trailing slashes and path case.
- Default ports.
- Percent-encoding.
- Query parameters and tracking parameters.
- URL fragments.
- Redirect destinations.
- Canonical declarations.
- Locale and alternate URL patterns.

Do not blindly remove every query parameter or fragment. Parameters may identify distinct content, filters, pagination states, or application routes; fragments may identify sections within a document. Canonical declarations are signals to interpret, not a license to overwrite the raw URL evidence.

Retain both the original destination and the normalized grouping key. If normalization merges URLs, document the rule and validate that the merge does not collapse distinct resources.

### 4.4 Preserve provenance

Every export or derived table should retain enough metadata to identify:

- Source tool and version, where available.
- Crawl configuration or settings profile.
- Collection date and time.
- Starting URL or uploaded URL list.
- Rendering and authentication context.
- Scope exclusions and crawl limits.
- Transformation and normalization rules.
- Manual corrections or exclusions.

This makes the findings traceable and supports meaningful comparison between audit runs.

## 5. Analyse Internal-Link Relationships

The analysis should answer questions relevant to the declared audit objective rather than produce metrics for their own sake.

### 5.1 Inlinks and outlinks

Review incoming and outgoing relationships by page, page class, template, and site section.

Useful questions include:

- Which intended important pages have no observed inbound links?
- Which pages receive links only from a recurring global component?
- Which source pages contain unusually many outgoing internal links for their role?
- Are expected relationships between related content groups present?
- Are there source pages that link to destinations no longer relevant to their content?
- Are important destinations receiving links from relevant pages, or only from generic site-wide elements?

The count of inlinks alone does not establish link quality, user value, or search-engine ranking impact. Interpret the number alongside source diversity, location, relevance, destination purpose, and page role.

### 5.2 Anchor text and link placement

Analyse anchor text in relation to its source and destination, not as a detached keyword-frequency report.

Review:
- Empty or missing text alternatives on linked elements where relevant to the audit scope.
- Repeated generic anchors that make destinations difficult to distinguish.
- Anchors that misrepresent the destination.
- Unexpectedly inconsistent labels for the same destination.
- Links whose surrounding passage does not explain why the destination is useful.
- Link-position patterns, such as whether a destination is linked only in a footer or recurring navigation.

Topic [11.4 — Contextual Internal Linking and Anchor Text](11.4-Contextual-Internal-Linking-and-Anchor-Text.md) owns the editorial principles for judging contextual relevance and descriptive wording. This audit topic owns the method for collecting and examining the observed anchor and position data.

Google recommends descriptive, relevant anchor text and explains that link context helps people and Google understand destinations. Use that guidance as a source for evaluation, not as a fixed anchor-text formula. [4]

### 5.3 Link distribution and page groups

Summarize link data across meaningful groups:

- Content types and templates.
- Navigation sections and subdirectories.
- Locale or regional page sets.
- Product, category, and editorial collections.
- Recently published or substantially updated pages.
- Pages identified as important by the site's own objectives.

Group comparisons can reveal a template that fails to expose expected links, a section with few observed connections, or a class of pages that receives links only from repeated global components.

Do not compare unlike populations without explaining the difference. A product catalogue, documentation library, and editorial blog may have different legitimate link distributions.

### 5.4 Depth, orphan candidates, and coverage findings

Use the audit dataset to identify candidates for deeper structural review:

- Pages with zero observed qualifying inlinks.
- Pages not reached from the selected crawl roots.
- Pages with high observed crawl depth under the selected crawler configuration.
- Important pages with few unique linking source pages.
- Page groups with unexpected gaps in their observed relationships.

These are audit findings or candidates, not final judgments. Interpret them using the definitions and scope rules in [11.6 — Orphan Pages, Link Depth, and Link Coverage](11.6-Orphan-Pages-Link-Depth-and-Link-Coverage.md).

In particular, a crawler's recorded discovery depth is a property of that crawl run and its discovery sequence. It should not be silently treated as a fully calculated shortest-path depth for every possible root, nor as a universal user click count.

### 5.5 Relationship status and destination outcomes

An internal link may point to a destination that:
- Resolves successfully.
- Redirects to another URL.
- Returns a not-found or server-error response.
- Is blocked or unavailable under the audit's request context.
- Resolves to a duplicate or non-canonical variant.
- Is outside the declared site boundary.

Record the source-to-target relationship and the observed outcome separately. For example, a link pointing to a redirected URL is an observed relationship plus a destination-response finding. The technical diagnosis and remediation of HTTP behavior, canonicalization, robots access, and rendering belong to Domain 10. Domain 11 can report the relationship-level impact and link-maintenance implications without duplicating the technical explanation.

## 6. Classify Findings and Prioritize Review

An audit should separate observations from validated issues and remediation decisions.

| Finding class | Example observation | Initial interpretation |
|---|---|---|
| Missing relationship | An expected page has no observed inbound internal link | Compare with the intended page population and Topic 11.6 before classifying it as an orphan. |
| Weak or narrow source coverage | A key destination receives links from only one relevant source page | Review source diversity and user journeys; do not equate count with quality. |
| Unexpected depth | A key page is reached only after many crawl hops | Verify roots, crawl scope, and alternative routes before deciding whether the route is poor. |
| Broken destination relationship | An internal link points to a URL returning an error | Preserve source and target evidence; route technical diagnosis to Domain 10. |
| Redirecting destination relationship | An internal link points through a redirect | Check whether the source should link directly to the intended final destination; technical redirect policy belongs to Domain 10. |
| Anchor/context mismatch | Link wording or source passage misrepresents the target | Review against Topic 11.4. |
| Template-level inconsistency | One template omits a relationship found on equivalent templates | Confirm whether the difference is intentional before proposing a template change. |
| Scope or extraction gap | Expected links are absent from the collected dataset | Revisit crawl settings, rendering, access, and collection sources before reporting a site defect. |

### 6.1 Prioritize with explicit criteria

Prioritization should reflect the audit's objective and the consequences of the observed relationship—not a vendor score or universal formula.

Consider:

1. **Page importance:** Is the destination important to a documented user task or site objective?
2. **Relationship relevance:** Does the source page provide a genuine reason to link to the destination?
3. **Reachability impact:** Does the finding affect a meaningful route or a broad page group?
4. **Audience impact:** Does it affect a critical user journey, locale, or access context?
5. **Scale and recurrence:** Is it isolated, template-wide, or repeated across a large population?
6. **Evidence confidence:** Has the finding been reproduced and manually checked where necessary?
7. **Remediation ownership:** Is the appropriate action owned by content, navigation, engineering, or technical SEO?

A high-volume issue is not automatically high priority. A single broken link on a critical task route may matter more than many low-impact anomalies. Conversely, a template-level defect may deserve attention because it affects many pages. State the rationale for priority assignments.

## 7. A Repeatable Internal-Link Audit Workflow

1. **Define the objective and scope.** Record property boundaries, page population, eligible link types, crawl roots, observation context, exclusions, and intended decisions.
2. **Build the comparison inventories.** Gather the relevant CMS/page list, sitemap URLs, critical-page list, and other evidence sources required by the objective.
3. **Configure the crawler.** Set internal scope, rendering, robots and authentication behavior, link extraction, crawl limits, and rate controls. Save the configuration.
4. **Collect page and link records.** Export the raw source-to-target relationships, page-level data, crawl metadata, and relevant destination outcomes.
5. **Validate collection coverage.** Check expected sections, templates, crawl limits, rendering states, and representative pages manually.
6. **Normalize without losing raw evidence.** Apply documented URL identity rules while retaining original URLs and transformation provenance.
7. **Reconcile inventories.** Compare crawl-discovered pages and relationships with the declared page population and supplementary sources. Keep each source's meaning distinct.
8. **Analyse the relationships.** Review inlinks, outlinks, unique linking pages, anchor text, link position, page groups, depth, orphan candidates, and destination outcomes as required by the audit objective.
9. **Validate candidate findings.** Re-open representative source pages and links; confirm that each finding is not a scope, rendering, normalization, or extraction artifact.
10. **Classify and prioritize.** Record evidence, impact, confidence, owner, and rationale. Refer technical findings to the appropriate Domain 10 topic.
11. **Recommend actions.** Link decisions should follow the principles in Topics 11.2–11.5; orphan/depth/coverage interpretation should follow 11.6; lifecycle ownership belongs to 11.8.
12. **Report and preserve the baseline.** Record the dataset, configuration, date, findings, exclusions, limitations, and next steps so later audits can be compared responsibly.

## 8. Reporting and Comparing Audit Results

A useful audit report should allow another person to understand what was examined, what was found, and how confidently the conclusions can be acted on.

Include:

- Audit objective and decision context.
- Property, URL, and page-class scope.
- Collection date, tool/version, crawl roots, and configuration.
- Link-extraction and URL-normalization rules.
- Inventory sources and reconciliation method.
- Coverage limitations, exclusions, and unobserved states.
- Findings with source URL, destination URL, link evidence, and relevant context.
- Classification, impact, confidence, priority rationale, and proposed owner.
- Representative validation evidence.
- Before/after comparison rules, if the audit is repeated.

When comparing two audits, check that the site scope, URL identity rules, crawler version/configuration, rendering, crawl roots, exclusions, and collection timing are sufficiently comparable. A change in tool configuration can change the observed dataset without any corresponding change to the website.

Avoid presenting a single site-wide score as a complete measure of internal-link quality. If a summary metric is used, define its unit, denominator, exclusions, and purpose. Keep raw counts, unique source-page counts, page-level distributions, and qualitative validation distinguishable.

## 9. Common Audit Failures and Misinterpretations

- **Treating a crawler export as a complete census:** every crawl is constrained by its entry points, configuration, rendering, and access.
- **Treating Search Console's Links report as exhaustive:** Google explicitly describes it as a sample and documents grouping and row limitations. [1]
- **Treating sitemap URLs as observed internal links:** a sitemap is a separate URL inventory, not a page-to-page hyperlink record. [2]
- **Confusing link instances with unique linking pages:** repeated template links can inflate raw occurrence counts.
- **Treating crawler crawl depth as an absolute property:** it depends on the selected start point, crawl rules, and observed discovery sequence.
- **Calling every zero-inlink candidate a confirmed orphan:** validate the page population, graph scope, and extraction conditions using Topic 11.6.
- **Treating every low-inlink page as defective:** page role, intentional standalone status, relevance, and audience needs matter.
- **Treating a tool's proprietary link metric as a Google metric:** vendor metrics describe the vendor's model unless independently established otherwise.
- **Treating a link count as a ranking prediction:** link counts do not prove search-engine weighting, indexation, or ranking outcomes.
- **Fixing technical symptoms in the wrong domain:** HTTP response, canonicalization, robots, and rendering remediation belong to Domain 10.
- **Comparing unlike audits:** changed scope or configuration can explain apparent changes in link counts and depth.
- **Reporting findings without source evidence:** every actionable issue should retain the actual source-to-target relationship and enough context to reproduce it.
